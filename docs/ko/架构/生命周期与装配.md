# 생명주기와 조립

이 문서는 `plugin.gd`가 runtime object를 어떻게 조립하고, Dock을 등록하며, Autoload와 debug bridge를 연결하고, 완전 재로드나 종료 시 어떻게 정리하는지 설명합니다.

---

## 핵심 진입점

현재 플러그인 진입점은 `addons/godot_dotnet_mcp/plugin.gd`이며, 타입은 `EditorPlugin`입니다. 더 이상 모든 business logic을 직접 들고 있지 않습니다. 대신 다음 객체들을 조립하는 얇은 wiring layer 역할을 합니다.

- `LocalizationService`
- `PluginRuntimeState`
- `SettingsStore`
- `ServerRuntimeController`
- `ToolCatalogService`
- `ClientConfigService`
- `UserToolService` (`user_tool_catalog_service.gd`와 `user_tool_maintenance_service.gd`에 위임)
- `PluginReloadCoordinator`
- `MCPRuntimeDebugStore`
- `plugin/features/server_feature.gd`
- `plugin/features/config_feature.gd`
- `plugin/features/ui_state_feature.gd`
- `plugin/features/user_tool_feature.gd`
- `plugin/features/reload_feature.gd`
- `plugin/features/tool_profile_feature.gd`
- `plugin/features/tool_access_feature.gd`
- `plugin/features/self_diagnostic_feature.gd`
- `PluginSelfDiagnosticStore`
- `plugin/presenters/dock_model_service.gd`
- `plugin/presenters/dock_presenter.gd`
- `plugin/presenters/client_config_presenter.gd`
- `ui/mcp_dock.tscn`

따라서 entry point는 주로 wiring, synchronization, bridging을 담당합니다. 복잡한 UI logic이나 tool implementation은 직접 소유하지 않습니다.

---

## `_enter_tree()` 조립 순서

`plugin.gd._enter_tree()`는 현재 다음 순서로 실행됩니다.

1. 이전 self-diagnostic cache를 지웁니다.
2. `PluginRuntimeState`를 다시 만듭니다. 그래야 hot reload 시 종료 과정에서 이미 비워진 stale state container를 재사용하지 않습니다.
3. `_refresh_service_instances()`를 통해 현재 service bundle을 새로 고칩니다.
4. `_load_state()`를 호출해 settings file과 custom profile을 읽습니다.
5. localization을 초기화하고 다시 적용한 뒤 현재 language를 반영합니다.
6. log level을 `MCPDebugBuffer`와 맞춥니다.
7. `PluginRuntimeCoordinator`를 통해 `ServerRuntimeController`를 만들고 연결한 뒤, 모든 server signal을 한 곳에서 연결합니다.
8. `PluginRuntimeCoordinator`를 통해 runtime bridge Autoload `MCPRuntimeBridge`를 설치합니다.
9. `PluginRuntimeCoordinator`를 통해 editor debug bridge `MCPEditorDebuggerBridge`를 설치합니다.
10. `ui/mcp_dock.tscn`을 인스턴스화해 붙입니다.
11. settings를 처음 불러온 경우 default profile에서 `disabled_tools`를 유도합니다.
12. 첫 `_refresh_dock()` 호출로 UI model을 투영합니다.
13. `_process()`에서 polling을 시작합니다.
14. `auto_start=true`이면 embedded MCP service를 자동 시작하고, settings projection, server node, HTTP server, tool loader, stdio stage에 걸린 시간을 plugin self-diagnostic action log에 기록합니다.
15. 재로드 전에 저장해 둔 focus snapshot이 있으면 Dock tab과 focus를 복원합니다.

진입점은 이제 `PluginActionRouter`, `PluginDockCoordinator`, `PluginRuntimeCoordinator`를 hot path에서 느리게 만드는 대신 안정적인 collaborator로 유지합니다. `PluginDockCoordinator`는 plugin 전용 dock create, remove, recreate, stale cleanup, signal wiring, dock instance counting을 담당합니다. `PluginRuntimeCoordinator`는 server controller, runtime bridge, debugger bridge의 생명주기를 담당합니다.

`ServerRuntimeController`의 생성, 연결, signal wiring, 분리, 재생성은 모두 `PluginRuntimeCoordinator`에 있으며, Dock 생명주기 wrapper는 `PluginDockCoordinator`에 있습니다.

## `_exit_tree()` 정리 순서

종료 시 플러그인은 Godot의 자연스러운 node release에만 의존하지 않습니다. 명시적으로, 그리고 순서대로 정리합니다.

1. `_process()`를 멈춥니다.
2. 현재 settings를 저장합니다.
3. Dock을 제거합니다.
4. editor debug bridge를 unload합니다.
5. `PluginRuntimeCoordinator`를 사용해 server signal을 끊고, `detach()`를 실행하고, controller reference를 지웁니다.
6. entry point가 들고 있던 feature, presenter, action router, service reference와 object graph를 명시적으로 비웁니다.
7. localization singleton을 초기화 상태로 되돌립니다.
8. 다음 hot reload에서 stale instance를 재사용하지 못하도록 entry point의 service reference를 비웁니다.

이 순서는 완전 재로드나 plugin disable 동안 남는 상태를 줄이기 위한 것입니다.

## Dock 조립 체인

Dock은 이제 `PluginDockCoordinator`의 고수준 API로 조립되며, 내부 단계는 다음과 같습니다.

1. 이전 instance를 지웁니다.
2. hot reload 뒤에 남아 있을 수 있는 stale Dock을 제거합니다.
3. `ui/mcp_dock.tscn`을 load합니다.
4. root node를 instantiate하고 모든 tab signal을 연결합니다.
5. `add_control_to_dock(DOCK_SLOT_RIGHT_UL, _dock)`로 editor에 등록합니다.
6. 하나보다 많은 instance가 발견되면 self-diagnostic incident를 기록합니다.

entry point와 Dock의 관계는 일방향입니다.

- Dock은 service object를 소유하지 않습니다.
- Dock은 signal과 `apply_model()`만 노출합니다.
- wiring 동안 `plugin.gd`는 signal을 feature나 안정적인 bridge method로, 다시 concrete service로 연결합니다.

## Runtime Bridge와 Debug Bridge

### Runtime Bridge Autoload

`PluginRuntimeCoordinator`는 project에 다음이 존재하도록 보장합니다.

- Name: `MCPRuntimeBridge`
- Path: `res://addons/godot_dotnet_mcp/plugin/runtime/mcp_runtime_bridge.gd`

다른 script가 같은 이름의 Autoload를 이미 소유하고 있으면, 플러그인은 이를 강제로 바꾸지 않습니다. 대신 다음을 수행합니다.

- runtime bridge state를 실패로 표시합니다.
- self-diagnostics에 incident를 기록합니다.
- 플러그인의 나머지는 계속 동작하게 둡니다.

### Editor Debug Bridge

`PluginRuntimeCoordinator`는 `MCPEditorDebuggerBridge`를 instantiate하고 `EditorDebuggerPlugin`으로 등록하여, 실행 중인 main project의 debugger session summary를 플러그인이 읽을 수 있는 데이터로 동기화합니다.

또한 다음도 담당합니다.

- `ServerRuntimeController`의 생성, attach, signal wiring, detach, 재생성
- `plugin.gd`가 server-controller 생명주기 상세에서 멀어지도록 유지

## 상태 Polling과 Model 갱신

플러그인은 모든 service state change를 깊은 dependency notification으로 바꾸지 않습니다. 대신 가벼운 polling을 사용합니다.

- `plugin.gd._process()`는 `0.5s`마다 `_refresh_dock()`를 호출합니다.
- `_refresh_dock()`는 shared model을 다시 만들고, `dock_model_service.gd`에 Dock context aggregation을 맡긴 뒤 presenter script로 전달합니다.
- `mcp_dock.gd.apply_model()`은 model을 세 탭으로 분배합니다.

장점은 다음과 같습니다.

- entry logic이 단순하고 state-sync 경로가 분명합니다.
- language, scaling, service state, statistics를 함께 갱신할 수 있습니다.
- UI controller가 pure presentation layer에 가깝게 유지됩니다.

## 완전 재로드 전략

플러그인은 두 가지 reload를 지원합니다.

### 1. Runtime Reload

`plugin_runtime_reload` domain soft-reload action이나 server page를 통해 트리거됩니다. 전체 플러그인 instance를 무너뜨리지 않고 tool domain이나 server를 갱신합니다.

### 2. Full Plugin Reload

`system_plugin_reload(action="full_reload_plugin")`, 호환용 entry `plugin_runtime_reload(action="full_reload_plugin")`, 또는 Home page의 full-reload button으로 트리거됩니다. 그 뒤 `PluginReloadCoordinator`가 Godot plugin layer를 다음 순서로 이끕니다.

1. `set_plugin_enabled(false)`
2. 이전 server node와 TCP listener가 해제될 짧은 대기
3. `set_plugin_enabled(true)`

coordinator는 plugin node 아래가 아니라 editor `base_control` 아래에 있으므로, plugin이 비활성화된 뒤에도 다시 활성화 단계를 끝낼 수 있습니다. 현재의 짧은 재활성화 지연은 옛 `TCPServer`가 포트를 놓는 중인데 새 plugin instance가 자동 시작되며 생기는 경합을 줄이는 데 도움이 됩니다.

완전 재로드 전에 플러그인은 다음을 기록합니다.

- 현재 host Dock tab
- `MCPDock` 안의 현재 inner tab
- focus된 control의 relative path

재로드 뒤에는 host Dock을 다시 활성화하고, 그 다음 inner tab과 focus를 복원합니다.

디스크상의 addon copy를 업데이트하는 것과 실행 중인 instance를 재로드하는 것은 서로 다른 단계입니다. `addons/godot_dotnet_mcp/`를 복사, 업데이트, 설치하는 작업은 대상 project의 디스크 파일만 바꿉니다. 실행 중인 editor instance는 디스크 파일이 바뀌었다고 해서 스스로 교체되지 않습니다. Settings sync가 성공하고 archive write와 `.mcp_sync.json` freshness marker write가 모두 성공하면, 플러그인은 새로 써진 plugin file이 현재 editor에서 적용되도록 전체 생명주기 재로드를 예약합니다. 다른 외부 디스크 업데이트의 경우 `system_plugin_reload(action="full_reload_plugin")`를 호출합니다. 재로드 후에는 `/health`, `system_plugin_reload(action="get_freshness")`, `plugin_runtime_state(action="get_self_health")`, 또는 `system_project_state(include_runtime_health=true).runtime_health.freshness`로 `running_instance`, `disk_source`, `sync`, `comparison`을 확인하고 `needs_lifecycle_reload=false`를 검증합니다.

## 경계와 책임

### `plugin.gd`의 책임

- 생명주기
- service object wiring
- Dock scene 진입점
- UI signal과 feature/service bridge 연결
- feature workflow 설정
- Dock model collaborator wiring과 presenter 호출
- `tool_loader`가 쓸 안정적인 tool access state entry 노출
- settings 읽기와 쓰기 트리거
- self-diagnostic incident 기록

### `plugin.gd`가 책임지지 않는 것

- 구체적인 UI layout
- 각 탭의 control state machine
- Server, Config, User Tool, Runtime Reload, Profile, Config Exchange, Tool Access, Self Diagnostic 상호작용의 단계별 orchestration
- Dock tab state writeback, language switching, tree collapse persistence, copy-tip orchestration
- Dock create, remove, recreate, stale cleanup, signal wiring, dock instance counting 상세
- Dock context aggregation, tool-tree projection, installation detection 상세
- `tool_loader` tool access state lookup 구현
- tool protocol dispatch
- profile file read/write 상세
- client config merge logic
- tool-domain execution logic
