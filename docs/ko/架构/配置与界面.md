# 설정과 UI

## Dock 구조

현재 Dock은 세 가지 작업에 집중합니다.

- `Home`: 서비스 상태, 포트, 언어, 디버그 토글, 자체 진단 요약
- `Tools`: 도구 범주 토글과 통계
- `Config`: 외부 MCP client를 위한 연결 설정 표시와 기록

더 이상 담지 않는 내용은 다음과 같습니다.

- 작성자 소개 콘텐츠
- 홍보성 문구
- 도구 기능과 무관한 설명 블록

## 진입과 탭 책임

Dock entry는 여전히 Godot editor의 오른쪽에 `plugin.gd`가 등록하지만, node 구조는 scene 기반입니다.

- `ui/mcp_dock.tscn`: Dock root scene, title bar, status light, `TabContainer` 담당
- `ui/server_panel.tscn`: 서비스 상태와 기본 설정
- `ui/tools_tab.tscn`: tool tree, search, preview, category 및 tool toggle, collapse state
- `ui/config_panel.tscn`: client configuration과 command generation

controller script는 `apply_model(model)`만 받고 service object를 직접 소유하지 않습니다.

## `Home` 탭

### 표시 정보

- 상태: 서비스가 실행 중인지 여부
- 서비스 주소: 현재 host와 port로 만든 MCP 주소
- 활성 연결 수: 현재 연결된 client 수
- 총 요청 수: 총 request 수와 총 connection 수
- 최근 요청: 마지막 HTTP method와 시각

### 사용 가능한 작업

1. 포트 변경
2. auto-start 토글
3. debug logging 토글
4. 플러그인 언어 토글
5. 서비스 시작
6. 서비스 재시작
7. 서비스 중지
8. 플러그인 완전 재로드

### 동작 메모

- `Start`는 `plugin.gd -> ServerRuntimeController.start()`를 호출합니다.
- `Restart`는 먼저 `reinitialize()`를 호출한 다음 `start()`를 실행하며, 이 과정에서 port, debug mode, disabled-tool list가 새로 고쳐집니다.
- `Stop`은 `MCPServer` listener만 멈춥니다. Dock 자체는 제거하지 않습니다.
- `Full Reload Plugin`은 더 이상 단순한 runtime `detach()`와 `attach()`가 아닙니다. Godot plugin layer의 `set_plugin_enabled(false/true)`를 호출하는 별도 coordinator node가 이를 주도하므로, Project Settings에서 플러그인을 끄고 다시 켜는 동작에 더 가깝게 작동합니다.
- 완전 재로드 전에 플러그인은 `MCPDock`의 바깥쪽 탭, 안쪽 탭, 탭 내부의 focus snapshot을 기록합니다. 새 인스턴스가 시작되면 먼저 host Dock의 `MCPDock` 탭으로 돌아간 뒤, 내부 탭과 원래 포커스된 control을 복원합니다.
- 언어 전환은 `settings.language`만 갱신하고 가벼운 `apply_model()` 갱신을 트리거합니다. 더 이상 Dock 전체를 재구성하지 않습니다.
- 언어 전환과 완전 재로드 뒤의 focus 복원은 모두 원래 control만 복원하고 강제 focus를 하지 않는 규칙을 따릅니다. 원래 control이 더 이상 없거나 focus를 받을 수 없으면 플러그인은 조용히 넘어갑니다.
- 언어 메뉴는 `self-name (localized name)` 형식으로 표시됩니다. 예를 들면 `English (英文)` 또는 `日本語 (日语)`입니다.

## `Tools` 탭

### 사용 가능한 작업

1. 현재 표시 중인 도구 검색
2. 단일 도구, 카테고리, 전체 도메인을 켜거나 끄기
3. root, category, tool, atomic node의 collapse state 기억
4. 우클릭 메뉴로 localized name, English ID, schema 복사
5. `user` category에서 delete-user-tool 요청 시작
6. 선택한 항목의 설명, parameter summary, runtime information, atomic-tool preview 보기

### 동작 메모

- 도구 tree의 enabled count는 정적 하드코딩 데이터가 아니라 runtime service가 반환한 live tool list에서 계산합니다.
- 현재 메인 tree는 runtime-generated Tool Presentation Model을 우선합니다. `toolTree`는 도구 구조를 domain, category, high-level tool, atomic, action layer로 표현합니다. 예전 local group-tree logic은 이 model이 없을 때만 사용됩니다.
- `/api/tools`, MCP `tools/list`, stdio `tools/list`는 여전히 flat `tools[]`를 노출하지만, 이제 `toolTree`, `toolGroups`, `groupPath`, `treeChildren`도 함께 제공하므로 client와 Dock이 같은 presentation semantics를 공유할 수 있습니다.
- search 결과는 main controller가 tree를 다시 만들기 전에 별도 search collaborator가 미리 계산합니다.
- preview text는 독립 preview collaborator가 만들며, 현재 domain, category, tool, atomic, action node를 모두 포함합니다.
- `collapsed_system_tools` 설정은 tree에서 기본적으로 접히는 system tool을 제어합니다. 현재는 public builtin `system_*` tool을 포함합니다.

## `Config` 탭

config-generation logic은 UI script에서 분리되어 helper module이 담당합니다. 목표는 두 가지입니다.

- Dock code와 string template의 결합도를 낮춘다.
- 서로 다른 client config 변경이 UI layer로 직접 새어 나오지 않게 한다.

### 플랫폼 필터링

Config page의 상단은 먼저 Agent platform을 선택하고, 그다음 해당 platform에 대한 내용만 보여 줍니다. 더 이상 모든 platform을 하나의 긴 목록으로 쌓지 않습니다.

platform은 두 그룹으로 나뉩니다.

- Desktop 및 config-file client: Claude Desktop, Cursor, Trae, Codex Desktop, OpenCode Desktop, Windsurf, Cline, Roo Code, Cherry Studio
- CLI command client: Claude Code, Codex, Gemini, OpenCode, Qwen Code

### 권장 워크플로

Config page는 다음 순서로 사용하는 것이 좋습니다.

1. 상단 platform dropdown에서 대상 client를 선택한다.
2. page가 config-file 영역을 보여 주는지 CLI 영역을 보여 주는지 확인한다.
3. desktop client는 먼저 config path와 JSON content를 확인한 뒤 `Write Config`와 `Copy` 중 무엇을 쓸지 결정한다.
4. CLI client는 먼저 command text를 확인한다. client가 scope를 지원하면 `user / project` scope도 함께 확인한다.
5. copy 또는 write 후에는 client 쪽으로 돌아가 연결을 확인한다.

### Config-File 영역

현재 one-click write 대상은 다음과 같습니다.

- Claude Desktop
- Cursor
- Trae
- Windsurf
- Cline
- Roo Code
- OpenCode

각 항목에는 다음이 포함됩니다.

- config file path
- 쓸 JSON content
- one-click write button
- copy button

content area는 `PanelContainer + Label`로 만들어지며 `TextEdit.read_only` theme style을 재사용합니다. copy button은 content area의 오른쪽 위에 뜨는 floating button으로 표시되며, text나 icon으로 보여 줄 수 있습니다. Config page의 바깥쪽 group card와 client card는 `Tree.panel` background와 1 px `Editor.separator_color` border를 사용하므로, Tools page와 같은 background depth를 유지하면서도 card 경계는 분명하게 보입니다.

one-click write 동작은 다음과 같습니다.

1. 현재 JSON text를 파싱한다.
2. 대상 파일이 이미 존재하고 유효한 JSON이면 가능한 한 작은 변경만으로 병합한다.
3. 파일 안의 다른 server는 건드리지 않고 `mcpServers["godot-mcp"]` 노드만 갱신한다.
4. 필요하면 쓰기 전에 directory를 재귀적으로 생성한다.

추가 메모:

- `Write Config`는 `mcpServers["godot-mcp"]`만 갱신합니다. 대상 파일의 다른 MCP service는 지우지 않습니다.
- `Copy`는 text box에 현재 보이는 전체 config를 복사합니다. 버전 관리가 적용된 환경이나 제한된 환경에 수동으로 붙여넣을 때 유용합니다.

### CLI 영역

현재 CLI platform은 다음과 같습니다.

- Claude Code
- Codex
- Gemini
- OpenCode
- Qwen Code

이들 중:

- Claude Code, Gemini, Qwen Code는 scope dropdown (`user` / `project`)도 보여 줍니다.
- Codex와 OpenCode는 현재 command text, configuration file, 또는 direct-open-current-project action을 보여 줍니다.

CLI 영역은 다음 규칙을 따릅니다.

- `scope`는 user-level 또는 project-level configuration을 지원하는 CLI client의 command argument나 config path에 영향을 줍니다.
- CLI 영역은 client 자체 command line을 통한 one-click add 또는 remove를 우선합니다. 직접 command writing을 지원하지 않는 client도 copy 또는 open-config-file 흐름은 받을 수 있습니다.
- platform이 desktop client로 바뀌면 CLI 영역은 숨겨져, 서로 관련 없는 command가 동시에 보이지 않게 합니다.

## 설정 영속화

Editor 설정은 다음을 가져야 합니다.

- 기본값
- reset 경로
- 재시작 후 복원
- 현재 project와 현재 editor 사이의 명확한 경계

현재 영속화 경로는 다음과 같습니다.

| Path | Purpose |
|---|---|
| `user://godot_dotnet_mcp/settings.json` | port, language, auto-start, debug mode, disabled tools, collapse state, 완전 재로드용 임시 focus snapshot 저장 |
| `user://godot_dotnet_mcp/profiles/*.json` | custom tool profile 저장 |

load logic은 `plugin/config/settings_store.gd`에 있습니다.

- settings file이 아직 없으면 모든 category와 domain은 기본적으로 접힌 상태입니다.
- settings file이 이미 있으면 누락된 field는 호환성을 위해 채워 넣습니다.
- `tool_profile_id`가 비어 있으면 플러그인은 `system`으로 되돌아갑니다.

## 문서에서의 UI 제약

UI나 setting이 바뀌면 문서도 다음을 함께 설명해야 합니다.

- entry tab이 어디에 있는지
- setting key 또는 config field 이름
- 변화가 protocol layer에 영향을 주는지
- 기존 client config migration이 필요한지

## 구현 메모

### UI 연결

현재 연결 경로는 다음과 같습니다.

1. `plugin.gd._build_dock_model()`이 state, tool list, config text, `editor_scale`을 수집합니다.
2. `ui/mcp_dock.gd`가 model을 세 개의 탭으로 분배합니다.
3. `ui/server_tab.gd`가 현재 `Home` 탭 구현을 담당합니다. 먼저 `server_tab_model_projection.gd`를 통해 model을 순수 presentation data로 바꾼 뒤, text, button state, dropdown을 채웁니다. `ui/tools_tab.gd`와 `ui/config_tab.gd`는 여전히 자기 collaborator만 소비합니다.
4. 사용자 동작은 명시적인 signal을 통해 `plugin.gd`로 돌아가고, `plugin.gd`는 service object나 settings store를 호출합니다.

### UI 현지화

Dock root container, Home, Tools, Config 탭, Config의 client title, install state, log level, tool-tree name, high-level tool description은 모두 localization key에서 채웁니다. 더 이상 scene file 안의 하드코딩 text에 의존하지 않습니다.

Godot의 자동 번역이 흔한 영어 단어를 다시 바꾸지 않도록, Dock root container와 세 탭의 root control은 모두 `auto_translate_mode`를 명시적으로 끕니다. 따라서 플러그인 언어 전환은 editor의 global translation state가 아니라 `LocalizationService`가 직접 제어합니다.

도구의 runtime error message는 여전히 구조화된 `error`와 `message` 값으로 돌아오며, 호출 측이 tool semantics에 맞춰 처리합니다. Dock 안에 보이는 text는 계속 중앙 집중식 localization으로 관리합니다.

### UI 스케일링

스케일링 전략은 이제 `EditorInterface.get_editor_scale()`만을 유일한 기준으로 사용합니다. 스케일이 영향을 주는 항목은 다음과 같습니다.

- Dock root minimum size
- 탭 padding
- `HBoxContainer`, `VBoxContainer`, `GridContainer`의 spacing
- `SpinBox`, `OptionButton`, `Button`의 최소 높이
- Config content area의 read-only text panel 높이
- 동적으로 생성되는 tool-tree note의 font size

이유는 다음과 같습니다.

- 원래 상수는 high DPI이거나 editor scale이 `1.0`보다 높을 때 너무 빽빽해 보입니다.
- 스케일 logic은 이미 controller로 내려갔고 더 이상 단일 entry script에서 유지되지 않습니다.

### Server와 Config 탭에 추가 layout rule이 필요한 이유

이 두 탭에는 다음이 들어 있습니다.

- `GridContainer`
- 긴 text를 가진 `Label`
- read-only `TextEdit`
- 가로로 늘어나야 하는 `OptionButton` control

`size_flags_horizontal = SIZE_EXPAND_FILL`과 스케일 조정 최소 높이를 명시하지 않으면 다음과 같은 결과가 나올 수 있습니다.

- text area가 너무 좁아짐
- button 높이가 editor의 visual scale보다 작아 보임
- checkbox label이 가장자리에 붙거나 아예 없는 것처럼 보임

## 문제 해결 팁

- server tab은 상태가 맞는데 control이 눈에 띄게 너무 작다면 `editor_scale`이 model에 들어갔는지 확인합니다.
- checkbox에 box만 보이고 label이 보이지 않으면 `server_tab.gd`가 `AutoStartCheck`에 localized text를 넣었는지 확인합니다.
- config page의 text box가 width에 맞춰 늘어나지 않으면 `config_panel.tscn`의 `Content`, 각 section, `TextEdit`에 모두 가로 확장 제약이 있는지 확인합니다.
- one-click write가 실패하면 먼저 대상 path가 쓰기 가능한지, 기존 JSON을 파싱할 수 있는지 확인합니다.
- main-project runtime debug 정보가 필요하면 `debug.runtime_bridge`를 우선 사용합니다. 이것은 native Output 또는 Debugger panel을 그대로 복제하는 대신 runtime-bridge event와 editor debugger session state를 돌려줍니다.
- `MCPRuntimeBridge`는 플러그인이 활성화되면 project Autoload로 자동 등록되므로 main project에서 수동 연결이 필요하지 않습니다. 다른 script가 같은 Autoload 이름을 이미 소유하고 있으면 runtime bridge는 연결되지 않았다고 보고합니다.
