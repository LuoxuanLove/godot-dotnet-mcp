# 설치와 배포

이 문서는 Godot .NET MCP 플러그인의 설치 방법, 활성화 단계, 배포 전 점검 항목을 설명합니다.

플러그인은 자체 포함형입니다. Roslyn 구문 분석은 Godot .NET 런타임 내부에서 실행되며, 외부 호스트 프로세스가 필요하지 않습니다.

---

## 설치 방법

### 방법 1: Godot 플러그인 저장소

Godot에서 대상 프로젝트를 열고 `AssetLib` 탭으로 들어가 `Godot .NET MCP`를 검색한 뒤 `Install`을 클릭합니다. 또는 Godot 플러그인 저장소 페이지를 직접 열 수 있습니다.

```text
https://godotengine.org/asset-library/asset/4923
```

설치가 끝나면 디렉터리 구조를 그대로 유지합니다.

```text
addons/godot_dotnet_mcp
```

그 다음:

1. Godot에서 대상 프로젝트를 엽니다.
2. `Project Settings > Plugins`로 들어갑니다.
3. `Godot .NET MCP`를 활성화합니다.
4. `MCPDock`를 엽니다.
5. `Home` 탭에서 서비스를 시작합니다.

### 방법 2: 소스 파일 직접 복사

저장소 개발과 디버깅, 또는 로컬 프로젝트에서 현재 소스 트리를 바로 쓰려는 경우에 적합합니다.

1. 소스의 `addons/godot_dotnet_mcp/`를 대상 Godot 프로젝트로 복사합니다.
2. Godot로 프로젝트를 엽니다.
3. `Project Settings > Plugins`로 들어갑니다.
4. `Godot .NET MCP`를 활성화합니다.
5. `MCPDock > Home`에서 서비스를 시작합니다.

---

## 런타임 요구 사항

- Godot `4.6+`, .NET 지원이 포함된 Godot Mono/.NET build
- 프로젝트에서 .NET 스크립트 지원 활성화

### C# 분석 설명

- C# 구문 분석은 플러그인 내부 Roslyn이 처리합니다. syntax-first 방식으로 Godot .NET 런타임 내부에서 실행됩니다.
- SemanticModel은 사용하지 않으며, 구문 트리 정보만 추출하고 프로젝트 컴파일 로딩은 하지 않습니다.
- 별도의 Roslyn 설치나 설정은 필요하지 않습니다.

## 브랜치와 병합 흐름

- 장기 `develop`이나 `main` 브랜치는 운영하지 않습니다. `dev`가 유일한 장기 통합 브랜치이며, 항상 최신으로 검증 가능한 상태를 유지해야 합니다.
- 기능 개발은 `dev`에서 `feature/*` 단기 브랜치로, 결함 수정은 `dev`에서 `fix/*` 단기 브랜치로 시작하고, 검증 후 `dev`에 다시 병합합니다.
- PR, `dev` 푸시, 수동 실행은 플러그인 검증 workflow를 트리거합니다. 일반 단기 브랜치 PR은 `pull_request` 검증을 사용해 같은 커밋이 `push`와 PR 검증을 동시에 받지 않도록 합니다. PR은 반드시 `dev`를 대상으로 해야 하며, 병합 전에 검증을 통과하고, 필요한 README, CHANGELOG, docs, CI required subset도 함께 맞춰야 합니다. CHANGELOG는 사용자에게 보이는 기능과 수정만이 아니라 중요한 Documentation과 Internal 변화도 기록해야 합니다.
- 정식 배포 마무리는 `release/v1.0.1` 같은 단기 브랜치로 계속 처리합니다. 버전 번호, 변경 기록, 문서, 검증 결과를 확인한 뒤 `dev`로 다시 합칩니다.

## 배포 흐름 진입점

상세한 배포 절차는 `docs/zh-CN/流程/发布Runbook.md`를 참조하세요. 배포 흐름은 Godot Asset Library 설치와 `addons/godot_dotnet_mcp/` 소스 파일 직접 복사 두 가지 전달 경로만 남깁니다. zip 패키지, release 패키지, 로컬 패키징 산출물, 그 설치 절차는 만들지도 않고, 올리지도 않고, 기록하지도 않습니다. `dev`가 갱신되면 다음 버전 설명 초안으로 `next` draft release를 유지할 수 있습니다. 초안과 정식 배포는 모두 `docs/zh-CN/流程/release-notes/release-notes-v*.md`의 수기 요약, `docs/zh-CN/CHANGELOG.md`의 세부 내역, commit summary를 같은 구조로 렌더링합니다. 정식 `v*` 배포는 버전 일치와 release note 원본 preflight를 수행하며, 같은 버전, 같은 커밋의 성공한 dry-run 기록이 있으면 build와 harness 검사를 다시 하지 않고 건너뛸 수 있습니다.

Agent나 bot이 개발에 참여할 때는 `docs/zh-CN/流程/Agent与Bot流程.md`를 따릅니다. 단기 브랜치 커밋과 푸시는 자동으로 처리할 수 있고, 추가 계정 없이 진행하려면 `actions-bot-relay`를 사용해 `github-actions[bot]`이 patch에서 PR을 생성할 수 있습니다. 원격 `dev` 병합은 반드시 유지보수자가 GitHub PR 페이지에서 수동으로 확인해야 합니다.

## 소스 저장소 경계

### 유지

- `addons/godot_dotnet_mcp/dotnet_bridge/`, 플러그인 내부 독립 .NET 라이브러리, Roslyn façade의 공유 코드, 외부 실행 파일이 아님
- `tests/godot_plugin_harness/`, 플러그인 headless harness
- `tests/godot_plugin_harness_fixture/`, harness fixture와 contract test

## 검증 권장 사항

### 설치 루프

다음 순서로 검증하는 것을 권장합니다.

1. Godot에서 플러그인을 활성화할 수 있고 `MCPDock`를 열 수 있는지 확인합니다.
2. `MCPDock > Home`에서 서비스 상태가 올바르게 표시되는지 확인합니다.
3. `GET http://127.0.0.1:3000/health`가 정상 응답하는지 확인합니다.
4. `GET http://127.0.0.1:3000/api/tools`가 도구 목록을 반환하는지 확인합니다.
5. MCP 클라이언트가 `http://127.0.0.1:3000/mcp`에 연결되는지 확인합니다.
6. C# 스크립트 도구, 예를 들면 `script_inspect`, `script_exports`가 `engine=roslyn`, `mode=syntax`를 반환하는지 확인합니다.

### 배포 전 점검

적어도 다음은 확인하는 것이 좋습니다.

1. `plugin.cfg`, 프로토콜 사실, 변경 기록의 버전이 일치하는지 확인합니다.
2. README, CHANGELOG, `docs/zh-CN/流程/release-notes/release-notes-v*.md`, 관련 문서, 검증 결과가 모두 동기화되어 있는지 확인합니다. CHANGELOG에는 중요한 Documentation과 Internal 변화가 들어가야 하고, release notes는 사용자에게 보이는 배포 서사만 유지해야 합니다.
3. 소스 트리에 플러그인 외 코드나 로컬 빌드 산출물이 섞이지 않았는지 확인합니다.
4. `.github/workflows/**` 변경이 workflow lint를 통과했는지 확인합니다.
5. PR 대상 브랜치가 `dev`인지, 정식 `v*` tag, `plugin.cfg`, 영문 changelog, 간체 중국어 changelog, release note 원본의 버전이 같은지 확인합니다.
6. release note가 플러그인 자체의 요약, 호환성 안내, 검증 정보, commit summary만 담고 있는지 확인합니다.
