# 아키텍처 개요

## 규범 진입점

- 강한 제약의 인코딩 및 아키텍처 규칙은 먼저 [아키텍처/코딩 및 아키텍처 규범.md](编码与架构规范.md)를 읽으세요.

## 목표 위치

`godot_dotnet_mcp`의 목표는 에디터 내부에서 동작하는 MCP 서비스 계층으로서, 안정적이고 조합 가능하며 검증 가능한 Godot 4 프로젝트 자동화 진입점을 제공하는 것입니다.

현재 설계는 다음을 중시합니다.

- 오프라인 스크립트 생성이 아니라 에디터 내부 도구 호출 중심
- 플러그인 내부 Roslyn은 Godot .NET 런타임 내부에서 syntax-first로 동작
- Godot .NET 에디터는 필수(4.6+ Mono/.NET build)
- 외부 host 없음, child process 없음
- 동의어 entry를 계속 쌓기보다 분류 안정성 우선
- Godot.NET 프로젝트의 정적 분석과 binding 검사를 핵심 능력으로 유지
- 필요한 GDScript 지원은 유지하되, 인터페이스 중심은 더 이상 GDScript가 아님

## 계층 구조

```text
EditorPlugin
  ├─ plugin.gd
  ├─ Dock Scene 조립
  ├─ 플러그인 상태 및 설정 조립
  ├─ 서비스 시작/정지 조정
  └─ UI 컨트롤러와의 명시적 signal 연결

MCPServer
  ├─ plugin/runtime/mcp_http_server.gd
  ├─ tools/core/tool_loader.gd
  ├─ HTTP/TCP listening
  ├─ JSON-RPC / MCP 요청 분배
  ├─ tools/list
  └─ tools/call

Tool Executors
  ├─ tools/<category>/executor.gd
  ├─ tools/*.gd (호환 구현층)
  ├─ system (고수준 도구: project/scene/script/index, Atomic Bridge 포함)
  ├─ scene / node / script
  ├─ filesystem / resource / project
  ├─ animation / physics / navigation / audio / ui
  ├─ editor / debug / plugin 등 도메인 도구
  └─ custom_tools/*.gd (User 도구, system/executor.gd가 로드)

Plugin 내부 Roslyn
  ├─ addons/godot_dotnet_mcp/dotnet_bridge/ (플러그인 내 Roslyn syntax library)
  ├─ plugin/runtime/roslyn/ (플러그인 내 Roslyn façade)
  └─ syntax-first 분석, SemanticModel 없음

Shared Helpers
  ├─ base_tools.gd
  ├─ plugin/config/config_paths.gd
  └─ tools/core/*
```

## 런타임 객체 관계

현재 플러그인 진입점은 단일 거대 스크립트에서 얇은 조립층으로 재구성되었으며, 런타임 객체 관계는 다음과 같습니다.

```text
plugin.gd
  ├─ PluginRuntimeState
  ├─ SettingsStore
  ├─ ServerRuntimeController
  ├─ ToolCatalogService
  ├─ ClientConfigService
  ├─ DockModelService
  ├─ DockPresenter
  ├─ PluginReloadCoordinator
  ├─ MCPRuntimeBridge (Autoload, main project runtime event channel 주입)
  ├─ MCPEditorDebuggerBridge (editor debug session events 수신)
  └─ ui/mcp_dock.tscn
       ├─ ui/server_panel.tscn
       ├─ ui/tools_tab.tscn
       └─ ui/config_panel.tscn
```

이 뜻은 다음과 같습니다.

- `plugin.gd`는 조립, 상태 동기화, signal bridge만 담당합니다.
- Dock model 집계와 표시 매핑은 각각 `dock_model_service.gd`, `dock_presenter.gd`에 위임합니다.
- Dock tab은 더 이상 서비스를 직접 생성하지 않으며 설정 파일도 직접 읽고 쓰지 않습니다.
- tool profile 계산, 설정 텍스트 생성, 설정 저장은 UI에서 분리됩니다.
- 플러그인 수준의 완전 재로드는 독립 coordinator 노드가 처리해, 현재 인스턴스가 사라져도 재활성화 동작을 잃지 않게 합니다.
- 앞으로 새 tab을 추가할 때는 진입 스크립트를 계속 키우지 말고 독립 scene과 controller를 추가하는 방식이 우선입니다.

## 핵심 책임

### `plugin.gd`

담당:

- 플러그인 생명주기 관리
- Dock scene과 controller 조립
- 상태, 서비스, tool catalog, config service 연결
- 최소 공개 API(`get_server` / `start_server` / `stop_server`) 노출
- `tool_loader`에 안정적인 `get_tool_access_provider()` bridge 제공
- `editor_scale`, 현재 언어, 서비스 참조를 Dock model 계층에 제공
- 완전 재로드 전후 Dock tab / focus snapshot 저장과 복원

비담당:

- 구체적 Dock 노드 트리 빌드
- tool tree profile matching과 count 계산
- 설정 파일 읽기/쓰기 세부
- protocol 수준 요청 분배
- 버튼 클릭 후 개별 UI 업데이트

### `plugin/runtime/mcp_http_server.gd`

담당:

- 요청 수신
- protocol 해석
- tool list 구성
- tool 호출을 `MCPToolLoader`로 전달
- 반환 구조 통일
- 연결 수, 요청 수, 최근 요청 method와 시각 관리

### `tools/core/tool_loader.gd`

담당:

- `category -> script path -> runtime instance` 로딩 관계 관리
- 내장 도구와 `custom_tools/*.gd` 스캔
- 활성화된 category만 pre-load하고 나머지는 definition cache로 유지
- 단일 domain / 전체 hot reload 진입점 제공
- load state, reload status, performance summary 집계

### `tools/*.gd`

담당:

- 특정 능력 도메인의 권위 있는 진입점 제공
- 도메인 내부에서 `action`으로 하위 행동 분기
- 입력/출력/오류 구조 일관성 유지
- `base_tools.gd`의 path parsing, node serialization, JSON/Variant 정규화 helper 재사용

### `ui/*.tscn` + `ui/*.gd`

담당:

- Dock root와 각 tab의 노드 구조 보유
- 사용자 동작을 명시적 signal로 `plugin.gd`에 보고
- 표시와 상호작용만 처리하고 서비스 생명주기는 직접 관리하지 않음
- `editor_scale`에 따라 간격, 최소 크기, 텍스트 영역 높이 조정
- 플러그인 내부 문구의 자동 번역은 끄고 로컬라이제이션 서비스가 표시 언어를 제어하게 함

### `plugin_*` 서비스 객체

담당:

- `plugin/runtime/plugin_runtime_state.gd`: 런타임 필드와 current settings / custom profile 상태
- `plugin/runtime/tool_profile_catalog.gd`: builtin profile directory와 profile storage directory
- `tools/tool_registry.gd`: builtin executor 등록의 사실 원본
- `tools/tool_manifest.gd`: tool domain/category metadata의 안정 진입점
- `plugin/runtime/plugin_runtime_state.gd`: settings path, default settings, collapsed default input, runtime state
- `plugin/config/settings_store.gd`: settings와 custom profile 지속화
- `plugin/runtime/server_runtime_controller.gd`: `MCPHttpServer` 생명주기와 상태 프록시
- `plugin/runtime/tool_catalog_service.gd`: domain/category/profile 계산
- `plugin/config/client_config_service.gd`: Config 페이지 config service façade, 실제 로직은 serializer / inspection / transaction / launcher adapter 협력자에 위임

### `plugin/runtime/roslyn/*`

담당:

- `plugin_roslyn_service.gd`: 플러그인 내부 Roslyn façade, C# syntax analysis 요청 처리
- `PluginRoslynRuntimeFacade.cs`: Roslyn syntax tree를 DTO로 변환하는 C# 측 façade
- `PluginRoslynSyntaxCore.cs`: 공유 Roslyn syntax core

## 시작 흐름

1. `plugin.gd._enter_tree()`가 `_load_state()`를 호출해 `user://godot_dotnet_mcp/settings.json`과 `user://godot_dotnet_mcp/profiles`를 읽습니다.
2. 플러그인이 언어를 설정하고 `ServerRuntimeController`를 조립합니다.
3. `MCPRuntimeBridge` Autoload를 현재 Godot 프로젝트에 설치합니다.
4. `MCPEditorDebuggerBridge`를 `EditorDebuggerPlugin`에 등록해 main project debug session 이벤트를 받습니다.
5. 진입점이 `ui/mcp_dock.tscn`을 인스턴스화하고 모든 명시적 signal을 연결합니다.
6. 최초 설정 로드라면 내장 profile 기준으로 `disabled_tools`를 계산합니다.
7. `auto_start`에 따라 서비스 자동 시작 여부를 결정합니다.
8. 이전 완전 재로드에서 남은 Dock focus snapshot이 있으면 첫 갱신 뒤 Dock tab과 원래 focus를 복원합니다.
9. `_process()`가 0.5초마다 Dock model을 갱신해 서비스 상태와 통계를 동기화합니다.

## UI 데이터 흐름

현재 Dock은 단방향 데이터 흐름을 사용합니다.

1. `_dock_model_service.build_model()`가 상태, 통계, tool, config text, `editor_scale`을 `dock_model_service.gd`에 위임해 집계합니다.
2. `dock_model_service.gd`가 context를 `dock_presenter.gd`에 넘겨 최종 model을 생성합니다.
3. `mcp_dock.gd.apply_model()`이 model을 세 tab에 분배합니다.
4. tab controller는 사용자 동작을 `start_requested`, `tool_toggled`, `config_write_requested` 같은 signal로 올립니다.
5. `plugin.gd`가 signal에 반응해 상태를 갱신하고, service 객체를 호출한 뒤 다시 `_refresh_dock()`를 수행합니다.

직접적인 이점은 다음과 같습니다.

- UI script 안에 서비스 참조를 보관할 필요가 없습니다.
- 언어 전환과 스케일 갱신을 한 번에 다시 그릴 수 있습니다.
- 어떤 tab이든 model 재생으로 보여줄 수 있어, 이후 테스트 보강이나 분리 작업이 쉽습니다.

## 현재 아키텍처 제약

- tool 이름은 분류 안정성을 우선하며, 중복 prefix를 쉽게 늘리지 않습니다.
- 반환값은 MCP 클라이언트가 직접 소비할 수 있어야 합니다.
- 쓰기 작업은 가능한 한 “쓰기 후 읽기 검증”을 지원해야 합니다.
- scene, script, resource 도구는 에디터 내부 워크플로를 우선 지원합니다.
- category의 외부 명칭은 안정적으로 유지하고, 내부 디렉터리 구조는 계속 진화할 수 있습니다.
- 플러그인 UI는 scene 기반으로 조직하고, 진입 스크립트는 얇은 조립층으로 유지합니다.
- tab script는 표시와 상호작용만 담당하고 `plugin/runtime/mcp_http_server.gd`를 직접 건드리지 않습니다.
- UI 스케일은 `EditorInterface.get_editor_scale()`를 유일한 배율 원천으로 사용합니다.
