## 🧩 Godot .NET MCP v1.2.1: Verified Editor UI Automation

이 version line은 editor UI automation을 개선해 client가 다음 workflow로 넘어가기 전에 Godot editor의 visible state를 기다릴 수 있게 합니다. Agent는 기존 editor control로 동작을 수행한 뒤 기대한 UI condition이 실제로 나타났는지 검증할 수 있습니다.

### ✨ 실제 UI 상태 대기

`system_editor_control`에 `wait_for_ui`를 추가했습니다. control 존재, 표시 상태, text matching, enabled / disabled state를 제한 시간 안에서 폴링할 수 있습니다. 성공하면 일치한 control summary와 timing detail을 반환하고, timeout이면 마지막 observed payload를 반환해 client가 locator나 다음 action을 조정할 수 있습니다.

### 🔧 더 안전한 automation loop

새 wait action은 menu, popup, click, hover, text entry control과 함께 동작하며 OS mouse automation이 필요하지 않습니다. editor dialog 열기, setting filter, transient panel 확인 같은 workflow를 Godot 내부에서 더 쉽게 검증할 수 있습니다.

Editor UI guidance는 이제 automation order를 명확히 합니다. semantic workflow와 navigation을 먼저 사용하고, control-level focus, text, value, popup action을 다음으로 사용하며, control-local mouse / pointer event는 fallback으로만 사용합니다. Agent는 좌표로 내려가기 전에 더 높은 수준의 경로를 선택할 수 있습니다.

Resource / prompt diagnostics는 resource output을 보고하기 전에 mixed-case URL credential, bearer / API-key variant, nested metadata secret을 redact합니다. troubleshooting evidence는 automation loop에 계속 유용하면서도 summary에 credential이 노출될 가능성을 낮춥니다.

### 🔍 Activity Diagnostics

Tool activity query는 이제 running / recent call을 state 또는 tool로 filter하고 slow call이나 failed call을 표시할 수 있습니다. client는 더 많은 작업을 시작하기 전에 멈춰 있을 수 있는 automation을 빠르게 발견할 수 있습니다.

### 🪟 Floating Window Evidence

`system_editor_control`은 이제 `get_popup`과 `capture_popup`으로 표시 중인 floating popup / window surface를 읽고 잘라낸 evidence를 가져올 수 있습니다. client는 button, menu item, text field, close action을 선택하기 전에 modal editor window와 PopupMenu 상태를 직접 확인할 수 있습니다.

`system_settings_dialog`는 settings surface를 capture할 때 이 evidence path를 자동으로 사용합니다. 현재 Project Settings / Editor Settings workflow가 해당 popup이나 editor window를 관측할 수 있으면 capture result는 선택된 backend와 target path를 표시하고, 더 좁은 surface를 사용할 수 없을 때만 broader editor screenshot으로 fallback합니다.

`system_editor_evidence`는 editor, control, popup, active-dialog, auto surface를 위한 evidence-aware capture entry를 제공합니다. 결과는 requested surface, actual backend, target path, visible popups, fallback reasons, degraded state를 표시하므로 Agent가 screenshot이 현재 task surface를 증명하는지, 아니면 더 넓은 fallback view만 제공하는지 판단할 수 있습니다.

### 🧭 Configuration Navigation and Evidence

`system_settings_dialog`는 Project Settings와 Editor Settings를 위한 high-level workflow를 추가합니다. client는 editor menu로 settings surface를 열고, dialog 표시를 기다리고, 후보 setting row를 검색하고, 반환된 result에 focus하고, evidence를 capture한 뒤 setting value를 직접 쓰지 않고 surface를 닫을 수 있습니다.

이 workflow는 이제 `list_rows`로 read-only row model도 반환해, 표시된 settings-like control을 보수적인 confidence와 evidence 필드로 요약한 뒤 필요한 value read, write, assertion을 선택할 수 있습니다.

`list_tabs`와 `activate_tab`으로 settings tab을 list / activate할 수 있고 `open(tab=...)`도 지원하므로, 좌표 클릭 없이 Project Settings 또는 Editor Settings tab 사이를 이동할 수 있습니다.

이 settings workflow는 visible category tree item을 list하고 row inspection 전에 고유 category에 focus할 수 있어 Project Settings와 Editor Settings navigation이 raw control enumeration에 덜 의존하게 합니다.

또한 `read_value`로 고유하게 일치한 visible row의 현재 값을 읽어 row와 value-control evidence와 함께 text, bool, number, enum typed payload를 반환할 수 있으며 setting value는 계속 직접 쓰지 않습니다.

Project configuration evidence는 이제 input map도 포함합니다. Agent는 `system_project_configure`에서 개별 project input action을 읽고 deadzone과 구체적인 keyboard, mouse, controller binding을 확인할 수 있습니다. 이를 통해 gameplay나 editor shortcut을 바꾸기 전에 실제 project configuration에 근거해 input map을 검토할 수 있습니다.

Project configuration은 이제 `system_project_configure(action="list_export_presets")`로 export preset도 나열할 수 있습니다. response는 preset name, platform, runnable state, filter, script export mode, export path shape를 요약하고 sensitive option key와 local absolute export path는 redact합니다.

Settings update source와 branch selector는 이제 긴 option list를 제한된 popup 안에 유지합니다. Agent는 menu가 editor workspace를 덮지 않은 상태로 사용 가능한 ref를 모두 확인할 수 있습니다.

client는 이제 `resolve_row`로 값을 읽거나 후속 UI action을 선택하기 전에 표시된 설정 행을 고유하게 확인할 수 있습니다. response에는 row path, confidence, selector evidence, ambiguity diagnostics가 포함되며 read-only 상태를 유지합니다.

Agent가 일치한 value editor로 keyboard focus만 이동해야 할 때는 `focus_value`가 value control을 focus하고 설정을 변경하지 않은 채 focus evidence를 반환합니다.

지원되는 고유 visible row는 이제 `set_value`로 text, number, bool control을 편집할 수 있습니다. 이 workflow는 editor UI control을 통해 값을 쓰고, 동작 후 row를 다시 관측하므로 client가 click이나 text edit 성공을 가정하지 않고 변경된 값을 확인할 수 있습니다.

`run_task`는 이제 이 settings chain을 하나의 trusted operation으로 감쌉니다. settings surface를 열고 좁히며, 고유 row를 확인하고, 변경 전 값을 읽고, 지원되는 값을 선택적으로 쓰고, 기대 결과를 검증하며, capture evidence를 붙일 수 있습니다. selector가 ambiguous하거나, hidden control write를 요청하거나, confidence가 너무 낮거나, 값이 바뀌기 전에 required capture evidence를 만들 수 없으면 write는 interaction 전에 거부됩니다.

Agent는 읽기 전용 `verify_value` check도 사용해 expected text, bool, number, enum 값을 고유하게 일치한 visible row와 비교할 수 있습니다. settings workflow에 UI action 전후로 setting value를 바꾸지 않는 assertion step을 추가할 수 있습니다.

Inspector automation은 이제 `system_inspector`를 통해 전용 high-level workflow를 제공합니다. client는 visible Inspector property model을 나열하고, 고유 property를 확인하고, 현재 typed value를 읽고, value editor에 focus하고, 지원되는 text / number / bool editor를 검증과 함께 쓰고, property evidence를 capture하거나, 현재 edited object 또는 준비된 node / resource target에 대해 locate / read / set / verify / capture task를 한 번에 실행할 수 있습니다.

Inspector workflow는 hidden-control write, ambiguous selector, disabled value editor, 지원하지 않는 complex editor를 추측하지 않고 거부합니다. 그래서 Agent는 raw editor control enumeration이나 coordinate-based input으로 내려가기 전에 property-level의 신뢰 가능한 경로를 사용할 수 있습니다.

### 🔎 검색 가능한 도구 발견

`system_tool_catalog`은 현재 tool catalog를 read-only로 검색하는 입구입니다. client는 query, category, domain으로 검색하고, 각 tool이 왜 match되었는지, 어떤 action과 parameter를 공개하는지, visible state와 enabled state가 무엇인지 확인할 수 있습니다.

이를 통해 profile, plugin domain tool, user tool state가 바뀐 뒤에도 configuration / editor workflow에 다시 들어가기 쉬워집니다. Agent는 오래된 tool name 기억에 의존하지 않고 다음 verified action 전에 적절한 system, project, editor, runtime, script, user-facing tool을 다시 찾을 수 있습니다.

Native MCP discovery도 이제 resource와 resource template metadata를 지역화합니다. client가 `resources/list` 또는 `resources/templates/list`를 호출하면 resource name과 description은 현재 plugin language를 따르고, URI와 template은 안정적으로 유지됩니다.

### 🧰 더 명확한 User Tool 이름

User tool listing과 compatibility report는 이제 script-declared name, 정규화된 internal name, 공개 MCP tool name을 함께 보여줍니다. scaffold preview도 공개 이름을 먼저 보여주며, 기존 `user_` prefix declaration에는 review warning을 반환해 client가 tool 표시 방식을 추측하지 않아도 됩니다.

새 scaffold는 base tool type을 global script-class registration에 의존하지 않아 headless catalog scan에서도 더 안정적으로 로드됩니다.

### 🧪 Read-Only Scene Inspection

`system_scene_inspect`는 scene check를 위한 read-only entry를 하나 제공합니다. `validate`는 loadability와 reference issue를 빠르게 확인하고, `analyze`는 node, binding, script 세부 정보를 더 깊게 확인하며, `full`은 두 payload를 분리한 채 한 response로 받고 싶은 workflow에 사용할 수 있습니다.

### 🛠 Plugin Maintenance Workflow

`system_plugin_maintenance`는 plugin status 확인, lifecycle reload 예약, update progress 확인, update source 선택, plugin update flow 시작을 하나로 묶은 maintenance entry를 제공합니다. 이 tool은 추가 high-level wrapper이며, 기존 client는 lower-level reload / update tool을 직접 조합하는 방식도 계속 사용할 수 있습니다.

### 🧭 Project Runtime Lifecycle

Project runtime control은 이제 `system_project_lifecycle(action=start|stop)`을 canonical high-level entry로 사용합니다. start, marker validation, auto-stop, explicit stop, foreground-window fallback guidance, runtime capability context가 별도의 run / stop tool 이름이 아니라 하나의 lifecycle surface 아래로 모입니다.

이전 project run / stop tool 이름을 호출하던 client는 `system_project_lifecycle(action=start)`와 `system_project_lifecycle(action=stop)`으로 이동해야 합니다. lifecycle이라는 이름은 editor automation flow를 일회성 launch command가 아니라 제어 가능한 runtime session으로 다루기 쉽게 만듭니다.

### ✅ Compatibility and Upgrade Notes

Project runtime control surface는 이제 `system_project_lifecycle(action=start|stop)`을 사용합니다. 이전 project run / stop tool 이름을 사용하던 client는 lifecycle entry로 이동해야 합니다. 기존 editor, settings, project configuration workflow는 계속 사용할 수 있습니다.

기존 scene validation / analysis tool은 계속 사용할 수 있습니다. `system_scene_inspect`는 하나의 high-level scene inspection surface가 필요한 client를 위한 추가 combined route입니다.

`system_plugin_maintenance`는 추가 high-level wrapper입니다. 기존 `system_plugin_reload`와 `system_plugin_update` 호출은 계속 지원됩니다.
