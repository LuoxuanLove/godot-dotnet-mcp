## 🧩 Godot .NET MCP v1.2.1: Verified Editor UI Automation

이 version line은 editor UI automation을 개선해 client가 다음 workflow로 넘어가기 전에 Godot editor의 visible state를 기다릴 수 있게 합니다. Agent는 기존 editor control로 동작을 수행한 뒤 기대한 UI condition이 실제로 나타났는지 검증할 수 있습니다.

### ✨ 실제 UI 상태 대기

`system_editor_control`에 `wait_for_ui`를 추가했습니다. control 존재, 표시 상태, text matching, enabled / disabled state를 제한 시간 안에서 폴링할 수 있습니다. 성공하면 일치한 control summary와 timing detail을 반환하고, timeout이면 마지막 observed payload를 반환해 client가 locator나 다음 action을 조정할 수 있습니다.

### 🔧 더 안전한 automation loop

새 wait action은 menu, popup, click, hover, text entry control과 함께 동작하며 OS mouse automation이 필요하지 않습니다. editor dialog 열기, setting filter, transient panel 확인 같은 workflow를 Godot 내부에서 더 쉽게 검증할 수 있습니다.

Resource / prompt diagnostics는 resource output을 보고하기 전에 mixed-case URL credential, bearer / API-key variant, nested metadata secret을 redact합니다. troubleshooting evidence는 automation loop에 계속 유용하면서도 summary에 credential이 노출될 가능성을 낮춥니다.

### 🪟 Floating Window Evidence

`system_editor_control`은 이제 `get_popup`과 `capture_popup`으로 표시 중인 floating popup / window surface를 읽고 잘라낸 evidence를 가져올 수 있습니다. client는 button, menu item, text field, close action을 선택하기 전에 modal editor window와 PopupMenu 상태를 직접 확인할 수 있습니다.

### 🧭 Configuration Navigation and Evidence

`system_settings_dialog`는 Project Settings와 Editor Settings를 위한 high-level workflow를 추가합니다. client는 editor menu로 settings surface를 열고, dialog 표시를 기다리고, 후보 setting row를 검색하고, 반환된 result에 focus하고, evidence를 capture한 뒤 setting value를 직접 쓰지 않고 surface를 닫을 수 있습니다.

이 workflow는 이제 `list_rows`로 read-only row model도 반환해, 표시된 settings-like control을 보수적인 confidence와 evidence 필드로 요약한 뒤 필요한 value read, write, assertion을 선택할 수 있습니다.

`list_tabs`와 `activate_tab`으로 settings tab을 list / activate할 수 있고 `open(tab=...)`도 지원하므로, 좌표 클릭 없이 Project Settings 또는 Editor Settings tab 사이를 이동할 수 있습니다.

이 settings workflow는 visible category tree item을 list하고 row inspection 전에 고유 category에 focus할 수 있어 Project Settings와 Editor Settings navigation이 raw control enumeration에 덜 의존하게 합니다.

또한 `read_value`로 고유하게 일치한 visible row의 현재 값을 읽어 row와 value-control evidence와 함께 text, bool, number, enum typed payload를 반환할 수 있으며 setting value는 계속 직접 쓰지 않습니다.

Project configuration evidence는 이제 input map도 포함합니다. Agent는 `system_project_configure`에서 개별 project input action을 읽고 deadzone과 구체적인 keyboard, mouse, controller binding을 확인할 수 있습니다. 이를 통해 gameplay나 editor shortcut을 바꾸기 전에 실제 project configuration에 근거해 input map을 검토할 수 있습니다.

Project configuration은 이제 `system_project_configure(action="list_export_presets")`로 export preset도 나열할 수 있습니다. response는 preset name, platform, runnable state, filter, script export mode, export path shape를 요약하고 sensitive option key와 local absolute export path는 redact합니다.

client는 이제 `resolve_row`로 값을 읽거나 후속 UI action을 선택하기 전에 표시된 설정 행을 고유하게 확인할 수 있습니다. response에는 row path, confidence, selector evidence, ambiguity diagnostics가 포함되며 read-only 상태를 유지합니다.

Agent가 일치한 value editor로 keyboard focus만 이동해야 할 때는 `focus_value`가 value control을 focus하고 설정을 변경하지 않은 채 focus evidence를 반환합니다.

지원되는 고유 visible row는 이제 `set_value`로 text, number, bool control을 편집할 수 있습니다. 이 workflow는 editor UI control을 통해 값을 쓰고, 동작 후 row를 다시 관측하므로 client가 click이나 text edit 성공을 가정하지 않고 변경된 값을 확인할 수 있습니다.

Agent는 읽기 전용 `verify_value` check도 사용해 expected text, bool, number, enum 값을 고유하게 일치한 visible row와 비교할 수 있습니다. settings workflow에 UI action 전후로 setting value를 바꾸지 않는 assertion step을 추가할 수 있습니다.

### 🔎 검색 가능한 도구 발견

`system_tool_catalog`은 현재 tool catalog를 read-only로 검색하는 입구입니다. client는 query, category, domain으로 검색하고, 각 tool이 왜 match되었는지, 어떤 action과 parameter를 공개하는지, visible state와 enabled state가 무엇인지 확인할 수 있습니다.

이를 통해 profile, plugin domain tool, user tool state가 바뀐 뒤에도 configuration / editor workflow에 다시 들어가기 쉬워집니다. Agent는 오래된 tool name 기억에 의존하지 않고 다음 verified action 전에 적절한 system, project, editor, runtime, script, user-facing tool을 다시 찾을 수 있습니다.

### ✅ Compatibility and Upgrade Notes

이 변경들은 public tool schema만 확장합니다. 기존 `system_editor_control`, `system_settings_dialog`, `system_project_configure` action은 계속 사용할 수 있으며, 새 action을 호출하지 않는 client는 request를 바꿀 필요가 없습니다.
