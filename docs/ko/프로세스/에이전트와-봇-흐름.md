# Agent 및 Bot 흐름

이 문서는 Agent 또는 bot이 Godot .NET MCP 개발에 참여할 때의 GitHub 작업 방식을 규정합니다.

---

## 1. 신원 원칙

- Agent 푸시와 PR 생성은 독립 machine user 또는 GitHub App을 쓰는 것이 권장됩니다.
- 별도 계정을 쓰지 않는다면 `actions-bot-relay`를 통해 `github-actions[bot]`가 유지관리자가 제공한 patch로 short branch와 PR을 만들 수 있습니다.
- git commit author만 바꿔서는 GitHub의 PR author나 latest push actor를 바꿀 수 없습니다.
- Bot 권한은 최소화해야 하며, 보통 branch push, PR 생성/갱신, 저장소 읽기만 있으면 충분합니다.

---

## 2. Branch와 PR

- Agent는 최신 `origin/dev`에서 의미가 분명한 short branch를 만듭니다: `feature/*`, `fix/*`, `docs/*`, `chore/*`, `hotfix/*`, `release/*`.
- 검증이 끝나면 current short branch를 커밋하고 푸시할 수 있습니다.
- 각 short branch와 PR에는 해당 범위의 수정만 들어가야 합니다.
- 다른 작업, 다른 수정, 이전에 합쳐지지 않은 커밋이 섞이면 독립 PR로 나누거나 최신 `origin/dev`에서 깨끗한 branch를 다시 만듭니다.
- 일반 integration PR은 `dev`를 향해야 합니다. 명시적 v2 predevelopment PR은 `v2.0`, `release/v2.0.0-baseline`, 또는 anchored `feature/v2-*`, `docs/v2-*`, `ci/v2-*` stacked base branch를 대상으로 삼을 수 있습니다. 그 밖의 target branch는 `pr-policy`가 실패로 처리합니다.
- `actions-bot-relay`가 만든 short branch는 반드시 `actions-bot/*` prefix를 써야 합니다.

---

## 3. PR 본문 요구사항

PR 본문은 간단한 템플릿을 써서, 유지관리자가 빠르게 읽을 수 있는 공개 정보만 남깁니다.

- `Summary`: 결과와 목적을 1~3개 항목으로 설명
- `Changes`: 실제 변경 사항 목록
- `Screenshots`: UI 또는 시각 변화가 있을 때만 유지
- `Testing`: 실제로 실행한 로컬 명령, CI check, editor / plugin 검증
- `Related Issues`: 연결된 issue, 없으면 비워도 됨

더 엄격한 branch, changelog, review, Cubic, merge 요구는 이 흐름 문서와 CI gate가 담당하며 PR 템플릿 본문에는 넣지 않습니다. PR 제목은 Conventional Commits 형식을 사용합니다. 예: `fix(scope): 짧은 설명`.

---

## 4. 완료 정의와 재수정 폐루프

공개 tool 동작, UI 구조, 생명주기 의미, CI/workflow 동작, 릴리스 내용이 바뀌면 완료 정의는 구현, contract test, 문서, 변경 기록을 모두 포함해야 합니다. 코드가 빌드된다고 끝난 것이 아닙니다. 관련 test나 문서가 여전히 옛 경로, 옛 field, 옛 의미를 설명하면 그 PR은 아직 재수정 상태입니다.

Agent는 PR을 제출하거나 갱신하기 전에 다음을 확인해야 합니다.

- 영향을 받은 contract test가 현재 실제 계약을 반영하는지 확인합니다. 오래된 test가 여전히 옛 경로나 옛 의미를 설명해서 실패한다면, 최종 보고에서 무관한 실패라고 부르지 말고 test contract를 먼저 고칩니다.
- 이번 PR의 공개 동작과 관련된 `docs/`, `README*`, tool 설명, protocol facts, `CHANGELOG*`가 서로 맞는지 확인합니다. `CHANGELOG*`에는 release note 원본 파일, docs / i18n 업데이트, runbook 변경, CI / harness 동작, policy check, protocol facts, 검증 범위 변경처럼 중요한 `Documentation`과 `Internal` 변화도 들어가야 합니다. 순수 version metadata bump는 별도 항목이 아닙니다.
- Review, Cubic, Codex, human 검토에서 test나 문서 gap을 찾으면 같은 PR 안에서 처리하고 resolved, outdated 또는 maintainer가 명시적으로 결정한 상태로 표시해야 합니다.
- 검증 기록에는 실제 실행한 test, build, harness case가 들어 있어야 합니다. 읽기 전용 확인은 영향을 받은 contract test를 대신하지 않습니다.

---

## 5. PR 완료 게이트

PR은 아래 조건을 모두 만족해야 유지관리자에게 merge 가능하다고 보고할 수 있습니다.

1. PR이 허용된 integration branch 또는 명시적 v2 stacked base를 향하고, 현재 검증 가능한 target base를 기준으로 다시 확인되었음
2. 일반 PR은 `pr-policy`가 통과했고 제목과 본문 객관 필드가 완전함. `actions-bot-relay` PR처럼 이 check가 자연스럽게 트리거되지 않는 경우에는 relay metadata, 명시적으로 트리거한 validation workflow, maintainer review가 이 확인을 대신 덮어야 함
3. `dotnet-build`가 통과함
4. `validate-plugin-harness`가 통과함
5. `.github/workflows/**`를 바꾸면 `lint-workflows`가 통과함
6. human, Cubic, Codex, 기타 review conversation이 모두 reply되고 resolved 됨
7. Cubic이 최신 head commit을 덮고 있으며, 최신 결과에 blocker가 없음
8. `CHANGELOG*`, 공개 문서, 검증 기록, 실제 변경 범위가 일치하고, 중요한 Documentation / Internal 변화가 changelog에 들어 있음. 어떤 문서를 업데이트할 필요가 없었다면 PR 본문에서 플러그인 관점의 이유를 설명해야 함

어느 하나라도 충족하지 못하면 PR은 완료가 아니라 재수정 또는 재검증 대기 상태입니다.

---

## 6. 재수정 반복 규율

각 PR 재수정은 실패한 gate나 reviewer가 지적한 구체 문제만 고쳐야 하며, 검증 순환에 새 범위를 끼워 넣으면 안 됩니다.

권장 순서:

1. 실패한 check, review thread, Cubic 최신 결과 읽기
2. 문제의 유효성 판단, 유효하면 국소 수정, 무효면 이유 답변
3. 직접 관련된 test, 문서, changelog 업데이트
4. short branch 커밋과 푸시
5. 최신 head를 기준으로 CI와 review gate를 다시 확인

예전 CI, 예전 review, 예전 Cubic 결과는 코드가 바뀐 뒤 완료 근거가 될 수 없습니다.

---

## 7. Merge 경계

- Agent는 `dev`에 직접 push하지 않습니다.
- Agent는 local merge 후 `dev`에 push하지 않습니다.
- Agent는 required checks를 우회하지 않습니다.
- Agent는 GitHub PR을 직접 merge하지 않습니다. 원격 `dev` merge는 유지관리자가 GitHub PR 페이지에서 직접 확인하고 실행해야 합니다.

---

## 8. GitHub Actions Bot Relay

`actions-bot-relay`는 별도 machine user를 두지 않을 때 쓰는 중계 방식입니다. 유지관리자나 Agent가 최신 `dev` 기반 unified patch를 만들고, workflow를 수동으로 실행하면 `github-actions[bot]`가 patch를 적용, 커밋, `actions-bot/*` branch push, `dev`를 향한 PR 생성/갱신을 합니다.

사용 전제: 저장소 Settings > Actions > General에서 GitHub Actions가 pull request를 만들고 승인할 수 있어야 합니다. 이 workflow는 기본 `GITHUB_TOKEN`만 쓰며 PAT가 필요 없습니다.

입력 요구사항:

- `patch_base64`: base64로 인코딩한 unified git patch
- `pr_title`: PR 제목
- `pr_body`: 간단한 템플릿을 사용하고 `pr-policy`가 요구하는 objective field를 만족하는 PR 본문
- `commit_message`: 커밋 메시지
- `branch_name`: 선택값, 비워 두거나 `actions-bot/*` prefix만 허용
- `base_branch`: 고정으로 `dev`

실행 경계:

- workflow는 patch만 받고 임의 사용자 스크립트를 실행하지 않습니다.
- workflow는 `dotnet-build.yml`, `validate-plugin.yml`, 신뢰된 `version-policy.yml`을 명시적으로 트리거합니다.
- `.github/workflows/**`를 바꾸면 `lint-workflows.yml`도 트리거합니다.
- 일반 short branch push는 PR 자동 검증 진입점이 아닙니다.
- `GITHUB_TOKEN`으로 만든 push/PR 이벤트는 일반 사용자 push처럼 모든 workflow를 자동으로 트리거하지 않으므로, relay는 검증 workflow를 명시적으로 실행해야 합니다.
- 유지관리자는 여전히 GitHub PR 페이지에서 검토, 승인, merge를 직접 해야 합니다.

---

## 9. 자동화 경계

- 자동 생성, 자동 갱신, 정기 유지보수형 변경은 반드시 short branch PR로만 반영하고, `dev`에 직접 쓰지 않습니다.
- 자동화 workflow는 `next` draft release를 생성하거나 갱신할 수 있지만, 정식 release 생성, zip / sha256 / 로컬 빌드 산출물 업로드, 유지관리자 판단 대체는 할 수 없습니다.
- 정식 tag, 원격 tag 삭제, release 본문 수정, 이미 존재하는 release 처리 여부는 유지관리자가 결정합니다.
- npm / Bun 배포, OIDC trusted publisher, CLA Assistant, 강제 push, PAT 기반 자동 merge는 사용하지 않습니다.

---

## 10. PR 보고 요구사항

Agent가 PR을 만들거나 갱신할 때는 다음을 설명해야 합니다.

- 수정 범위와 대상 branch
- changelog / 문서 업데이트 포함 여부
- 실행한 검증 명령과 결과
- 현재 CI, review conversation, Cubic 상태
- 남은 유지관리자 수동 작업
