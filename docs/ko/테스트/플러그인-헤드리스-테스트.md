# 플러그인 헤드리스 테스트

이 문서는 `Godot Headless Harness`의 현재 구조, 검증 범위, 알려진 경계를 설명합니다.

## 목표

플러그인 측 테스트 시스템의 목표는 다음과 같습니다.

- `gdUnit`이나 `GUT` 같은 외부 테스트 framework를 도입하지 않습니다.
- repository-owned fixture project에서 headless Godot을 직접 실행합니다.
- plugin runtime, tool loading, routing, system impl의 핵심 동작을 검증합니다.
- runtime refactor에 대한 빠른 회귀 표면을 제공합니다.

## 현재 파일 배치

```text
tests/godot_plugin_harness/
├─ GodotPluginHarness.csproj
└─ Program.cs

tests/godot_plugin_harness_fixture/
├─ project.godot
└─ tests/
   ├─ headless_suite_runner.gd
   ├─ runtime_bridge_contract_test.gd
   ├─ runtime_control_contract_test.gd
   ├─ user_tool_service_contract_test.gd
   ├─ script_tool_executor_contract_test.gd
   ├─ scene_tool_executor_contract_test.gd
   ├─ http_server_contract_test.gd
   ├─ json_rpc_router_contract_test.gd
   ├─ tool_loader_contract_test.gd
   ├─ tools_tab_rendering_contract_test.gd
   └─ plugin_entrypoint_contract_test.gd
```

주요 책임은 다음과 같습니다.

| 파일 | 목적 |
|---|---|
| `Program.cs` | fixture와 addon을 임시 stage root로 복사하고, Godot을 실행하고, stdout/stderr와 suite JSON을 수집합니다. |
| `project.godot` | 최소 테스트 프로젝트입니다. |
| `headless_suite_runner.gd` | suite entry point이며 case를 하나씩 실행하고 결과를 집계합니다. |
| `*_contract_test.gd` | 모듈별 단일 contract case입니다. |

## 현재 검증 범위

harness는 case를 자동 발견합니다. 대표 범위는 다음과 같습니다.

- runtime bridge fallback reply
- runtime control state와 parameter error model
- runtime reply normalization과 fallback 처리
- user tool scaffold, directory scan, compatibility report, deletion, restore, audit
- script, node, scene, debug, editor, filesystem, project, resource executor의 대표 경로
- HTTP server lifecycle, `tools/list`, `tools/call`
- JSON-RPC initialize, notification, method-not-found behavior
- editor lifecycle endpoint와 action service
- system project, script, runtime, index impl contract
- tool loader initialization과 disabled-tool shrinking
- Tools tab rendering과 Dock-local popup coordinate contract
- plugin entrypoint lifecycle

## 실행 방식

harness는 repository directory에서 직접 Godot을 실행하지 않습니다. 대신 fixture와 addon을 임시 stage root에 복사하고, 그곳에서 Godot을 실행합니다.

장점은 다음과 같습니다.

- 실제 assembly path와 가까운 환경을 만듭니다.
- 작업 directory를 직접 오염시키지 않습니다.
- 실패 시 `--keep-stage-root`로 stage root를 유지할 수 있습니다.
- harness-owned 임시 process만 정리할 수 있습니다.

## 단일 case와 다중 case

`headless_suite_runner.gd`는 case-level start/end log, single-case filter, multi-case selection, per-case cleanup hook, suite-level final cleanup을 지원합니다.

이 기능은 hang, performance 문제, cleanup 문제를 디버깅할 때 유용합니다.

## 현재 명령

권장 명령:

```powershell
dotnet run --project .\tests\godot_plugin_harness\GodotPluginHarness.csproj -c Release -- --godot-path "<Godot Editor Path>"
```

CI required subset을 재현하려면 script entry point를 직접 실행합니다.

```powershell
.\scripts\test_plugin_side_roslyn.ps1 -GodotPath "<Godot Path>"
```

자주 쓰는 추가 option:

- `--keep-stage-root`
- `--cases case_a,case_b`
- `--cleanup-stale-processes`

## 현재 출력

현재 출력에는 다음 정보가 포함됩니다.

- suite success와 success marker detection
- stage root
- 각 case의 result와 duration
- 전체 suite duration과 phase timing
- Godot exit code
- cleanup diagnostics
- stderr summary

일반 headless suite에서 `ObjectDB instances leaked at exit`나 `resources still in use at exit`이 보이면 harness는 실패합니다. editor probe mode는 editor exit noise를 별도 정책으로 처리합니다.

## 알려진 경계

- 테스트는 private method 이름보다 public test entry point와 contract seam을 우선합니다.
- 현재 형태는 structural contract와 local fake가 섞여 있습니다.
- 모든 UI pixel, 모든 OS foreground behavior, 모든 Godot API 조합을 검증하지는 않습니다.
- fixture와 본체가 달라지면 검증 결과도 달라질 수 있으므로 함께 갱신해야 합니다.

## 결론

플러그인 headless harness는 runtime 문제를 실제로 발견하고 회귀를 막는 데 사용되고 있습니다. 현재 초점은 테스트 seam과 cleanup boundary를 안정적으로 유지하는 것입니다.
