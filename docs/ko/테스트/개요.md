# 테스트 개요

이 문서는 Godot .NET MCP의 현재 테스트 구조, 상태, 알려진 경계, 앞으로의 발전 방향을 설명합니다.

## 전체 목표

테스트 체계의 목표는 네 가지입니다.

- 플러그인 entrypoint와 runtime service가 깨지지 않았는지 빠르게 확인합니다.
- 도구 loader, routing, system impl, user tool flow의 핵심 계약을 검증합니다.
- CI에서 빠른 검사와 무거운 Godot harness를 분리합니다.
- 문서, changelog, release note source, workflow가 서로 다른 사실을 말하지 않도록 막습니다.

## 주요 구성

현재 테스트는 다음 층으로 구성됩니다.

| 층 | 역할 |
|---|---|
| .NET build | Roslyn bridge와 C# 프로젝트가 컴파일되는지 확인 |
| guardrail scripts | refactor policy, docs i18n, release source 등 구조 규칙 확인 |
| Godot headless harness | 실제 fixture project에 addon을 복사해 Godot에서 contract suite 실행 |
| smoke와 CI | PR, merge group, dev push, release tag에서 필요한 subset 실행 |

## 현재 초점

테스트는 아직 모든 UI pixel이나 모든 Godot API 조합을 검증하지 않습니다. 대신 다음처럼 회귀 가능성이 큰 계약에 집중합니다.

- HTTP와 JSON-RPC routing
- tool loader와 disabled tool state
- runtime bridge와 runtime control reply
- scene, node, script, resource executor의 대표 경로
- client config serialization과 file transaction
- Dock model projection과 Tools tab rendering contract
- plugin entrypoint lifecycle

## 성공 기준

성공 기준은 단순히 “에러가 없다”가 아닙니다.

- suite JSON이 성공이어야 합니다.
- required subset이 CI에서 안정적으로 통과해야 합니다.
- tool loader status가 준비된 상태여야 합니다.
- harness가 stage root, duration, stderr summary 같은 증거를 남겨야 합니다.
- 문서와 release 관련 source가 현재 version과 맞아야 합니다.

## 알려진 경계

- Headless 검증은 UI 픽셀 정밀도보다 구조와 상태를 우선합니다.
- 일부 editor probe는 일반 headless suite와 exit noise 정책이 다릅니다.
- fixture와 plugin 본체가 다르면 검증 결과도 달라질 수 있으므로 함께 갱신해야 합니다.
- 새 도메인을 추가하면 executor, catalog, docs, harness fixture가 함께 움직여야 합니다.

## 발전 방향

테스트는 새 기능이 들어갈 때마다 “나중에 보강”이 아니라 같은 변경 범위에서 같이 보강되어야 합니다.

- 새 system tool은 최소한 routing과 대표 success/error contract를 가져야 합니다.
- 새 UI model은 rendering contract나 model projection test를 가져야 합니다.
- release workflow가 바뀌면 release source와 docs i18n guardrail이 함께 갱신되어야 합니다.
