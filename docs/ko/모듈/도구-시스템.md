# 도구 시스템

## 개요

`Godot .NET MCP`의 도구 시스템은 기능 영역별로 나뉩니다. 각 도구군은 장면 관리, 노드 편집, 스크립트 분석, 리소스 처리, 플러그인 운영처럼 명확한 작업 흐름 하나를 맡습니다.

현재 카탈로그는 세 가지 원칙을 우선합니다.

- 안정적인 분류: 하나의 거대한 액션 표면이 아니라 기능 영역으로 도구를 찾습니다.
- 쓰기 후 검증: 대부분의 쓰기 작업은 읽기 또는 조회 도구와 짝을 이룹니다.
- 실용적인 범위: 이론상 API 전체보다 Godot 편집기에서 자주 쓰는 흐름을 우선합니다.

## MCP 리소스와 프롬프트

JSON-RPC 계층은 `tools/list`와 `tools/call` 외에도 MCP 리소스와 프롬프트를 제공합니다.

- `resources/list`는 프로젝트 정보, 진단 요약, 기능 설명, 도구 카탈로그 JSON 리소스를 노출합니다.
- `resources/templates/list`는 장면, 스크립트, 리소스 읽기 템플릿을 제공합니다. 템플릿 읽기는 경로를 `res://`로 정규화하고, `..`, 절대 경로, 지원하지 않는 확장자를 거부합니다.
- `prompts/list`와 `prompts/get`은 프로젝트 파악, 콘텐츠 제작, 진단 triage, 참조 무결성, 런타임 검증, 편집기 UI 제어를 위한 고수준 프롬프트를 노출합니다.

이 표면은 가벼운 문맥과 작업 안내를 위한 것입니다. 파일을 바꾸거나 편집기를 제어하려면 여전히 대응하는 `system_*`, `scene_*`, `script_*`, `resource_*`, `filesystem_*` 도구를 사용해야 합니다.

## 현재 루트 그룹

Tools 페이지는 다음 루트 그룹을 보여 줍니다.

| 루트 그룹 | 주요 범주 | 일반적인 용도 |
|---|---|---|
| `Core` | `system`, `scene`, `node`, `script`, `resource`, `filesystem`, `project`, `editor`, `debug`, `dap`, `group`, `signal` | 시스템 도구, 장면, 노드, 스크립트, 리소스, 프로젝트, 편집기, DAP 디버깅 |
| `Plugin` | `plugin_runtime`, `plugin_evolution`, `plugin_developer` | 플러그인 런타임 상태, 사용자 도구 관리, 개발자 제어 |
| `Visual` | `animation`, `material`, `shader`, `lighting`, `particle`, `tilemap`, `geometry` | 애니메이션, 렌더링, 시각 리소스, 레벨 콘텐츠 |
| `Gameplay` | `physics`, `navigation`, `audio` | 물리, 내비게이션, 오디오, 런타임 동작 |
| `Interface` | `ui` | UI 구조, 테마, 레이아웃 |
| `User` | `user` | 사용자 확장 메커니즘으로 로드되는 사용자 도구 |

## 주요 도구 범주

### `system`

시스템 계층은 Agent가 사용하는 권장 시작점입니다. 프로젝트 상태, 플러그인 freshness와 생명주기 reload, 편집기 UI 제어, 런타임 진단, 장면 분석, 스크립트 구조 검사, 심볼 인덱싱을 제공합니다.

대표 도구는 다음 흐름으로 묶입니다.

- 프로젝트 수준: `system_project_state`, `system_editor_state`, `system_runtime_diagnose`, `system_project_configure`, `system_project_run`, `system_project_stop`.
- 플러그인 생명주기: `system_plugin_reload`, `system_plugin_update`.
- 편집기 UI: `system_editor_control`, `system_editor_log`.
- 런타임 자동화: `system_runtime_control`, `system_runtime_step`.
- DAP 디버깅: `system_dap_debugger`.
- 장면 수준: `system_scene_validate`, `system_scene_analyze`, `system_scene_patch`.
- 스크립트 수준: `system_bindings_audit`, `system_script_analyze`, `system_script_patch`.
- 인덱스 수준: `system_project_symbol_search`, `system_scene_dependency_graph`.

### `scene`, `node`, `script`

이 범주는 Godot 프로젝트의 구조를 직접 다룹니다.

- `scene`은 장면 로드, 계층 조회, 장면 실행, 바인딩 audit, 구조 패치를 맡습니다.
- `node`는 노드 조회, 속성 변경, 생명주기, 메타데이터, 표시 상태를 맡습니다.
- `script`는 스크립트 읽기, 구조 inspection, 참조 추적, 편집 흐름을 맡습니다.

### `plugin_runtime`, `plugin_developer`, `plugin_evolution`

플러그인 범주는 플러그인 자체의 상태와 유지보수 흐름을 다룹니다.

- `plugin_runtime`은 현재 런타임 상태, reload, self-diagnostic을 읽습니다.
- `plugin_developer`는 개발 보조, 언어 전환, 사용 가이드, 진단 표면을 제공합니다.
- `plugin_evolution`은 업데이트 source, 사용자 도구 scaffold, audit, 제거 흐름을 맡습니다.

## 호출과 반환 규칙

도구 입력은 가능한 한 명시적이어야 하고, 도구 출력은 클라이언트가 바로 판단할 수 있는 구조를 가져야 합니다.

- 성공 결과는 작업 결과와 검증에 필요한 readback 정보를 함께 제공합니다.
- 실패 결과는 사람이 읽을 수 있는 메시지와 구조화된 원인을 함께 제공합니다.
- 쓰기 도구는 가능한 한 변경 대상, 적용 결과, 후속 검증 힌트를 반환합니다.
- 도구 이름은 내부 구현 파일명보다 사용자가 수행하려는 작업을 반영해야 합니다.

## 사용자 도구

`plugin_evolution`은 사용자 도구의 전체 생명주기를 다룹니다. 자세한 내용은 [사용자 확장](사용자-확장.md)을 참고하세요.

사용자 도구는 `custom_tools/`에서 발견되며, 이름은 반드시 `user_*` 접두사를 가져야 합니다. 내장 도구와 사용자 도구는 Tools 페이지에서 함께 볼 수 있지만, 출처와 책임은 분리되어야 합니다.

## 유지보수 원칙

- 낮은 수준의 atomic helper를 공개 목록에 과도하게 나열하지 않습니다.
- 같은 의미의 도구를 다른 이름으로 반복하지 않습니다.
- action을 추가할 때는 같은 기능 영역 안의 자연스러운 동작인지 확인합니다.
- 도구 schema, Tools 페이지 preview, 문서, 테스트 fixture를 함께 갱신합니다.
