# 사용자 확장

이 문서는 `custom_tools/`에 들어가는 사용자 도구의 인터페이스 규칙, 로딩 메커니즘, `plugin_evolution` 도구, 승인 흐름, audit 기록을 설명합니다.

## 사용자 도구란 무엇인가

사용자 도구는 프로젝트 전용 확장입니다. 플러그인 본체를 바꾸지 않고도 특정 프로젝트에 맞는 MCP capability를 추가할 수 있습니다.

사용자 도구는 플러그인의 핵심 기능을 늘리는 수단이 아니라, 프로젝트별 반복 작업을 안전하게 보조하기 위한 표면입니다.

## 기본 규칙

- 도구 이름은 반드시 `user_*` 접두사를 사용합니다.
- 파일은 `custom_tools/` 아래에 둡니다.
- 내장 도구와 사용자 도구의 책임을 섞지 않습니다.
- 프로젝트마다 다른 사용자 도구를 가질 수 있습니다.
- 잘못된 스크립트가 있어도 플러그인 전체가 멈추지 않아야 합니다.

## 로딩 메커니즘

플러그인은 `custom_tools/` 아래의 유효한 GDScript 파일을 발견하고 hot load할 수 있습니다.

- editor를 재시작하지 않아도 변경을 감지할 수 있습니다.
- Tools 페이지는 source, 상태, reload 필요 여부, 최신 오류를 표시할 수 있습니다.
- 파싱 실패나 interface 불일치는 구조화된 상태로 남겨야 합니다.
- 사용자 도구가 실패해도 내장 도구 로더는 가능한 범위에서 계속 동작해야 합니다.

## scaffold와 승인 흐름

`plugin_evolution_scaffold_user_tool`은 두 단계 승인 흐름을 사용합니다.

1. 먼저 승인 없는 preflight로 생성될 내용을 확인합니다.
2. 내용과 대상 경로가 적절하면 `authorized=true`로 실제 생성을 요청합니다.
3. 생성 후 audit 기록과 Tools 페이지 상태를 확인합니다.
4. 필요한 경우 reload 또는 refresh로 새 도구가 보이는지 확인합니다.

이 흐름은 사용자 도구를 안전하게 추가하기 위한 장치입니다. Agent가 곧바로 파일을 쓰기보다, 먼저 생성 계획을 검토할 수 있게 합니다.

## audit

`plugin_evolution_user_tool_audit`는 승인과 삭제 기록을 추적합니다.

- 어떤 도구가 만들어졌는지
- 어떤 경로가 사용되었는지
- 삭제 또는 복원이 있었는지
- 승인 흐름이 지켜졌는지
- 최신 오류나 reload 상태가 무엇인지

audit는 나중에 “무엇이 언제 들어왔는지”를 확인하기 위한 안전망입니다.

## 삭제와 복원

사용자 도구 삭제는 단순한 파일 제거가 아니라 복원 가능성을 고려해야 합니다.

- 삭제 전 백업 디렉터리를 존중합니다.
- 실제 제거 후 Tools 페이지와 도구 목록이 갱신되어야 합니다.
- 복원 흐름은 기존 도구와 이름이 충돌하지 않는지 확인해야 합니다.

## `plugin_developer_user_visibility`

`plugin_developer_user_visibility`는 Dock에서 `User` category를 보여 주는 데 사용할 수 있습니다.

- 내장 도구와 사용자 도구를 같은 tree에서 보고 싶을 때 유용합니다.
- 다만 표시 방식은 사용자 도구의 책임과 내장 도구의 책임을 분리해야 합니다.
- 사용자 도구가 없을 때도 빈 상태가 명확해야 합니다.

## 안전성

사용자 도구는 프로젝트 안에서 실행되는 코드이므로 안전성이 중요합니다.

- 알 수 없는 스크립트를 무조건 실행하지 않습니다.
- preflight를 생략하지 않습니다.
- 승인 플래그의 의미를 흐리지 않습니다.
- 실패한 로드와 실행 오류를 audit 가능하게 남깁니다.
- 사용자 도구 때문에 내장 도구 registry가 손상되지 않아야 합니다.
