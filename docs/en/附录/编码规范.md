# Encoding Rules

This document defines the text file encoding rules for the `godot-dotnet-mcp` repository. The goal is to satisfy all of the following at the same time:

- maintainability across platforms for code and config files
- stable reading on Windows development machines
- practical use with the current `Windows PowerShell 5.1` workflow

The core rule is:

- use `UTF-8` without BOM by default
- only use `UTF-8 with BOM` when the file must work with the default read behavior of `Windows PowerShell 5.1` or with Agent memory-file consumption

The current rule set is enforced through these configuration files:

- `godot-dotnet-mcp/.editorconfig`: applies to formal source, configuration, docs, and `*.ps1` inside the repository
- the workspace root `.editorconfig`: applies only to the root-level collaboration memory files; the plugin repository itself follows this document and its own config

---

## Overall Rules

### Must use UTF-8 without BOM

The following file types and directories must use `UTF-8` without BOM by default:

- all source files:
  - `*.cs`
  - `*.gd`
  - `*.shader`
- all project and config files:
  - `*.csproj`
  - `*.props`
  - `*.targets`
  - `*.sln`
  - `*.json`
  - `*.yml`
  - `*.yaml`
  - `*.xml`
  - `*.toml`
  - `*.cfg`
  - `*.editorconfig`
  - `.gitignore`
  - `.gitattributes`
- all Godot text resources:
  - `*.tscn`
  - `*.tres`
- all formal public docs:
  - `README*.md`
  - `docs/**/*.md`

Reasons:

- this is the most stable and most universal default for the cross-platform toolchain
- it avoids BOM interference with script headers, config parsers, and strict tools
- it matches the common convention for current `.NET` and Godot text resources

### Must use UTF-8 with BOM

The following file types and directories should use `UTF-8 with BOM` in this repository:

- `AGENTS.md`
- `CLAUDE.md`
- `*.ps1`

Reasons:

- these files are often read or executed directly by `Windows PowerShell 5.1` in the current Windows environment
- `PowerShell 5.1` can display UTF-8 Chinese text incorrectly if the file has no BOM
- Agent memory files should open correctly in the default Windows toolchain

---

## PowerShell 5.1 Constraints

The current environment still includes `Windows PowerShell 5.1`, so these rules are required:

### Reading UTF-8 files

- when reading UTF-8 files without BOM, explicitly specify the encoding
- do not rely on the default `Get-Content` behavior for formal source, config, and `docs/**/*.md` files that contain Chinese text

Recommended form:

```powershell
Get-Content -Encoding UTF8 -Path .\docs\附录\编码规范.md
```

### Writing UTF-8 files

- do not rely on the default `Set-Content` or `Out-File` behavior for repository files, because the default can produce ANSI or the wrong encoding
- writes must explicitly specify the target encoding
- for UTF-8 without BOM, do not rely on `Set-Content -Encoding UTF8` in PowerShell 5.1, because it writes a BOM

Recommended approach:

- for formal source, config, and public docs:
  - prefer saving as `UTF-8` without BOM in the editor
  - or use the .NET API to write UTF-8 without BOM explicitly
- for `AGENTS.md`, `CLAUDE.md`, and `*.ps1`:
  - write `UTF-8 with BOM` explicitly

Without-BOM example:

```powershell
[System.IO.File]::WriteAllText(
    $path,
    $content,
    (New-Object System.Text.UTF8Encoding($false))
)
```

With-BOM example:

```powershell
[System.IO.File]::WriteAllText(
    $path,
    $content,
    (New-Object System.Text.UTF8Encoding($true))
)
```

## Execution Rules

### New files

- new source, config, and formal docs should default to `UTF-8` without BOM
- new `*.ps1`, `AGENTS.md`, and `CLAUDE.md` files should default to `UTF-8 with BOM`

### Editing existing files

- when editing a file, keep the target encoding of that file’s class and do not mix encodings
- if an existing file’s encoding conflicts with this rule set, tighten it to the target encoding when that does not interfere with the current task
- if you change the encoding rules, update both `.editorconfig` and this document; do not change only one side

### During review and refactoring

- if you see Chinese garbling, first check whether PowerShell 5.1 read the file as UTF-8 without BOM, instead of assuming the file is damaged
- when judging whether the repository is clean, check the encoding as well as the contents

---

## Exceptions

- if the repository’s main development environment eventually moves to PowerShell 7, the rule set can be re-evaluated and the BOM footprint may be reduced further
- if a third-party tool explicitly requires a special encoding, follow that tool’s hard requirement, but explain the reason in the relevant documentation
