# Lifecycle and Wiring

This document describes how the plugin entry point `plugin.gd` wires runtime objects, registers the Dock, connects Autoloads and debug bridges, and cleans up during a full reload or exit.

---

## Core Entry Point

The current plugin entry point is `addons/godot_dotnet_mcp/plugin.gd`, and its type is `EditorPlugin`. It no longer carries all business logic itself. Instead, it acts as a thin wiring layer that composes these objects:

- `LocalizationService`
- `PluginRuntimeState`
- `SettingsStore`
- `ServerRuntimeController`
- `ToolCatalogService`
- `ClientConfigService`
- `UserToolService` (delegates to `user_tool_catalog_service.gd` and `user_tool_maintenance_service.gd`)
- `PluginReloadCoordinator`
- `MCPRuntimeDebugStore`
- `plugin/features/server_feature.gd`
- `plugin/features/config_feature.gd`
- `plugin/features/ui_state_feature.gd`
- `plugin/features/user_tool_feature.gd`
- `plugin/features/reload_feature.gd`
- `plugin/features/tool_profile_feature.gd`
- `plugin/features/tool_access_feature.gd`
- `plugin/features/self_diagnostic_feature.gd`
- `PluginSelfDiagnosticStore`
- `plugin/presenters/dock_model_service.gd`
- `plugin/presenters/dock_presenter.gd`
- `plugin/presenters/client_config_presenter.gd`
- `ui/mcp_dock.tscn`

So the entry point is mainly responsible for wiring, synchronization, and bridging. It does not directly own the complex UI logic or tool implementations.

## `_enter_tree()` Wiring Order

`plugin.gd._enter_tree()` currently runs in this order:

1. Clear the previous self-diagnostic cache.
2. Recreate `PluginRuntimeState` so hot reload does not reuse a stale state container that was already cleared during exit.
3. Refresh the current service bundle through `_refresh_service_instances()`.
4. Call `_load_state()` to read the settings file and custom profiles.
5. Reset and initialize localization, then apply the current language.
6. Sync the log level to `MCPDebugBuffer`.
7. Create and attach `ServerRuntimeController` through `PluginRuntimeCoordinator`, and wire all server signals in one place.
8. Install the runtime bridge Autoload through `PluginRuntimeCoordinator`: `MCPRuntimeBridge`.
9. Install the editor debug bridge through `PluginRuntimeCoordinator`: `MCPEditorDebuggerBridge`.
10. Instantiate and attach `ui/mcp_dock.tscn`.
11. If this is the first load with settings, derive `disabled_tools` from the default profile.
12. Project the UI model with the first `_refresh_dock()` call.
13. Start polling in `_process()`.
14. If `auto_start=true`, start the embedded MCP service automatically, and record the time spent in the settings projection, server node, HTTP server, tool loader, and stdio stages in the plugin self-diagnostic action log.
15. Restore the Dock tab and focus if a focus snapshot was saved before reload.

The entry point now keeps `PluginActionRouter`, `PluginDockCoordinator`, and `PluginRuntimeCoordinator` as stable collaborators instead of lazily creating them in the hot path. `PluginDockCoordinator` now owns plugin-specific dock create, remove, recreate, stale cleanup, signal wiring, and dock instance counting. `PluginRuntimeCoordinator` owns the server controller, runtime bridge, and debugger bridge lifecycle.

The creation, attachment, signal wiring, detachment, and recreation of `ServerRuntimeController` now live in `PluginRuntimeCoordinator`, and the Dock lifecycle wrapper now lives in `PluginDockCoordinator`.

## `_exit_tree()` Cleanup Order

On exit, the plugin does not rely on Godot’s natural node release. It cleans up explicitly and in order:

1. Stop `_process()`.
2. Save the current settings.
3. Remove the Dock.
4. Unload the editor debug bridge.
5. Use `PluginRuntimeCoordinator` to disconnect server signals, run `detach()`, and clear the controller reference.
6. Explicitly clear the entry point’s feature, presenter, action router, and service references and object graph.
7. Reset the localization singleton.
8. Clear the entry point’s service references so no stale instances can be reused on the next hot reload.

This order is meant to reduce leftover state during a full reload or plugin disable.

## Dock Wiring Chain

The Dock is now assembled through the higher-level API in `PluginDockCoordinator`, with these steps inside:

1. Clear the old instance.
2. Remove any stale Dock that may remain after hot reload.
3. Load `ui/mcp_dock.tscn`.
4. Instantiate the root node and connect all tab signals.
5. Register it with the editor through `add_control_to_dock(DOCK_SLOT_RIGHT_UL, _dock)`.
6. If more than one instance is found, record a self-diagnostic incident.

The relationship between the entry point and the Dock is one-way:

- The Dock does not own service objects
- The Dock only exposes signals and `apply_model()`
- During wiring, `plugin.gd` connects signals to features or stable bridge methods, and then to the concrete services

## Runtime Bridge and Debug Bridge

### Runtime Bridge Autoload

`PluginRuntimeCoordinator` makes sure the project contains:

- Name: `MCPRuntimeBridge`
- Path: `res://addons/godot_dotnet_mcp/plugin/runtime/mcp_runtime_bridge.gd`

If another script already owns a same-named Autoload, the plugin does not forcefully replace it. Instead it:

- marks the runtime bridge state as failed
- writes an incident to self-diagnostics
- keeps the rest of the plugin working

### Editor Debug Bridge

`PluginRuntimeCoordinator` instantiates `MCPEditorDebuggerBridge` and registers it as an `EditorDebuggerPlugin` so the running main project’s debugger session summary can be synchronized into data that the plugin can read.

It also owns:

- creation, attach, signal wiring, detach, and recreation of `ServerRuntimeController`
- keeping `plugin.gd` away from direct server-controller lifecycle details

## State Polling and Model Refresh

The plugin does not make every service state change into a deep dependency notification. Instead it uses lightweight polling:

- `plugin.gd._process()` calls `_refresh_dock()` every `0.5s`
- `_refresh_dock()` rebuilds the shared model and delegates Dock context aggregation to `dock_model_service.gd`, then passes it to the presenter scripts
- `mcp_dock.gd.apply_model()` distributes the model to the three tabs

The benefits are:

- the entry logic stays simple and the state-sync path stays clear
- language, scaling, service state, and statistics can refresh together
- the UI controller stays close to a pure presentation layer

## Full Reload Strategy

The plugin supports two kinds of reload:

### 1. Runtime Reload

Triggered through the `plugin_runtime_reload` domain soft-reload action or from the server page. It refreshes tool domains or the server without destroying the whole plugin instance.

### 2. Full Plugin Reload

Triggered by `system_plugin_reload(action="full_reload_plugin")`, the compatibility entry `plugin_runtime_reload(action="full_reload_plugin")`, or the Home page full-reload button. `PluginReloadCoordinator` then drives the Godot plugin layer through:

1. `set_plugin_enabled(false)`
2. A short wait for the old server node and TCP listener to release
3. `set_plugin_enabled(true)`

The coordinator sits under the editor `base_control`, not under the plugin’s own node, so it can still finish the re-enable step after the plugin is disabled. The current short delay before re-enable helps reduce the race where the old `TCPServer` is still releasing its port while the new plugin instance auto-starts.

Before a full reload, the plugin records:

- the current host Dock tab
- the current internal tab in `MCPDock`
- the relative path of the focused control

After reload, it reactivates the host Dock and then restores the inner tab and focus.

Updating the on-disk addon copy and reloading the running instance are two different stages. Copying, updating, or installing `addons/godot_dotnet_mcp/` only changes files on disk in the target project. The running editor instance will not replace itself just because the disk files changed. When Settings sync succeeds and both archive write and `.mcp_sync.json` freshness marker write succeed, the plugin schedules a full lifecycle reload so the newly written plugin files take effect in the current editor. For other external on-disk updates, call `system_plugin_reload(action="full_reload_plugin")`. After reload, use `/health`, `system_plugin_reload(action="get_freshness")`, `plugin_runtime_state(action="get_self_health")`, or `system_project_state(include_runtime_health=true).runtime_health.freshness` to check `running_instance`, `disk_source`, `sync`, and `comparison`, and confirm `needs_lifecycle_reload=false`.

## Boundaries and Responsibilities

### `plugin.gd` is responsible for

- lifecycle
- service object wiring
- Dock scene entry point
- UI signal to feature and service bridge
- feature workflow configuration
- Dock model collaborator wiring and presenter calls
- exposing a stable tool access state entry for `tool_loader`
- settings read and write triggers
- self-diagnostic incident records

### `plugin.gd` is not responsible for

- specific UI layout
- the control state machine for each tab
- the step-by-step orchestration of Server, Config, User Tool, Runtime Reload, Profile, Config Exchange, Tool Access, or Self Diagnostic interactions
- Dock tab state writeback, language switching, tree collapse persistence, or copy-tip orchestration
- Dock create, remove, recreate, stale cleanup, signal wiring, or dock instance counting details
- Dock context aggregation, tool-tree projection, or installation detection details
- the implementation of `tool_loader` tool access state lookup
- tool protocol dispatch
- profile file read and write details
- client config merge logic
- tool-domain execution logic
