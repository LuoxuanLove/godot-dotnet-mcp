# Installation and Release

This document describes the installation method, enable steps, and pre-release checks for the Godot .NET MCP plugin.

The plugin is self-contained: Roslyn syntax analysis runs inside the Godot .NET runtime and does not need an external host process.

---

## Installation Methods

### Method 1: Godot Asset Library

Open the target project in Godot, go to the `AssetLib` tab, search for `Godot .NET MCP`, and click `Install`. You can also open the Godot Asset Library page:

```text
https://godotengine.org/asset-library/asset/4923
```

After installation, keep the directory layout as:

```text
addons/godot_dotnet_mcp
```

Then:

1. Open the target project in Godot
2. Go to `Project Settings > Plugins`
3. Enable `Godot .NET MCP`
4. Open `MCPDock`
5. Start the service from the `Home` tab

### Method 2: Copy the Source Files Directly

This is useful for repository development, debugging, or direct use of the current source tree in a local project:

1. Copy `addons/godot_dotnet_mcp/` from source into the target Godot project
2. Open the project in Godot
3. Go to `Project Settings > Plugins`
4. Enable `Godot .NET MCP`
5. Open `MCPDock > Home` and start the service

## Runtime Requirements

- Godot `4.6+` with .NET support, meaning a Godot Mono or .NET build
- The project must have .NET scripting enabled

### C# Analysis Notes

- C# syntax analysis is handled by Roslyn inside the plugin. It is syntax-first and runs in the Godot .NET runtime itself
- It only extracts syntax-tree information. It does not use `SemanticModel` and does not compile-load the project
- No external Roslyn installation or configuration is needed

## Branch and Merge Flow

- There is no long-lived `develop` or `main` branch. `dev` is the only long-lived integration branch and should always stay in a current, verifiable state
- Feature work should branch from `dev` into `feature/*` short branches, and bug fixes should branch from `dev` into `fix/*` short branches
- PRs, `dev` pushes, and manual runs can trigger plugin validation workflows. Normal short-branch PRs are validated through `pull_request` so the same commit does not trigger both short-branch `push` and PR validation. PRs must target `dev`, and the necessary README, changelog, docs, and CI required subset must be kept in sync before merge. The changelog must cover important `Documentation` and `Internal` changes, not only user-visible features and fixes
- Final release wrapping still uses a short branch such as `release/v1.0.1`. Confirm the version number, release notes, docs, and validation results before merging back into `dev`

## Release Flow Entry Point

See `docs/流程/发布Runbook.md` for the full release procedure. The release flow keeps only two delivery paths: Godot Asset Library installation and direct copy of the `addons/godot_dotnet_mcp/` source files. It does not produce, upload, or document zip packages, release packages, local build artifacts, or their installation flow. After `dev` moves forward, you can maintain a `next` draft release as the next-version note draft. Both the draft and the formal release are rendered from the hand-written summary in `docs/流程/release-notes/release-notes-v*.md`, the changelog details in `docs/en/CHANGELOG.md`, and the commit summary. The formal `v*` release will run version consistency and release-note source preflight checks and can reuse the successful dry-run record for the same commit to skip repeated build and harness work.

When an Agent or bot participates in development, follow `docs/流程/Agent与Bot流程.md`: short-branch commits and pushes can be automated, and if no extra account is used, `actions-bot-relay` can let `github-actions[bot]` create a PR from a patch. A remote `dev` merge must still be confirmed manually by a maintainer on GitHub.

## Validation Tips

### Installation Loop

Recommended validation order:

1. The plugin can be enabled in Godot and `MCPDock` can be opened
2. `MCPDock > Home` displays the service state correctly
3. `GET http://127.0.0.1:3000/health` returns a healthy response
4. `GET http://127.0.0.1:3000/api/tools` returns the tool list
5. The MCP client can connect to `http://127.0.0.1:3000/mcp`
6. The C# script tools, such as `script_inspect` and `script_exports`, return `engine=roslyn` and `mode=syntax`

### Pre-Release Checks

Check at least these items:

1. `plugin.cfg`, the protocol facts, and the changelog all agree on the version
2. The README, changelog, `docs/流程/release-notes/release-notes-v*.md`, the related docs, and validation results are synced. The changelog has recorded important `Documentation` and `Internal` changes, while the release note source still only contains the user-facing release story
3. The source tree does not introduce non-plugin code or local build artifacts
4. Any `.github/workflows/**` change has passed workflow lint
5. The PR target branch is `dev`, and the formal release `v*` tag, `plugin.cfg`, the English changelog, the Simplified Chinese changelog, and the release-note source file all match
6. The release note only contains the plugin’s own summary, compatibility notes, validation info, and commit summary
