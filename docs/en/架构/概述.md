# Architecture Overview

## Reference Entry Point

- For the strict encoding and architecture rules, read `docs/架构/编码与架构规范.md` first.

## Target Position

`godot_dotnet_mcp` is meant to be an in-editor MCP service layer that provides a stable, composable, and verifiable automation entry point for Godot 4 projects.

The current design emphasizes:

- editor-internal tool calls instead of offline script generation
- Roslyn running inside the Godot .NET runtime, with a syntax-first approach
- requiring the Godot .NET editor build, 4.6+ Mono/.NET
- no external host and no child process
- keeping the category structure stable instead of adding more and more duplicate entry points
- making static analysis and binding checks for Godot.NET projects a core feature
- keeping the necessary GDScript support, but no longer centering the interface around GDScript

## Layer Structure

```text
EditorPlugin
  ├─ plugin.gd
  ├─ Dock scene assembly
  ├─ plugin state and settings assembly
  ├─ service start and stop coordination
  └─ explicit signal connections with the UI controllers

MCPServer
  ├─ plugin/runtime/mcp_http_server.gd
  ├─ tools/core/tool_loader.gd
  ├─ HTTP/TCP listener
  ├─ JSON-RPC / MCP request dispatch
  ├─ tools/list
  └─ tools/call

Tool Executors
  ├─ tools/<category>/executor.gd
  ├─ tools/*.gd (compatibility implementation layer)
  ├─ system (high-level tools: project, scene, script, index, including Atomic Bridge)
  ├─ scene / node / script
  ├─ filesystem / resource / project
  ├─ animation / physics / navigation / audio / ui
  ├─ editor / debug / plugin domains
  └─ custom_tools/*.gd (User tools, loaded by system/executor.gd)

Plugin-internal Roslyn
  ├─ addons/godot_dotnet_mcp/dotnet_bridge/ (plugin-local Roslyn syntax library)
  ├─ plugin/runtime/roslyn/ (plugin-local Roslyn facade)
  └─ syntax-first analysis, no SemanticModel

Shared Helpers
  ├─ base_tools.gd
  ├─ plugin/config/config_paths.gd
  └─ tools/core/*
```

## Runtime Object Relationships

The plugin entry point used to be a single oversized script. It has now been reduced to a thin assembly layer. The current object graph is:

```text
plugin.gd
  ├─ PluginRuntimeState
  ├─ SettingsStore
  ├─ ServerRuntimeController
  ├─ ToolCatalogService
  ├─ ClientConfigService
  ├─ DockModelService
  ├─ DockPresenter
  ├─ PluginReloadCoordinator
  ├─ MCPRuntimeBridge (Autoload, injects the main project runtime event channel)
  ├─ MCPEditorDebuggerBridge (receives editor debugger session events)
  └─ ui/mcp_dock.tscn
       ├─ ui/server_panel.tscn
       ├─ ui/tools_tab.tscn
       └─ ui/config_panel.tscn
```

That means:

- `plugin.gd` only handles assembly, state sync, and signal bridging
- Dock model aggregation and presentation mapping are delegated to `dock_model_service.gd` and `dock_presenter.gd`
- Dock tabs no longer create service objects or read and write config files directly
- tool profile calculation, config text generation, and settings persistence are moved out of the UI
- plugin-level full reload is handled by a separate coordinator node that keeps the re-enable action alive after the current plugin instance is destroyed
- when adding a new tab, prefer a new scene and controller instead of making the entry script larger

## Core Responsibilities

### `plugin.gd`

Responsible for:

- managing the plugin lifecycle
- assembling the Dock scene and controllers
- connecting state, services, tool catalog, and config services
- exposing the smallest possible public API (`get_server` / `start_server` / `stop_server`)
- exposing a stable `get_tool_access_provider()` bridge for `tool_loader`
- providing `editor_scale`, current language, and service references to the Dock model layer
- saving and restoring the Dock tab, focus, and snapshot around a full reload

Not responsible for:

- building the Dock node tree
- matching profiles and counting tools
- reading or writing config files in detail
- protocol-level request dispatch
- updating individual controls after a button click

### `plugin/runtime/mcp_http_server.gd`

Responsible for:

- accepting requests
- parsing the protocol
- building the tool list
- forwarding tool calls to `MCPToolLoader`
- wrapping results in a consistent response shape
- tracking connections, requests, the latest request method, and the time

### `tools/core/tool_loader.gd`

Responsible for:

- keeping the `category -> script path -> runtime instance` loading map
- scanning builtin tools and `custom_tools/*.gd`
- preloading enabled categories while keeping the other category definitions cached
- exposing single-domain and full hot reload entry points
- collecting load state, reload status, and performance summaries

### `tools/*.gd`

Responsible for:

- providing the authoritative entry point for one capability domain
- dispatching sub-behavior through `action`
- keeping input, output, and error structures consistent
- reusing the path parsing, node serialization, and JSON/Variant normalization helpers from `base_tools.gd`

### `ui/*.tscn` + `ui/*.gd`

Responsible for:

- hosting the Dock root UI and each tab node structure
- reporting user actions to `plugin.gd` through explicit signals
- handling presentation and interaction only, not the service lifecycle
- adjusting spacing, minimum size, and text area height according to `editor_scale`
- turning off Godot automatic translation for internal plugin text, so display language is controlled by the local localization service

### `plugin_*` Service Objects

Responsible for:

- `plugin/runtime/plugin_runtime_state.gd`: runtime fields and the current settings / custom profile state
- `plugin/runtime/tool_profile_catalog.gd`: builtin profile catalog and profile storage directory
- `tools/tool_registry.gd`: the source of truth for builtin executor registration
- `tools/tool_manifest.gd`: stable access point for tool domain and category metadata
- `plugin/runtime/plugin_runtime_state.gd`: settings path, default settings, collapsed defaults, and runtime state
- `plugin/config/settings_store.gd`: settings and custom profile persistence
- `plugin/runtime/server_runtime_controller.gd`: `MCPHttpServer` lifecycle and status proxy
- `plugin/runtime/tool_catalog_service.gd`: domain, category, and profile calculation
- `plugin/config/client_config_service.gd`: the Config page service facade, with the concrete logic moved to serializer, inspection, transaction, and launcher adapter collaborators

### `plugin/runtime/roslyn/*`

Responsible for:

- `plugin_roslyn_service.gd`: plugin-local Roslyn service facade that handles C# syntax analysis requests
- `PluginRoslynRuntimeFacade.cs`: C# facade that turns Roslyn syntax trees into DTOs
- `PluginRoslynSyntaxCore.cs`: shared Roslyn syntax core

## Startup Flow

1. `plugin.gd._enter_tree()` calls `_load_state()` and reads data from `user://godot_dotnet_mcp/settings.json` and `user://godot_dotnet_mcp/profiles`.
2. The plugin applies the language and assembles `ServerRuntimeController`.
3. `MCPRuntimeBridge` is installed as an Autoload in the current Godot project, by injecting it into `project.godot`.
4. `MCPEditorDebuggerBridge` is registered with `EditorDebuggerPlugin` and starts receiving debugger session events from the main project.
5. The entry script instantiates `ui/mcp_dock.tscn` and connects all explicit signals.
6. If this is the first settings load, it calculates `disabled_tools` from the builtin profile.
7. It starts the server when `auto_start` says to do so.
8. If a focus snapshot was saved before the last full reload, it restores the Dock tab, the inner tab, and the original focused control after the first refresh.
9. `_process()` refreshes the Dock model every 0.5 seconds so the service state and statistics stay in sync.

## UI Data Flow

The Dock uses a one-way data flow:

1. `plugin.gd._build_dock_model()` delegates to `dock_model_service.gd` to aggregate state, statistics, tools, config text, and `editor_scale`.
2. `dock_model_service.gd` passes the context to `dock_presenter.gd` to build the final model.
3. `mcp_dock.gd.apply_model()` distributes the model to the three tabs.
4. The tab controllers push user actions back as signals, such as `start_requested`, `tool_toggled`, and `config_write_requested`.
5. `plugin.gd` receives the signals, updates state, calls the service objects, and refreshes the Dock again.

The direct benefits are:

- the UI scripts do not need to keep service references
- language changes and scaling updates can rerender together, while language changes stay as a light `apply_model()` refresh
- any tab can be replayed from the model, which makes future tests and splits easier

## Current Architecture Rules

- Prefer category stability over introducing duplicate prefixes
- Return values must be directly consumable by MCP clients
- Write operations should support write-then-read verification whenever possible
- Scene, script, and resource tools should serve editor workflows first
- The public category names stay stable, while the internal directory structure may still evolve
- The plugin UI should be scene-based, while the entry script stays thin
- Tab scripts should only handle presentation and interaction, not talk directly to `plugin/runtime/mcp_http_server.gd`
- `EditorInterface.get_editor_scale()` is the only scaling source
