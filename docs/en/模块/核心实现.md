# Core Implementation

This document summarizes the responsibility boundaries of `localization/`, `plugin/config/`, `plugin/runtime/`, `custom_tools/`, and the shared helper scripts. It is the core implementation overview outside the tool-domain bodies themselves.

---

## Directory Layers

```text
localization/
plugin/
  ├─ config/
  └─ runtime/
tools/
  ├─ core/
  ├─ *_tools.gd
  └─ <category>/executor.gd
custom_tools/
dotnet_bridge/
```

## `localization/`

### Contents

- `localization_service.gd`
- `locale_en.gd`
- `locale_zh_cn.gd`
- `locale_zh_tw.gd`
- `locale_ja.gd`
- `locale_de.gd`
- `locale_es.gd`
- `locale_fr.gd`
- `locale_pt.gd`
- `locale_ru.gd`

### Responsibilities

- load all language dictionaries
- switch the current language
- provide `get_text()` and language-display-name helpers
- supply text for the Dock UI and tool-profile copy

### Constraints

- the key set in each language file should match `locale_en.gd`
- fixed scene text should not be the final display source
- plugin root controls generally disable `auto_translate_mode`

## `plugin/runtime/`

This is the most important service layer in the current plugin implementation.

### State and Lifecycle

- `plugin_runtime_state.gd`
- `plugin_runtime_state_service.gd`
- `tool_profile_catalog.gd`
- `plugin_runtime_state.gd`
- `server_runtime_controller.gd`
- `plugin_reload_coordinator.gd`

### Diagnostics and Debugging

- `plugin_self_diagnostic_store.gd`
- `mcp_runtime_debug_store.gd`
- `mcp_editor_debugger_bridge.gd`: registers as `EditorDebuggerPlugin`, receives the main project’s debugger session events, and forwards them to `MCPDebugBuffer` and `MCPRuntimeDebugStore`
- `mcp_runtime_bridge.gd`: installed in the main project as an Autoload. The project runtime can send structured events through `emit_event`, `emit_log`, `emit_info`, `emit_warning`, and `emit_error`. It uses two channels, `godot_mcp/runtime_event` and `godot_mcp/runtime_log`, caches up to 300 entries, and falls back to `user://godot_mcp_runtime_bridge_events.json` when `EngineDebugger` is inactive

### Service and Catalog

- `mcp_http_server.gd`
- `mcp_tool_loader_supervisor.gd`
- `mcp_tool_rpc_router.gd`
- `tool_catalog_service.gd`
- `user_tool_service.gd`
- `user_tool_catalog_service.gd`
- `user_tool_maintenance_service.gd`

These objects together support:

- settings and profile projection
- embedded server lifecycle
- tool-loader lifecycle, self-recovery, and supervision
- tool routing and result normalization for `tools/list` and `tools/call`
- tool-catalog and permission trimming
- user-tool discovery and management
- the self-diagnostic path

## Shared Layer in `tools/`

Besides the category executors, the `tools/` directory also contains shared scripts:

### Base and Shared Root Scripts

- `base_tools.gd`
- `plugin_shared.gd`
- other `*_tools.gd`

### General Helpers

- `mcp_debug_buffer.gd`
- `mcp_file_utils.gd`
- `mcp_json_utils.gd`
- `mcp_node_utils.gd`
- `mcp_script_parser.gd`
- `mcp_type_utils.gd`

### Core

- `tool_manifest.gd`
- `tool_registry.gd`
- `core/tool_loader.gd`
- `core/tool_lsp_diagnostics_adapter.gd`

Their relationship is:

- `tool_registry.gd` defines the official registration chain for builtin executors
- `tool_manifest.gd` handles stable domain and category metadata for the UI, permission layer, and state layer
- `tool_loader.gd` loads executors directly from `tool_registry.gd` and owns loading, calling, and reloading
- `tool_lsp_diagnostics_adapter.gd` owns the lifecycle of GDScript LSP diagnostics, bridge binding, and debug snapshots from the loader main chain
- `base_tools.gd` and the other helpers reduce repeated code

## `custom_tools/`

This directory holds User tool scripts maintained through the `plugin_evolution` tools or scaffolding. Current rules:

- do not write into builtin tool-domain directories
- create or delete scripts only through the two-step `plugin_evolution` authorization flow
- discover them through `system/executor.gd._load_custom_tools()`
- when deleting, write to `.backup/` so recovery is possible

---

## Core Design Direction

The current implementation follows four principles:

- thin entry point: `plugin.gd` only wires and bridges
- scene-based UI: each Dock tab is its own scene and controller
- domain-split tools: categories are split by executor instead of being stuffed into one large tool
- structured observation: errors, actions, sessions, and logs are recorded in a structured way whenever possible
- single permission entry: `tool_access_feature.gd` is the only permission provider on the plugin side
