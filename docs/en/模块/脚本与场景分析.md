# Script and Scene Analysis

## Script Tools

Current script tool interfaces include:

- `script_read`
- `script_open`
- `script_inspect`
- `script_symbols`
- `script_exports`
- `script_edit_gd`

### Capability Boundaries

- both `.gd` and `.cs` support reading, opening, and structural analysis
- `.gd` supports limited editing
- `.cs` is currently read-only analysis only and does not take on complex rewriting work

## `script_*` Operation Guide

### `script_read`

Purpose:

- read raw `.gd` or `.cs` source text
- quickly confirm whether a script file path is correct
- provide context for external clients

Recommended cases:

- when you need the client to see the full script text
- when the structured result from `script_inspect` is not enough to explain the problem

### `script_open`

Purpose:

- open a script in the Godot editor script tab
- jump to a specific line
- inspect the current list of open scripts

Recommended cases:

- when switching back from MCP to manual editing
- when you want to jump from the analysis result to the real code location in the editor

### `script_inspect`

Purpose:

- return the language, class name, base type, methods, exported members, and export groups

Recommended cases:

- when you want to quickly see what a script exposes
- when you need a static structure check without opening the script editor

### `script_symbols`

Purpose:

- return class, method, export, and enum information in a unified structure
- support filtering by kind and keyword

Recommended cases:

- building a script index
- quick filtering by exported member or method name

### `script_exports`

Purpose:

- return only exported members and export groups

Recommended cases:

- comparing with scene bindings
- caring only about Inspector-visible fields and not the full symbol table

### `script_edit_gd`

Purpose:

- provide limited editing for GDScript only

Supported actions:

- create a new script
- rewrite the file as a whole
- add or remove functions
- add variables, signals, or exported fields
- read function and variable lists

Limitations:

- does not take on arbitrary AST-level rewriting
- does not handle C# editing
- is better for template-style small changes than for large-scale rewrites

## Scene Analysis Tools

Current scene analysis tools include:

- `scene_bindings`
- `scene_audit`

### Target Problems

They are mainly used to find the following issues:

- `[Export]` members that are not bound
- missing scene binding values
- mismatches between binding types and the expected types
- scripts that exist but do not expose their exported members correctly

## `scene_*` Analysis Guide

### `scene_bindings`

Purpose:

- analyze the real binding state of exported members in the current scene or a specific scene

Recommended flow:

1. Use `scene_bindings.current` or `scene_bindings.from_path`.
2. Check each node’s script path, exported members, current binding value, and whether anything is missing.
3. If you need to confirm the script declaration, call `script_exports` or `script_inspect`.

### `scene_audit`

Purpose:

- reduce the `scene_bindings` result into a structured issue list

Recommended flow:

1. Use `scene_audit.current` or `scene_audit.from_path`.
2. Focus on `issue_count` and `issues`.
3. For the node paths inside the issues, call `scene_hierarchy`, `node_query`, or the script tools to continue tracing.

## Relationship with Godot.NET

The value of this tool set is not just reading script text. It connects script structure with scene instance binding state. For Godot.NET projects, that is usually the slowest part of manual debugging.

## Typical Troubleshooting Flow

### Exported field is empty

1. Use `script_exports` to check whether the script really declares `[Export]` or `@export`.
2. Use `scene_bindings` to check whether the field is empty in the scene instance.
3. Use `scene_audit` to get a structured issue description.
4. If you need to locate the node, use `scene_hierarchy` or `node_query.get_info`.

### Inspector looks wrong after changing the base class

1. Use `script_inspect` to confirm the current `base_type`.
2. Use `scene_bindings` to see whether the existing exported bindings still resolve.
3. If the bindings disappear, check whether the scene needs to be saved again or rebound.

### You want to jump back from the script declaration to the editor

1. Use `script_symbols` or `script_inspect` to find the method or exported member.
2. Use `script_open.open_at_line` to jump directly to the line in the script.

## Implementation Method

### Script analysis

The stable entry point for script analysis is currently `tools/script/executor.gd`. The route is:

1. `catalog.gd` provides the `script_*` tool definitions.
2. `script_executor.gd` routes by tool name.
3. The `read / inspect / references / gdscript_edit / csharp_edit` services handle the concrete logic.
4. Shared helpers continue to come from `base_tools.gd` and `mcp_script_parser.gd`.

This works because:

- `.gd` and `.cs` need to share one public return shape
- external clients usually only care about getting the class, methods, and exports, not a full compilation semantic model

### Scene binding analysis

The stable entry point for scene analysis is currently `tools/scene/executor.gd`. The route is:

1. `catalog.gd` provides the `management / hierarchy / run / bindings / audit` tool definitions.
2. `scene_executor.gd` routes by tool name.
3. The `management / hierarchy / run / bindings / audit` services handle the concrete logic.
4. `bindings_service.gd` handles exported member parsing, instance value extraction, and issue construction.
5. `audit_service.gd` projects a structured issue list on top of the binding analysis results.

The key point is that this does not look only at the scene file text, and it does not look only at the script text. It uses the combined result of script declaration plus scene instance value.

## Current Risk Points

If any of the following happens, it should be treated as an implementation defect first, not as user misuse:

- the script tools can parse exported members, but scene analysis cannot read the same member
- scene analysis can find the node, but cannot stably resolve the same path for the node tools
- the returned structure is missing binding value types, which prevents the client from telling whether a binding is real
