# Tool System

## Overview

`Godot .NET MCP` splits its tools by capability domain. Each family owns one clear workflow, such as scene management, node editing, script analysis, resource handling, or plugin operations.

The current catalog focuses on three principles:

- Stable grouping: find tools by capability domain first, not by one giant action surface.
- Write then verify: pair most write operations with a readback or query tool.
- Practical coverage: prioritize common Godot editor workflows over theoretical API completeness.

## MCP Resources and Prompts

The JSON-RPC layer exposes first-class MCP Resources and Prompts in addition to `tools/list` and `tools/call`.

- `resources/list` exposes project information and diagnostic summary JSON resources, plus capability and tool-catalog JSON resources for fast context setup.
- `resources/templates/list` exposes three read-only templates: `godot-dotnet-mcp://scene/{path}`, `godot-dotnet-mcp://script/{path}`, and `godot-dotnet-mcp://resource/{path}`. Template reads normalize the path to `res://` and reject `..`, absolute paths, and unsupported extensions.
- `prompts/list` and `prompts/get` expose six high-level prompts: `godot.project_orientation`, `godot.content_authoring`, `godot.debug_triage`, `godot.reference_integrity`, `godot.runtime_validation`, and `godot.editor_ui_control`.

These surfaces are for lightweight context and workflow guidance. To change files or control the editor, still use the corresponding `system_*`, `scene_*`, `script_*`, `resource_*`, or `filesystem_*` tools.

Prompt Guides are native MCP prompt surfaces, not `tools/call` actions. Use `prompts/list` first, then `prompts/get` with optional parameters to read the workflow text. `system_help` also returns a `prompt_guides` summary so the Agent can discover the prompts from the help entry point.

| Root Group | Main Categories | Typical Use |

## Main Tool Categories

### `system`

The system layer is the recommended starting point for Agents. It provides project state, plugin freshness and lifecycle reload, editor UI control, runtime diagnostics, scene analysis, script structure checks, and symbol indexing.

The exposed high-level system tools are grouped into eight sets:

- Project-level: `system_project_state`, `system_editor_state`, `system_runtime_diagnose`, `system_project_configure`, `system_project_run`, `system_project_stop`.
- Plugin lifecycle: `system_plugin_reload`, `system_plugin_update`.
- Editor UI: `system_editor_control`, `system_editor_log`.
- Runtime automation: `system_runtime_control`, `system_runtime_step(action=step|capture|input)`.
- DAP debugging: `system_dap_debugger(...)`.
- Scene-level: `system_scene_validate`, `system_scene_analyze`, `system_scene_patch`.
- Script-level: `system_bindings_audit`, `system_script_analyze`, `system_script_patch`.
- Index-level: `system_project_symbol_search`, `system_scene_dependency_graph`.

`system_project_state` supports `summary=true` for a compact state and `sections=[...]` for segmented reads. If neither is specified, it returns the full flattened response.

`system_project_run` can optionally wait for structured runtime-bridge events through `success_markers` and `failure_markers`. Without markers it keeps the compatible immediate return and `timeout_ms` auto-stop behavior. With markers, `timeout_ms` becomes a bounded wait timeout and failure markers win.

`system_editor_control` can switch screens, capture editor screenshots, enumerate controls, map coordinates, focus controls, activate controls, and click within a control using local coordinates. It does not move the physical cursor or control the system window.

`system_plugin_reload` reads freshness or schedules a full plugin disable/enable lifecycle reload. `system_plugin_update` reads the current version and source ref, starts ref discovery and sync, and polls sync and reload progress.

`system_runtime_control` and `system_runtime_step` handle runtime gating and runtime I/O. `system_dap_debugger` connects to the built-in Godot DAP endpoint at `127.0.0.1:6006` by default and returns structured `dap_unavailable` data when the endpoint cannot be reached.

Runtime automation and project read-only capabilities are reported separately through `runtime_capabilities`, so Agents can decide whether the current MCP can start runtime, take control, capture runtime, or stay out of the foreground.

`system_userdata_maintenance` keeps screenshot and audit caches under `user://godot_dotnet_mcp/` and only cleans them when explicitly called.

### `plugin_runtime`

`plugin_runtime` handles plugin state, reload, server, tool enable/disable, and usage guidance.

### `plugin_evolution`

`plugin_evolution` handles the full lifecycle of User tools. See [用户扩展.md](用户扩展.md) for details.

### `plugin_developer`

`plugin_developer` handles Dock visibility, log level, language, tool presets, and config import/export.

### `animation`, `material`, `shader`, `lighting`, `particle`, `tilemap`, `geometry`

These categories cover animation, materials, lighting, particles, TileMap, and geometry workflows.

### `physics`, `navigation`, `audio`, `ui`

These categories cover runtime behavior and interface content.

### `group` and `signal`

These two categories remain separate entry points for batch calls and signal connection management.

## Plugin Tool Domains

Plugin-related tools are split into separate categories by responsibility:

- `plugin_runtime`
- `plugin_evolution`
- `plugin_developer`

New integrations, documentation, and script examples should use the corresponding fine-grained tool names, and should be registered and displayed through `tools/tool_registry.gd`.

## Typical Usage

1. Use a query tool first to confirm the target path, state, or whether the file exists.
2. Then perform the write operation.
3. Finally, immediately use the corresponding read tool to verify the result.

If the task involves plugin state or User tools:

1. First use `plugin_runtime_state` to check the current state.
2. Then use `plugin_runtime_toggle` or `plugin_runtime_reload` to make adjustments.
3. If User tools need attention, use the `plugin_evolution_*` tools.
4. After the change, read state or audit records again to confirm the result.

If the problem happens during main-project runtime:

1. Run the main project from the editor as usual.
2. After stopping, use `system_runtime_diagnose`.
3. Read runtime errors, compile issues, and performance snapshots.

## Input and Return Conventions

- Tool name format: `{category}_{tool}`.
- Tool parameters are passed according to each tool’s own field definitions.
- `/api/tools`, MCP `tools/list`, and the Dock Tools page all generate display results from the same visible-tool set.

Common path rules:

- Resource paths use `res://`.
- Node paths should preferably be relative to the current scene root node.
- `/root/...`-style paths are still valid in the current version.

Common return shape:

- Success results usually contain `success`, `message`, and `data`.
- Failures return `success: false` and `error`.

## Usage Advice

- When adding new workflows, look for an existing category first instead of assuming a new tool is needed.
- When changing project content, prefer tool combinations that support write-then-readback verification.
- If you need plugin guidance, use the three `usage_guide` tools directly.
- Before working on User tools, read [用户扩展.md](用户扩展.md).
