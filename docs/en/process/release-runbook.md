# Release Runbook

This document records the pre-release checks and remote release flow for Godot .NET MCP. It only describes releases for this plugin, not any project outside the repository or any local workspace flow.

---

## 1. Release Principles

- `dev` is the stable integration branch. Every change must land in `dev` through a short-branch PR before release
- Normal `feature/*`, `fix/*`, `docs/*`, `chore/*`, and `hotfix/*` PRs must keep the plugin’s public version metadata aligned with `dev`. Only a `release/*` PR that targets `dev` may change that version
- Formal GitHub Releases are created through the maintainer-triggered `publish-release` workflow. Pushing a `v*` tag runs tag validation and release-note artifact generation, but it does not create the formal GitHub Release
- Installation paths are limited to the Godot Asset Library and direct copy of prepared installable addon contents. Do not document raw repository source-copy installs; the raw source tree contains internal bridge and companion projects that must stay out of host project compile surfaces. Repository-level development directories such as `companion/`, `tests/`, and `scripts/` are not installed into Godot projects
- Do not create, upload, or document zip packages, release packages, local build artifacts, or their installation flow
- `next` draft releases are only next-version release-note drafts, not formal releases, and they do not include package assets

---

## 2. Pre-Release Checklist

1. Confirm that `addons/godot_dotnet_mcp/plugin.cfg`, all localized changelogs, all localized `v*` release-note source files, and the public docs all match
   - The changelog must record the full important change set relative to the previous released version, not only user-visible `Added`, `Changed`, or `Fixed` items. Important `Documentation` and `Internal` changes also belong in `docs/en/CHANGELOG.md`, `docs/zh-CN/变更日志.md`, `docs/ja/変更履歴.md`, and `docs/ko/변경-로그.md`, such as release note sources, README, docs, runbook updates, CI and harness behavior, policy checks, protocol facts, and validation coverage changes
   - A pure version metadata bump is not written to the changelog unless it also changes user-visible compatibility, installation, or release validation behavior. Internal issues introduced and fixed in the same version line are also not listed as separate changelog items
2. Confirm that the matching English, Simplified Chinese, Japanese, and Korean `v*` release-note source files exist, are persistent documentation files, and read like user-facing hand-written release stories. The workflow renders the GitHub Release body from the English release note, validates the English changelog version section, and appends the commit summary
3. Confirm that the `next` draft release has been refreshed into the formal release format and can be used as a preview of the GitHub Release body
4. Confirm that the PR only contains the current release scope and does not mix in other fixes or unmerged history
5. Confirm that the public docs only describe the plugin’s own installation, usage, release, and compatibility information
6. Run or confirm CI with:

```powershell
.\scripts\test_plugin_side_roslyn.ps1 -GodotPath "<Godot Editor Path>"
```

7. If `.github/workflows/**` changed, confirm that `lint-workflows` passes
8. If you are pushing a formal release tag, confirm that the tag uses `v*`, points to a commit reachable from `dev`, and matches `plugin.cfg`, all four localized changelogs, and all four localized `v*` release-note source files

## 3. Release Note Format

The formal GitHub Release body is generated by `scripts/render_release_notes.ps1` and keeps a two-layer structure:

1. The hand-written summary layer used for the GitHub Release body comes from `docs/en/process/release-notes/release-notes-v<version>.md`. It explains the release theme, key highlights, compatibility notes, and upgrade judgment. The Simplified Chinese, Japanese, and Korean release-note source files must stay persisted in their localized documentation trees and link across languages below the title and introduction
2. The automatic summary layer first validates the target version or `Unreleased` section in `docs/en/CHANGELOG.md`, then appends the recent commit summary. Release workflows also check that the other localized changelogs and release notes mention the same version

When writing the hand-written summary, follow these rules:

- Learn from the released `v1.0.1` emoji narrative structure: a second-level heading with an emoji, the version, and the user theme, one short user-facing theme paragraph, third-level sections grouped by user impact and each with an emoji, and a final compatibility, installation, or upgrade note with an emoji
- Only describe user-visible capabilities, editor experience, diagnostic quality, installation or upgrade impact, and compatibility changes. Do not restate commit lists, internal task lists, or PR content
- Do not write maintenance-flow, development-flow, or release-mechanics changes into the hand-written summary, such as GitHub Actions trigger UI, dry-run caches, PR or branch policy, CI splits, or tag-check implementation, unless those changes directly affect how users install or use the plugin
- The English, Simplified Chinese, Japanese, and Korean `v<plugin.cfg version>` release-note source files must exist, mention the current version, and remain in the localized docs trees. Only remove old-version notes after the plugin metadata moves to the new version and the new notes are added
- If a version line has just been created and has no real development content yet, first create an initialization template. The template may only say that the version line has been initialized and that the final release will be completed later with the real user-visible changes since the previous version. It must not invent features, fixes, or maintenance-flow changes
- Recommended template:

```markdown
## <emoji> Godot .NET MCP vX.Y.Z: <user-facing theme>

Godot .NET MCP `vX.Y.Z` is a <release type> for <target users>. It improves <user-facing outcome> while keeping <compatibility / installation / tool-surface expectation>.

### <emoji> <user impact area>

Explain what changed, why it matters to plugin users, and what behavior they can expect.

### ✅ Compatibility and Upgrade Notes

Explain Godot and .NET compatibility, supported installation paths, upgrade judgment, and any user-visible caveats.
```

Initialization template for a brand-new release line:

```markdown
## 🧩 Godot .NET MCP vX.Y.Z: Release Theme Not Yet Final

Godot .NET MCP `vX.Y.Z` has been initialized as the next release line. Before the final release, replace this draft text with the actual user-visible changes shipped since the previous release.

### ✨ Highlights Reserved For Real Changes

Add user-facing capabilities here once they exist.

### 🔧 Fixes Reserved For Real Changes

Add user-facing fixes here once they exist.

### ✅ Compatibility and Upgrade Notes

Confirm Godot and .NET compatibility, supported installation paths, upgrade judgment, and any user-visible caveats before release.
```

`draft-release-notes` refreshes the `next` draft release after `dev` updates. The formal release body is generated by `publish-release`; `publish-plugin` uses the same script only to validate tag-triggered release-note artifacts

## 4. Remote Release Flow

1. Create a release short branch from the latest `origin/dev`, for example `release/v1.0.1`
2. Finish the version, all localized changelogs, all localized `v*` release notes, and public-docs cleanup
3. Push the short branch and create a PR targeting `dev`
4. Wait for `validate-plugin-harness` and the related workflow checks to pass
5. Have the maintainer confirm and merge the PR on GitHub
6. Manually run or wait for `draft-release-notes` to refresh the `next` draft release, then check that the body matches the formal release format
7. Prefer manually triggering the `publish-release` workflow. In GitHub Actions, choose `dev` in `Use workflow from`, and keep `dry_run=true` first to validate the version, release notes, build, and harness checks
8. After the dry run passes and the release content looks correct, run `publish-release` again with `dry_run=false`. If the version and target commit have not changed, the workflow will reuse the successful dry-run record and skip the repeated build and harness checks. It will then create the new `v*` tag on the current `dev` commit, generate the formal GitHub Release, and remove the consumed `next` draft release
9. If you need extra tag validation, you can create and push a `v*` tag on the merged `dev`, or manually trigger `publish-plugin` from that `v*` tag ref. That path checks the tag version, release-note source files, reachability from `dev`, build, harness, and rendered release-note artifact; it is validation-only and does not create the formal GitHub Release
10. `publish-release` checks version consistency, all localized changelog and release-note source files, and existing releases before creating the formal GitHub Release from the English release note. `publish-plugin` performs the same source and tag validation for pushed tags or manual verification, but stops after validation and artifact upload

`publish-release` only performs the release finish-up. It does not commit version bumps, merge PRs, push `dev`, overwrite or delete formal tags, or produce or upload zip or package assets. If a matching tag already points at the target commit but the GitHub Release is missing, the workflow may reuse that tag to create the missing Release. If the tag points elsewhere or the GitHub Release already exists, the workflow fails and asks for a new version or manual handling

---

## 5. Failure Handling

- If CI fails, fix it on the short branch and push again. Do not edit `dev` directly
- If the release note is wrong, prefer editing the GitHub Release body. If the source doc or changelog is wrong, open a short branch and fix that instead
- If the tag is wrong, the maintainer decides whether to delete the remote tag. The Agent must not delete or rewrite release tags on its own
- If the `next` draft release content is wrong, first fix `docs/en/process/release-notes/release-notes-v*.md` or the changelog and then run `draft-release-notes` again. If a localized source is out of sync, fix the matching localized release note or changelog before release. If the rendering rule itself is wrong, fix the workflow or script through a short-branch PR
