# v1.4.0 Protocol Refactor Plan

Godot .NET MCP v1.4.0 follows a debt-reduction and protocol-purification line. The refactor aligns the public MCP surface with the MCP 2025-06-18 separation of responsibilities: context, state, and catalogs move to Resources; workflow guidance stays in Prompts; Tools narrow to entries that execute actions or computational workflows.

The target shape is a smaller canonical public tool surface, resource-first discovery, a single tool-catalog fact source, and layered test gates that can be sharded by speed, isolation, behavior, and migration status.

## Key Changes

- Add canonical resource URIs: `guides/index`, `guides/capabilities`, `guides/ui-automation`, `state/project/summary`, `state/editor`, `activity/status`, `activity/recent`, `activity/call/{id}`, `tools/catalog/exposed`, and `tools/catalog/visible`.
- Keep the six workflow prompts, but stop recommending `system_help` as the first discovery step. Clients should read guide resources or use `prompts/list` and `prompts/get`.
- Remove cognitive and duplicate public tools from `tools/list`: `system_help`, `system_tool_catalog`, and `system_tool_activity`. Legacy calls must return explicit replacement resource URIs.
- Collapse duplicated high-level tools: replace `system_scene_validate` and `system_scene_analyze` with `system_scene_inspect(action=validate|analyze|full)`; replace `system_plugin_reload` and `system_plugin_update` with `system_plugin_maintenance(action=reload|update|...)`; replace read-only `system_editor_log` usage with log and activity resources.
- Return `tools/list` to the standard MCP tool list: callable tools, schemas, annotations, and required `_meta` only. Full tree, group, atomic, and action presentation data belongs in catalog resources.
- Add `structuredContent` and optional `outputSchema` to tool results. Text JSON remains for client compatibility, while `structuredContent` becomes the canonical internal contract.
- Move read-only project file, scene, script, and resource text access to resource templates. Keep `system_project_files` for writes, moves, deletes, scans, reimports, and other actions instead of default read-context discovery.

## Implementation Plan

### 1. Test Guardrails First

- Add a contract case manifest with fixed fields: `name`, `layer`, `domain`, `behavior=current|migration|deprecation|removal_guard`, `speed=fast|headless|editor|release`, `isolation=pure|user_fs|stage_root|editor`, and `v1_4_disposition=keep|rewrite|delete|expires`.
- Replace hard-coded required contract case lists with manifest label selection.
- Reclassify old behavior tests into compatibility tests that must remain, migration-window tests, and removal guards that prevent old structures from returning.

### 2. Protocol Surface Purification

- Implement guide, state, activity, and catalog resources in `mcp_resources_service.gd`.
- Make existing project information, diagnostics, and tool catalog resources consume the same snapshot data.
- Update prompt text so the cognitive path is resource, then prompt, then canonical tool, then resource or activity verification.
- Update `mcp_tool_rpc_router.gd` and tool-list construction so public tools only include canonical action tools.
- Add contracts proving `resources/list`, `resources/read`, `prompts/get`, `tools/list`, and `tools/call` produce matching HTTP and stdio output.

### 3. Public Tool Debt Cleanup

- Remove redundant public tools: `system_help`, `system_tool_catalog`, `system_tool_activity`, `system_scene_validate`, `system_scene_analyze`, `system_plugin_reload`, `system_plugin_update`, and `system_editor_log`.
- Remove old internal aliases: `filesystem_file`, `debug_log`, and `resource_manage`.
- Replace all internal references before removal.
- Upgrade tests from "not exposed" checks to "not callable" and "not present in visible catalog" guards.
- Keep required safety and migration layers: protocol-facts fallback, runtime fallback event store, legacy user-data cleanup, `trace` to `debug` normalization, old user-tool settings key migration, and client config read migration.

### 4. Tool Catalog Refactor

- Add a single `ToolCatalogManifest` for category, domain key, executor path, source, exposure, hot-reloadability, and presentation order.
- Keep `MCPToolManifest` and `MCPToolRegistry` as adapters only until duplicate fact sources can be removed.
- Add `ToolCatalogSnapshotService` to generate exposed, visible, and all-tool sets; domain states; presentation trees; and search indexes in one pass.
- Make RPC, Tools API, Dock, and catalog resources consume the same snapshot.
- Demote `atomic_bridge` to an `AtomicToolFacade` that keeps write guards and helpers but delegates execution through unified internal execution instead of maintaining a second executor-path map.
- Merge each system implementation's schema, handler, and atomic dependencies into declarative specs, then derive `SystemTreeCatalog` from those specs.

### 5. Old Monolith Removal

- For each domain that already has `tools/<domain>/executor.gd`, migrate and delete the root-level `tools/<domain>_tools.gd` monolith.
- Do not remove `base_tools.gd` or real shared helpers.
- Final contracts should assert the old monolith files do not exist instead of saying they should be removed after split executors are complete.
- Prioritize domains already named by contracts: audio, animation, signal, tilemap, and UI. Then continue with filesystem, debug, resource, node, project, scene, and other larger domains.

### 6. Internal Service Convergence

- Split `MCPToolLoader` into a runtime facade, definition catalog, execution service, visibility policy, and activity recorder, while keeping external adapters until every caller is migrated.
- Make HTTP and stdio share the same JSON-RPC method router, tool router, result normalization, and resources/prompts dispatch path.
- Collapse tiny callable context bags into service graph or ports objects.
- Slim `plugin.gd` down to EditorPlugin lifecycle and service wiring. Move update behavior, user tools, diagnostics, Dock models, and configuration actions into dedicated feature services.

## Test Plan

- Fast static gates: .NET build, manifest lint, refactor guardrails, version policy, docs i18n, and workflow lint.
- Headless smoke gates: resource-first MCP contracts, canonical `tools/list`, `tools/call` `structuredContent`, removal guards, and tool snapshot parity.
- Headless integration gates: domain-sharded runtime, resources/prompts/tools, client config migration, user tools, localization, and transport parity.
- Editor probes: plugin entrypoint, settings persistence, real editor-only lifecycle, UI evidence, settings, and inspector workflows.
- Migration and deprecation gates: old user-tool naming, old client config, old stdio config, and old C# reference path-first behavior should verify migration diagnostics instead of permanently protecting old implementations.
- Release preflight: full harness, clean install build, release-note rendering, changelog/i18n, and version/tag boundary validation.

## Assumptions

- v1.4.0 allows breaking cleanup, focused on public tool-name convergence and old internal alias removal.
- Limited Resources or Prompts support in some clients does not decide the protocol surface. The plugin follows the MCP specification while returning clear errors and replacement URIs.
- `script_references` legacy path-first behavior remains until a dedicated C# reference-system task is opened. This plan only marks related tests as migration or deprecation candidates.
- Each PR handles one refactor axis: test guardrails, protocol surface, public tool cleanup, manifest/snapshot, monolith removal, loader/atomic convergence, or plugin slimming.
