# v2.0.0 UI Information Design Plan

## Summary

The v2.0.0 protocol work narrows the public MCP tool surface to canonical `system_*` and `user_*` entries while the implementation still keeps many internal executor categories. The Dock must make that split visible: default pages should show what an Agent or user should call, while deeper views explain composition and operational health without mixing every executor into the same ordinary tool tree.

This plan covers the Tools, Resources, and Prompts pages. It is a design target for staged PRs, not a release note.


## Tools Page

The Tools page should default to an Agent Tools view. That view answers: what can I call?

Default groups:

```text
Agent Tools
├─ Project & Context
├─ Editor Automation
├─ Scene & Resource
├─ Script & C# Semantics
├─ Runtime & Debugging
├─ Plugin Maintenance
└─ User Tools
```

Rules:

- Show canonical public tools and user tools by default.
- Do not show internal executor categories in the default tree.
- Do not show removed or legacy tools as normal tools.
- Do not show resource or prompt discovery entries as normal callable tools.
- Count only default-visible public tools in the default total.
- Use cross-links such as implemented by executor instead of duplicate nodes.

The default Agent Tools view should use the following canonical grouping targets:

```text

```

The Tools page should also support two deeper views:

- Structure view: shows actions, inputs, outputs, data sources, services, and internal executors behind a selected public tool.
- Diagnostics view: shows exposure, callability, source file, manifest entry, policy decision, load status, schema status, recent activity, and replacement guidance.

Structure view answers: what is this tool made from? Nodes in this view must be explicitly labeled as tool, action, input, output, data source, service, or executor. Non-tool nodes must never show run-style affordances. A typical structure row should look like:

```text

│  └─ plugin self diagnostics
├─ Internal Executors
│  ├─ project
│  ├─ filesystem
│  └─ runtime
└─ Output
   ├─ summary
   ├─ project
   ├─ files
   ├─ runtime
   └─ health
```

Diagnostics view answers: why is this entry visible, hidden, callable, blocked, or removed? A diagnostic row should expose the exact decision inputs:

Removed legacy entries must appear only in diagnostics, with replacement guidance:

```text

├─ callable: compatibility guidance only
├─ replacement resource: godot-dotnet-mcp://guides/index

```

```text

├─ core

├─ interface
├─ plugin
└─ user
```

Each internal executor row should show loaded state, enabled tool count, total tool count, source path, load errors, reload status, hot reload status, public tools produced, and internal tools produced.

If one capability is related to several nodes, use cross-links rather than duplicate rows. For example, `system_dap_debugger` belongs to Runtime & Debugging and links to the `dap` executor as its implementation detail; `dap` must not also appear as a peer ordinary tool in the default tree.

## Resources Page

The Resources page should default to a Resource Catalog view. That view answers: what can I read?

Default groups:

```text
Resources
├─ Guides
├─ Project State
├─ Editor State
├─ Activity & Logs
├─ Tool Catalog
├─ Resource Templates
└─ Advanced Resources
```

Rules:

- Show canonical resource URIs and templates from `resources/list` and `resources/templates/list`.
- Display title, description, icons, MIME type, template parameters, and stable URI.
- Keep tool-like actions out of the default resource tree; link to related tools instead.
- Do not classify resources by URI substring in the Dock when `_meta.resourceKind` or equivalent catalog metadata exists.
- Treat templates as reusable read targets, not callable tools.

The Resources page should include:

- Reader view: preview the selected resource content, MIME type, metadata, and copy URI action.
- Template view: show template parameters, examples, validation hints, and copy expanded URI action.
- Diagnostics view: show source service, resource kind, visibility, last read status, content size, template binding errors, stale cache status, and fallback guidance.

Protocol and safety rules:

- Treat `resources/list`, `resources/templates/list`, and `resources/read` as the source of truth for page content, previews, and error behavior.
- Preserve the existing redaction behavior for logs and diagnostics.
- Preserve template path validation, traversal rejection, absolute/user path rejection, binary rejection, and oversized content handling.
- Label compatibility resources as compatibility entries instead of promoting them above canonical resources.

Resource acceptance checks:

- Guides, state, activity, logs, catalog, and templates appear once in the default catalog.
- Template entries are not counted as tools.
- Resource kind comes from shared metadata, not Dock-side string guessing.
- Resource preview handles large content, empty content, unsupported MIME types, and read errors without visual overlap.
- Diagnostics can explain missing, hidden, or failed resource reads.
- Resource preview semantics remain equivalent to `resources/read(uri)`.

## Prompts Page

The Prompts page should default to a Prompt Catalog view. That view answers: what workflow guidance can I request?

Default groups:

```text
Prompts
├─ Project Understanding
├─ Editor Workflow
├─ Runtime Validation
├─ Script & C# Workflow
├─ Plugin Maintenance
└─ Advanced Prompts
```

Rules:

- Show prompts from `prompts/list` with title, description, icons, arguments, and stable name.
- Keep prompt entries separate from tools and resources.
- Show prompt arguments as arguments, not as child tools.
- Do not infer prompt kind from name substrings when metadata is available.
- Make required, optional, enum, bool, and path-like arguments visually distinct.

The Prompts page should include:

- Prompt builder view: argument editors, validation hints, preview request, and copy prompt name.
- Message preview view: rendered messages, roles, text content, and resource/tool links.
- Diagnostics view: prompt source, prompt kind, argument schema, unknown-argument policy, type validation status, last render error, and related resources/tools.

Protocol and safety rules:

- Treat `prompts/list` and `prompts/get` as the source of truth for page content, previews, and error behavior.
- Preserve prompt unknown-argument and wrong-type validation semantics.
- Preserve truncation metadata and any localized title, description, and argument text supplied by the prompt service.
- Keep prompt preview semantics equivalent to `prompts/get(name, arguments)`.

Prompt acceptance checks:

- Workflow prompts appear once in the default catalog.
- Arguments do not resize the layout or overlap labels on narrow panels.
- Unknown and wrong-type arguments are shown as validation concerns.
- Rendered messages keep roles and content clear.
- Diagnostics can explain prompt visibility, argument validation, and render failures.

## Shared Interaction Rules

Use a shared mode switch where a page has multiple depths:

```text
Default
Structure
Diagnostics
Advanced
```

Search is shared across views, but every result must include a type badge:

```text
Public
Internal
Legacy
Removed
Disabled
Error
Resource
Template
Prompt
Argument
```

Preview panels should use stable dimensions and compact labels. Buttons use icons when available, with tooltips for unfamiliar actions. Disabled or non-callable nodes must not show run-style actions.

## PR Plan

### PR 1: Plan and Model Contract

- Store this plan in the docs tree.
- Add presentation model contracts for Tools, Resources, and Prompts.
- Keep UI changes minimal.

### PR 2: Agent Tools Default View

- Switch the Tools tab default tree to canonical public tools plus user tools.
- Move executor categories to an advanced or diagnostics path.
- Fix default counts and duplicate DAP/runtime/project-style rows.

### PR 3: Resources and Prompts Default Views

- Make Resources and Prompts consume explicit presentation models.
- Add stable previews, argument/template panels, and metadata badges.
- Remove private Dock classification guesses where shared metadata exists.

### PR 4: Structure and Diagnostics Views

- Add deeper views for Tools, Resources, and Prompts.
- Show exposure, callability, data source, validation, activity, replacement, and load/read/render status.
- Add filters for errors, hidden entries, legacy entries, internal entries, and disabled entries.

### PR 5: Visual Verification and Polish

- Validate desktop and narrow-panel rendering.
- Confirm labels, buttons, previews, schemas, and badges do not overlap.
- Capture visual evidence for Tools, Resources, and Prompts.

## Acceptance Criteria

- The default Tools page shows canonical callable tools once and excludes internal executor categories from default counts.
- DAP, runtime, project, scene, and resource capabilities do not appear twice as equal top-level ordinary tools.
- Removed legacy tools are absent from Agent Tools but visible in diagnostics with replacement guidance.
- The Resources page shows resource entries and templates once, with metadata-driven kinds and safe previews.
- The Prompts page shows prompts once, with argument editors and message preview separated from tools.
- Structure and diagnostics views make non-callable nodes visibly non-callable.
- Every view can explain why an entry is visible, hidden, disabled, removed, or failing.
- Visual verification covers Tools, Resources, and Prompts after implementation PRs.
