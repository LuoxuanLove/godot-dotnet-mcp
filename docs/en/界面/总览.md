# UI Overview

This document explains the relationship between the scenes and scripts under `ui/`, and how the Dock root scene distributes a shared model to the `Home`, `Tools`, `Config`, and `Settings` tabs.

---

## UI File Layout

The current `ui/` directory is made of these files:

| Path | Purpose |
|---|---|
| `ui/mcp_dock.tscn` | Dock root scene |
| `ui/mcp_dock.gd` | Dock root controller |
| `ui/server_panel.tscn` | `Home` tab scene, keeping the original `server` file name |
| `ui/server_tab.gd` | `Home` tab controller |
| `ui/server_tab_model_projection.gd` | Pure projection collaborator for the `Home` tab |
| `ui/tools_tab.tscn` | `Tools` tab scene |
| `ui/tools_tab.gd` | `Tools` tab controller |
| `ui/config_panel.tscn` | `Config` tab scene |
| `ui/config_tab.gd` | `Config` tab controller |
| `ui/settings_panel.tscn` | `Settings` tab scene |
| `ui/settings_tab.gd` | `Settings` tab controller |
| `ui/settings_tab_model_projection.gd` | Pure projection collaborator for the `Settings` tab |

---

## Root Scene Responsibilities

`mcp_dock.tscn` is responsible for:

- the title bar
- the status light
- the current running-state text
- the `TabContainer`
- the scene host for the tab instances

`mcp_dock.gd` is responsible for:

- instantiating the four tab scenes
- connecting the signals emitted by each tab controller
- receiving the shared model from `plugin.gd`
- setting the tab titles, localized text, and root-level status light
- handling host Dock tab switching and focus restore

---

## Root Controller Data Flow

The Dock currently uses one-way data flow:

```text
plugin.gd
  -> build and publish the Dock model
  -> mcp_dock.gd.apply_model(model)
  -> server_tab.gd / tools_tab.gd / config_tab.gd / settings_tab.gd
  -> server_tab_model_projection.gd / settings_tab_model_projection.gd (pure projection inside each tab)
  -> user action signal
  -> plugin.gd
```

Advantages:

- the UI layer does not read or write the server or settings directly
- every tab works from the same model
- language switching, scaling, and state refresh can redraw together

## Signal Bridging

The signals currently bridged by `mcp_dock.gd` are roughly divided into four groups:

### Service Control

- `port_changed`
- `auto_start_toggled`
- `log_level_changed`
- `permission_level_changed`
- `language_changed`
- `start_requested`
- `restart_requested`
- `stop_requested`
- `full_reload_requested`

### Tools Tab Actions

- `delete_user_tool_requested`
- `tool_toggled`
- `category_toggled`
- `domain_toggled`
- `tree_collapse_changed`

### Config Tab Actions

- `cli_scope_changed`
- `config_platform_changed`
- `config_write_requested`
- `copy_requested`

### Settings Tab Actions

- `port_changed`
- `log_level_changed`
- `language_changed`
- `update_source_changed`
- `update_custom_branch_changed`
- `update_check_requested`
- `update_apply_requested`

All of these signals flow back into `plugin.gd`, which then calls the service objects.

## Tab Instantiation

`mcp_dock.gd` does the following in `_ensure_tabs()`:

1. Clear the current children under `TabContainer`
2. Load and instantiate the following scenes in order:
   - `server_panel.tscn` as the `Home` tab
   - `tools_tab.tscn`
   - `config_panel.tscn`
   - `settings_panel.tscn`
3. Check whether the tab controllers implement `apply_model()`

The direct effect is:

- each tab can maintain its own node tree
- the entry script does not need to know the inner controls of each tab
- adding a new tab later only needs a new scene, a controller, and root-scene wiring

## Scaling and Layout Strategy

UI scaling still uses `EditorInterface.get_editor_scale()` as the single source of truth, but the implementation now separates two kinds of layout parameters:

### Still Controlled by Script at Runtime

- control minimum height
- tool-tree column width
- minimum height of dynamically generated card content
- shadow size

### Preferably Controlled by the Scene

- `MarginContainer` margins
- `VBoxContainer`, `HBoxContainer`, and `GridContainer` spacing
- separator placement
- `VSplitContainer` split layout

This means the tab scripts only keep the scaling-related hard constraints, while normal UI spacing should be tuned in the `.tscn` files first.

---

## Current Maintenance Rules for the UI Directory

- tab controllers only handle the display and interaction for their own tab
- the Dock root controller handles cross-tab coordination and signal forwarding
- scene control names should stay semantically clear, preferably using `XxxPanel`, `XxxMargin`, `XxxSeparator`, and `XxxContent`
- avoid overriding ordinary margins or separation in scripts unless it is necessary
