## 🧩 Godot .NET MCP v1.2.1：可验证的编辑器 UI 自动化

该版本线改进编辑器 UI 自动化体验，让客户端能在继续下一步之前等待 Godot 编辑器里的可见状态。Agent 可以通过既有编辑器控件执行动作，然后验证期望的界面条件是否真正出现。

### ✨ 等待真实 UI 状态

`system_editor_control` 现在包含 `wait_for_ui`，可在有界时间内轮询控件存在、可见性、文本匹配以及启用 / 禁用状态。等待成功会返回匹配控件摘要与耗时信息；超时会返回最后一次观测负载，方便客户端调整定位条件或下一步动作。

### 🔧 更安全的自动化循环

新的等待动作与菜单、弹窗、点击、hover 和文本输入控制能力互补，不需要 OS 鼠标自动化。打开编辑器对话框、过滤设置、确认临时面板等流程可以在 Godot 内部得到更可靠的验证。

编辑器 UI 指引现在明确自动化顺序：优先使用语义工作流和导航，其次使用控件级聚焦、文本、数值与弹窗动作，仅在 fallback 场景中使用控件本地鼠标或指针事件。Agent 可以先选择更高层路径，再考虑坐标。

Resource 与 prompt 诊断现在会在上报 resource 输出前遮蔽大小写混合的 URL credential、bearer / API-key 变体以及嵌套 metadata secret。故障排查证据仍然可用于自动化循环，同时不会在摘要里暴露凭据。

### 🪟 浮动窗口证据

`system_editor_control` 现在可通过 `get_popup` 与 `capture_popup` 读取并截取可见浮动弹窗 / 窗口界面。客户端在选择按钮、菜单项、文本输入框或关闭动作前，可以直接取得 modal 编辑器窗口与 PopupMenu 的证据。

`system_settings_dialog` 在捕获设置界面时会自动使用这条证据路径。如果当前 Project Settings 或 Editor Settings 工作流能观测到对应弹窗或编辑器窗口，截图结果会标明所选 backend 与目标路径；只有在更窄的界面边界不可用时，才回退到整编辑器截图。

### 🧭 配置导航与证据

`system_settings_dialog` 新增面向 Project Settings 与 Editor Settings 的高层工作流。客户端可以通过编辑器菜单打开设置界面，等待对话框可见，搜索候选设置行，聚焦返回结果，截图保留证据，并在不直接写入设置值的前提下关闭界面。

该工作流还通过 `list_rows` 暴露只读设置行模型，用保守置信度和证据字段描述可见设置类控件，随后可按需读取、写入或断言值。

它还可以通过 `list_tabs` 和 `activate_tab` 列出并激活设置标签页，并支持 `open(tab=...)`，让客户端无需坐标点击即可在 Project Settings 或 Editor Settings 标签页之间移动。

该设置工作流可以列出可见分类树项，并在检查设置行之前聚焦唯一分类，让 Project Settings 与 Editor Settings 导航更少依赖原始控件枚举。

它还可以通过 `read_value` 读取唯一匹配的可见设置行当前值，返回带行和值控件证据的 text、bool、number 或 enum 类型化结果，同时仍避免直接写入设置。

项目配置证据现在也覆盖输入映射：Agent 可以通过 `system_project_configure` 读取单个项目输入动作，查看 deadzone 以及具体键盘、鼠标或手柄绑定。这让输入映射审查可以先基于真实项目配置，再决定是否修改游戏或编辑器快捷键。

项目配置现在也可以通过 `system_project_configure(action="list_export_presets")` 列出导出预设。响应会摘要预设名称、平台、runnable 状态、过滤器、脚本导出模式和导出路径形态，同时遮蔽敏感 option key 与本机绝对导出路径。

客户端现在还可以通过 `resolve_row` 在读取值或选择后续 UI 动作前解析唯一可见设置行。响应会携带行路径、置信度、选择器证据和歧义诊断，同时保持只读。

当 Agent 只需要把键盘焦点移动到匹配的值编辑控件时，`focus_value` 会聚焦该值控件并返回聚焦证据，不会修改设置。

受支持的唯一可见设置行现在还可以通过 `set_value` 编辑 text、number 与 bool 控件。该流程会通过编辑器 UI 控件写入，并在操作后重新观测设置行，让客户端验证实际值已经变化，而不是假设点击或文本编辑成功。

`run_task` 现在把这条设置链路封装为一个可信操作。它可以打开并缩小设置界面、解析唯一设置行、读取修改前值、按需写入受支持的值、验证预期结果并附带截图证据。若选择器存在歧义、请求隐藏控件写入、置信度过低，或要求截图但无法在改值前生成证据，写入会在交互前被拒绝。

Agent 也可以使用只读 `verify_value` 检查，将预期的 text、bool、number 或 enum 值与唯一匹配的可见设置行进行比较。这样设置工作流可以在 UI 动作之前或之后加入不改变设置值的断言步骤。

### 🔎 可搜索的工具发现

`system_tool_catalog` 为当前工具目录提供只读搜索入口。客户端可以按关键词、分类或域搜索，并查看每个工具为什么匹配、公开了哪些动作和参数、当前是否可见以及是否启用。

这让配置和编辑器工作流在 profile、plugin 域工具或 user 工具状态变化后更容易重新进入：Agent 可以先重新发现合适的 system、project、editor、runtime、script 或用户侧工具，再选择下一步可验证动作。

原生 MCP 发现现在也会本地化 resource 与 resource template metadata。当客户端调用 `resources/list` 或 `resources/templates/list` 时，resource 名称和说明会跟随当前插件语言，而 URI 与 template 仍保持稳定。


### 🧭 项目运行时生命周期

项目运行控制现在使用 `system_project_lifecycle(action=start|stop)` 作为规范高层入口。启动、marker 验证、自动停止、显式停止、前台窗口 fallback 指引和运行时能力上下文都收敛到同一个生命周期表面，而不是分散在单独的运行与停止工具名里。

此前调用旧项目运行或停止工具名的客户端应迁移到 `system_project_lifecycle(action=start)` 和 `system_project_lifecycle(action=stop)`。生命周期命名让编辑器自动化流程更像可控的运行时会话，而不是一次性的启动命令。

### ✅ Compatibility and Upgrade Notes

项目运行控制表面现在使用 `system_project_lifecycle(action=start|stop)`。使用旧项目运行或停止工具名的客户端应迁移到生命周期入口；现有编辑器、设置与项目配置工作流仍保持可用。
