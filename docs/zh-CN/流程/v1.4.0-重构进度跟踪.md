# v1.4.0 重构进度跟踪

本文将 v1.4.0 协议重构计划拆成可执行检查清单。每一项都应能对应到可审查、可验证并合入 v1.4 重构分支的 PR。

状态说明：

- `Done`：已实现、验证、审查，并合入 v1.4 重构分支。
- `Partial`：已有有效进展，但仍有必须补完的后续工作。
- `Pending`：尚无实质实现。
- `Blocked`：存在明确外部前置条件。

## 当前阶段

v1.4.0 已完成初始护栏，并进入协议面准备中段。当前重构目标已经切换为默认符合 MCP 2025-11-25，旧 2025-06-18 对齐成果保留为兼容基础。当前分支已有测试脚手架和多项 MCP 协议改进，但尚未完成 2025-11-25 transport/schema/metadata 门禁、破坏性公开工具清债、单一工具目录事实源、旧 monolith 删除和内部服务收敛。

## 下一批 PR 队列

1. 新增 MCP 2025-11-25 conformance gate taxonomy，以及 protocol-version/schema/tool-name metadata contracts。
2. 将 `http://127.0.0.1:3000/mcp` 定义为默认 Streamable HTTP endpoint，并补 version/session/Accept/SSE/Origin contracts。
3. 将 newline-delimited stdio 作为默认模式，`Content-Length` 仅保留为显式 legacy compatibility。
4. 为 Resources、Resource Templates、Prompts、Tools 补 2025-11-25 icons/title/description/schema metadata。
5. 将 Dock / Tools UI 模型改为从共享 catalog snapshot metadata 渲染，不再维护私有 tree facts。
6. 将剩余 Dock 与 Tools/RPC catalog 消费方迁到 `ToolCatalogManifest` / `ToolCatalogSnapshotService`。
7. 继续清理 debug、resource、node、project、scene 等更大的 monolith domain。
8. 将 `atomic_bridge` 降级到统一内部执行 facade 之后。
9. 在 snapshot service 稳定后拆分 `MCPToolLoader` 职责。
10. catalog 消费方共享 manifest/snapshot 路径后，继续推进内部服务收敛。

## 跟踪规则

- 每个 breaking removal 必须在错误中返回 replacement method 或 resource URI。
- 每个删除的公开工具必须有测试证明它不在 `tools/list`、不在 visible catalog resource，并且不能作为成功动作调用。
- Prompt 指引必须描述 resource-first 路径，不得把已删除 discovery tool 作为起点。
- v1.4 默认 endpoint 是作为 MCP Streamable HTTP 的 `http://127.0.0.1:3000/mcp`；legacy `/api/tools`、`/health`、JSON-only POST 行为和 `Content-Length` stdio 必须标为兼容面。
- UI catalog 模型必须消费共享 catalog snapshot metadata，不得另造私有目录事实。
- Changelog 必须保持 `Added / Changed / Fixed / Documentation / Internal` 顺序，且同一版本不得重复 section。
- PR 合入 v1.4 重构分支前，必须完成本地验证、相关 GitHub 检查、所有 conversation 和 Codex review gate。
