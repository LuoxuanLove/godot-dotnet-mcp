# 发布 Runbook

本文档记录 Godot .NET MCP 的发布前检查与远程发布流程。它只描述插件自身发布。

---

## 1. 发布原则

- `dev` 是稳定集成分支；发布前所有变更必须先通过短分支 PR 合入 `dev`。
- 普通 `feature/*`、`fix/*`、`docs/*`、`chore/*`、`hotfix/*` PR 必须保持插件公开版本元数据与 `dev` 一致；只有指向 `dev` 的 `release/*` PR 可以修改该版本。
- 发布由维护者手动触发或推送 `v*` tag 触发，Agent 不直接合并或推送 `dev`。
- 发布安装方式只保留 Godot Asset Library 安装和直接复制 `addons/godot_dotnet_mcp/` 源文件两种路径。
- 不制作、上传或记录 zip 包、发布包、本地打包产物及其安装流程。
- `next` draft release 仅作为下一版发布说明草稿，不是正式发布，也不附带包资产。

---

## 2. 发布前检查

1. 确认 `addons/godot_dotnet_mcp/plugin.cfg` 版本、四种语言 changelog、四种语言 `v*` 发布说明源文件和公开文档一致。
   - Changelog 必须记录目标版本相对上一已发布版本的完整重要变化，不只记录用户可见的 `Added` / `Changed` / `Fixed`。重要的 `Documentation` 与 `Internal` 变化也必须维护到 `docs/en/CHANGELOG.md`、`docs/ko/변경-로그.md`、`docs/ja/変更履歴.md` 与 `docs/zh-CN/变更日志.md`，例如 release note 源文件、README / docs / i18n / Runbook 更新、CI / harness / workflow 行为、policy 检查、protocol facts 和验证覆盖变化。
   - 纯版本元数据切换本身不写入 changelog，除非它同时改变用户可见兼容性、安装方式或发布验证行为；开发过程中引入后又在同一版本线内修复的内部问题也不作为独立 changelog 条目。
2. 确认对应版本的英文、简体中文、日文与韩文 `v*` 发布说明源文件都存在，作为持久化文档保留，且内容为面向用户的手写发布叙事；workflow 会使用英文发布说明渲染 GitHub Release 正文，校验英文 changelog 版本段落并追加 commit summary。
3. 确认 `next` draft release 已按正式发布格式刷新，并可作为正式 GitHub Release 正文预览。
4. 确认 PR 只包含当前发布目标范围，未夹带其它修复或历史未合并提交。
5. 确认公开文档只描述插件自身的安装、使用、发布与兼容性信息。
6. 运行或确认 CI 已通过：

```powershell
.\scripts\test_plugin_side_roslyn.ps1 -GodotPath "<Godot Editor Path>"
```

7. 如修改了 `.github/workflows/**`，确认 `lint-workflows` 通过。
8. 如推送正式发布 tag，确认 tag 使用 `v*`，tag 指向可从 `dev` 到达的提交，且 tag 版本与 `plugin.cfg`、四语 changelog 和四语 `v*` 发布说明源文件一致。

---

## 3. 发布说明格式

正式 GitHub Release 正文由 `scripts/render_release_notes.ps1` 生成，保持两层结构：

1. GitHub Release 使用的手写摘要层来自 `docs/en/process/release-notes/release-notes-v<version>.md`，用于说明版本主题、关键亮点、兼容性提示和升级判断。简体中文、日文和韩文发布说明源文件必须继续保留在各自本地化文档树中，并在标题与简介后提供跨语言链接。
2. 自动摘要层：workflow 先校验 `docs/en/CHANGELOG.md` 中的目标版本或 `Unreleased` 段落，再追加最近 commit summary；发布 workflow 也会检查其他三种语言 changelog 与发布说明是否提到同一版本。

编写手写摘要时应遵循：

- 学习已发布 `v1.0.1` 的 emoji 叙事结构：带 emoji、版本和用户主题的二级标题，一段用户可理解的版本主题说明，按用户影响划分且每项都带 emoji 的三级章节，以及最后带 emoji 的兼容性 / 安装 / 升级提示。
- 只描述用户可感知的插件能力、编辑器体验、诊断质量、安装 / 升级影响与兼容性变化，不复述 commit 列表、内部任务列表或 PR 内容。
- 不把维护流程、开发流程或发布机械变化写入手写摘要，例如 GitHub Actions 触发界面、dry-run 缓存、PR / branch policy、CI 内部拆分、tag 校验实现等；除非这些变化本身直接改变最终用户安装或使用插件的方式。
- 当前 `plugin.cfg` 版本对应的英文、简体中文、日文和韩文发布说明源文件都必须存在、提到该版本，并保留在本地化文档树中；只有在插件元数据切换到新版本并新增对应 note 后，才清理旧版本源文件。
- 版本刚切换但尚无实际开发内容时，先创建可后续补全的初始化模板；模板只能说明版本线已初始化，正式发布前将按相对上一版本的实际用户可见变更补全，不得提前编造功能、修复或维护流程。
- 推荐模板：

```markdown
## <emoji> Godot .NET MCP vX.Y.Z: <用户可感知主题>

Godot .NET MCP `vX.Y.Z` is a <release type> for <target users>. It improves <user-facing outcome> while keeping <compatibility / installation / tool-surface expectation>.

### <emoji> <用户影响领域>

Explain what changed, why it matters to plugin users, and what behavior they can expect.

### ✅ Compatibility and Upgrade Notes

Explain Godot/.NET compatibility, supported installation paths, upgrade judgment, and any user-visible caveats.
```

版本刚切换后的初始化模板：

```markdown
## 🧩 Godot .NET MCP vX.Y.Z: 发布主题尚未最终确定

Godot .NET MCP `vX.Y.Z` 已初始化为下一条版本线。正式发布前，应将这段草稿文字替换为相对上一版本实际交付的用户可见变更。

### ✨ 预留给真实变更的亮点

当真实用户可见能力存在后，在此补充。

### 🔧 预留给真实变更的修复

当真实用户可见修复存在后，在此补充。

### ✅ 兼容性与升级提示

发布前确认 Godot / .NET 兼容性、支持的安装路径、升级判断以及任何用户可见注意事项。
```

`draft-release-notes` 会在 `dev` 更新后用同一脚本刷新 `next` draft release；正式发布正文由 `publish-release` 生成，`publish-plugin` 只在 tag 触发验证时用同一脚本生成发布说明 artifact。

## 4. 远程发布流程

1. 从最新 `origin/dev` 创建发布短分支，例如 `release/v1.0.1`。
2. 完成版本、四语变更记录、四语 `v*` 发布说明和公开文档收口。
3. 推送短分支并创建指向 `dev` 的 PR。
4. 等待 `validate-plugin-harness` 和相关 workflow 检查通过。
5. 由维护者在 GitHub PR 页面手动确认并合并。
6. 手动运行或等待 `draft-release-notes` 刷新 `next` draft release，并检查正文是否符合正式发布格式。
7. 优先手动触发 `publish-release` workflow，在 GitHub Actions 的 `Use workflow from` 中选择 `dev`，先保持 `dry_run=true` 验证版本、tag、发布说明和构建检查。
8. dry run 通过并确认发布内容后，重新运行 `publish-release`，将 `dry_run` 设为 `false`；如果版本与目标提交未变，workflow 会复用成功 dry-run 记录并跳过重复 build 与 harness 检查，然后在 `dev` 当前提交上创建新的 `v*` tag，生成正式 GitHub Release，并删除已消费的 `next` draft release。
9. 如需额外验证 tag，可在合并后的 `dev` 上创建并推送 `v*` tag，或从该 `v*` tag ref 手动触发 `publish-plugin` workflow；该路径会确认 tag 版本、发布说明源文件、`dev` 可达性、构建、harness 和渲染出的发布说明 artifact，但只做验证，不创建正式 GitHub Release。
10. `publish-release` 会在创建正式 GitHub Release 前检查版本一致性、四语 changelog、四语发布说明源文件和已存在 release，并使用英文发布说明生成正式正文。`publish-plugin` 对推送 tag 或手动验证执行同类源文件与 tag 检查，但在验证和 artifact 上传后结束。

`publish-release` 只执行发布收尾：不会提交版本号变更、不会合并 PR、不会推送 `dev`、不会覆盖或删除正式 tag，也不会制作或上传 zip / package 资产。若匹配 tag 已指向目标提交但 GitHub Release 缺失，workflow 可复用该 tag 补建 Release；若 tag 指向其他提交或 GitHub Release 已存在，workflow 会失败并要求选择新版本或人工处理。

---

## 5. 失败处理

- CI 失败时，修复应回到短分支并重新推送，不直接修改 `dev`。
- 发布说明错误时，优先编辑 GitHub Release 正文；如果源文档或 changelog 错误，再开短分支修正。
- tag 错误时，由维护者决定是否删除远程 tag；Agent 不擅自删除或重写发布 tag。
- `next` draft release 内容错误时，优先修正英文发布说明或英文 changelog 后重新运行 `draft-release-notes`；如本地化源不同步，发布前修正对应语言的发布说明或 changelog。如渲染规则本身错误，应通过短分支 PR 修改 workflow 或脚本。
