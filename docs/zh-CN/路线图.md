# 路线图


本文档描述 Godot .NET MCP 的产品方向。它是规划文档，不是发布承诺，也不能替代 issue 级设计。随着实现约束、测试结果和用户反馈逐步清晰，版本范围可能调整。

## 产品定位

Godot .NET MCP 是面向 Godot 4.6+ .NET 项目的编辑器原生 MCP 插件。它在 1.x 的身份保持为：

- MCP 服务直接运行在 Godot 编辑器内部；
- 提供实时编辑器、项目、场景、运行时、诊断、截图、C# 结构、资源和工具扩展上下文；
- 对外暴露高层 `system_*` 工作流，而不是让 Agent 面对过多低层原子工具；
- 保持设置直接，并避免核心插件体验依赖额外常驻后台服务；
- 让 Agent 的工作能通过诊断、运行时证据和编辑器状态验证，而不只是完成文件编辑。

本项目不应以原始工具数量竞争，而应以语义质量、setup-aware 指引、C#/.NET 项目理解、编辑器状态准确性、运行时验证和稳定公开 MCP surface 竞争。

## v1.x 开发方向

1.x 线应在持续完善编辑器原生插件架构的同时，让 Godot .NET MCP 成为面向 Agent 的证据优先工作流平台。优先目标是帮助 Agent 发现正确能力、完成聚焦修改、通过 Godot 验证修改，并报告可信证据。

### 能力发现与工具治理

- 强化 `system_help` 与工具目录资源，使 Agent 能按任务选择工具，而不是从大型扁平列表中猜测。
- 让工具组和 profile 更清晰，包括 core、runtime、DAP、editor UI、visual、plugin 和 user-extension 能力。
- 暴露 setup-gated 状态，例如项目未运行、runtime control 不可用、DAP endpoint 不可用、需要编辑器前台或缺少用户工具。
- 保持高层 `system_*` 入口作为公开工作流层，同时将低层 executor 保留为内部实现细节。
- 将公开工具名、参数、返回字段和 protocol facts 视为 1.x 工作流的稳定 API surface。

### 闭环运行验证

- 将现有 project run、runtime control、runtime step、截图、editor log 和 runtime diagnosis 工具组织成更清晰的验证工作流。
- 支持证据导向的报告，说明运行了什么、匹配了哪些 marker、捕获了哪些截图或运行时状态、是否出现错误以及是否完成清理。
- 避免把成功启动误认为行为验证通过；运行时验证应区分启动、交互、诊断和证明。
- 扩展 marker validation、runtime event 处理、截图可用性、停止/清理行为和错误报告的 contract 与 harness 覆盖。

### C# 与 Godot 绑定深度

- 深化 Roslyn 支持的 Godot .NET 项目结构、导出成员、partial class、signal、NodePath 使用、resource、PackedScene 和生成项目元数据检查。
- 改进 C# diagnostics、Godot 场景/资源引用、编辑器可见绑定和运行时错误之间的连接。
- 明确 managed C# 调试边界：Godot DAP 工具可以支持 Godot debugger 工作流，而 managed C# breakpoint 仍可能需要专用 .NET debugger。
- 优先提供实用的绑定、资源和构建诊断工作流，而不是宽泛但浅层的代码分析宣称。

### 作为项目能力包的用户扩展

- 改进 `custom_tools/` 脚手架、兼容性检查、热加载安全性、审计输出和恢复指引。
- 帮助 Agent 在不修改插件源码的情况下创建项目专属 `user_*` 工具。
- 文档化用户工具的预期 schema、返回结构、dry-run 模式、验证期望和故障隔离规则。
- 让 Tools 页和 prompt 指引把用户扩展作为一等能力展示，同时与内置工具清晰分离。

### 可演示工作流

1.x 线应包含可复现示例，展示插件如何端到端解决真实 Godot .NET 问题，例如：

- 发现、修复并重新验证 C# export 或 NodePath 绑定问题；
- 诊断并修复损坏的场景/资源引用；
- 通过日志、诊断、截图和聚焦修复追踪运行时失败；
- 安全地脚手架、加载、审计并使用一个用户扩展。

这些示例应强调可重复性和证据，而不是营销宽度。

### 稳定性与公开 Schema 纪律

- 保留已建立的 `system_*` 工具身份，避免不必要的破坏性变更。
- 尽可能新增字段，而不是删除或重命名字段。
- 保持 protocol facts、工具 schema、Resources、Prompts、本地化描述、文档、changelog 和测试同步。
- 当公开行为必须改变时，维护清晰的迁移说明。

### 编辑器 UX 与 Agent UX

- 让 Dock 聚焦于服务健康、当前上下文、工具发现、配置、更新状态和可执行诊断。
- 改进编辑器 UI 工作的截图验证路径。
- 持续降低受支持 MCP client 的设置摩擦，同时让当前安装/配置状态可见。
- 保持用户可见插件界面和工具描述的本地化完整性。

### 诊断与证据质量

- 在不强制完整文件枚举的前提下，改进大型项目的项目状态摘要。
- 将场景依赖、资源引用、绑定审计、运行时日志和性能快照扩展为可读证据摘要。
- 保持失败报告具体：说明失败内容、当前会话为何不能执行某操作，以及哪个设置步骤可以解除阻塞。

### 测试与发布可靠性

- 持续扩展 headless harness、editor probe、contract、本地化和发布验证覆盖。
- 保持 Asset Library 安装验证与导出的插件内容一致。
- 确保 release notes 和 changelog 描述用户可见能力及重要内部验证变化，而不是变成实现日志。

## v2.0 开发方向

v2.0 是探索超出 1.x 编辑器原生插件边界的架构扩展的合适阶段。主要探索方向是可选的外部或 headless companion mode。

### 可选外部或 Headless Companion

只有当 v2.0 companion 能解决编辑器原生插件难以覆盖的真实工作流时，才应考虑它。可能目标包括：

- 在不要求编辑器 UI 打开的情况下检查 `.tscn`、`.tres`、`.csproj`、solution 文件和 C# 源码；
- 在本地自动化或 CI 风格环境中运行 build、restore、静态审计、资源引用和绑定检查；
- 在不需要编辑器实时上下文时，以受控 headless 或 runtime validation 模式启动 Godot；
- 为远程或自动化 Agent 会话提供更低摩擦的路径；
- 当编辑器插件会话可用时，升级为实时编辑器上下文。

这个 companion 不得削弱核心插件体验。编辑器插件仍应是实时编辑器状态、选中节点、Dock 状态、编辑器截图、编辑器日志和编辑器 UI 控制的权威来源。

### v2.0 架构原则

- 将 1.x 编辑器原生插件保持为稳定模式，而不是即将废弃的过渡方案。
- 任何 companion 都应是可选、显式且 capability-gated 的；它不应成为隐藏的必需后台进程。
- 在 editor-live 能力与 headless/static 能力之间定义严格协议边界。
- 除非结果结构和限制被清楚记录，否则避免在不同模式间重复工具语义。
- 通过可预览、可审计且在可行范围内可恢复的写操作保持用户信任。

### 更深入的 .NET Runtime 与调试叙事

如果 Godot 与 .NET 调试/工具链边界允许，v2.0 也可以探索更深入的 .NET 工作流：

- 更强的 managed exception 到 C# 源码、场景和资源的关联；
- 更丰富的 MSBuild 与 SDK 兼容性诊断；
- 更清晰地区分 Godot DAP debugging 与 managed .NET debugging 的职责；
- 更精确地将运行时失败映射到项目文件、场景绑定和导出成员。

## 非目标

- 不把追求更大的原始工具数量作为成功指标。
- 不把任意本地代码执行作为默认用户可见能力暴露。
- 不用模糊的调试宣称替代专用 .NET IDE debugger。
- 不让外部 companion 成为 1.x 编辑器原生工作流的强制依赖。
- 不把项目专属业务工具内置到插件仓库；项目专属能力应属于用户扩展。
- 不把本文档视为已承诺的发布排期。
