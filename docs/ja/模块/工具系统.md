# Tool System

この文書は、tool の grouping、主な category、呼び出し方法、return ルールを説明します。

---

## 全体像

plugin の tool system は、Agent に見せる高レベルの入口と、内部の実装 detail を分けるためにあります。

- 高レベル tool は、実際の作業 flow をそのまま表す
- 低レベルの atomic helper は、内部実装を支える
- すべては、editor 内の状態と project 文脈に結びつく

---

## grouping の考え方

tool は次の軸で分かれます。

- `system_*`：project、scene、script、index、runtime、diagnostic の高レベル flow
- `script_*`：C# と script 編集の flow
- `scene_*`：scene 検査と修正の flow
- `node_*`：node 操作
- `plugin_runtime_*`：plugin 自身の runtime 管理
- `plugin_developer_*`：開発者向けの補助
- `plugin_evolution_*`：plugin の進化や user tool 関係
- `user_*`：project 専用の拡張 tool

---

## 何を高レベル tool として出すか

高レベル tool は、Agent が「何をしたいか」で選べるべきです。

例。

- C# script の構造を確認する
- scene の binding を調べる
- runtime を起動して証拠を取る
- editor state を見て UI を操作する
- user tool を作る / 調べる / 消す

高レベル tool にするかどうかは、内部の algorithm の数ではなく、Agent が自然に選べる単位かで決めます。

---

## action ベースの分け方

1 つの tool の中でも、`action` で細かい動作を分けることがあります。

- `action` は同じ能力 domain の中での振る舞いの切り替え
- `action` を増やすときは、意味が薄い分割になっていないか確認する
- 似た action が並びすぎたら、tool を再設計する

---

## return ルール

tool の返り値は、MCP client がそのまま使える形にします。

- 文字列だけで済むなら、無理に構造を重くしない
- しかし、状態、warning、error、payload があるなら、構造化する
- write 系 tool は、できるだけ read-back 検証しやすい形にする

---

## 使い方の例

- `system_help` は、どういう tool があるかを知る入口
- `system_project_state` は、今の project の全体状態を読む入口
- `system_runtime_step` は、runtime の操作と証拠取りをまとめる入口
- `script_inspect` や `script_exports` は、C# の構造を読む入口

---

## 避けること

- 低レベル atomic helper をそのまま表に並べすぎない
- 同じ意味の tool を別名で増やさない
- tool 名を内部実装の都合だけで決めない
- Agent が選べないほど細かい action を増やしすぎない
