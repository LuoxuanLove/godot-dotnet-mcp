# リリース Runbook

この文書は、Godot .NET MCP の release 前チェックと遠隔 release の流れを記録します。ここで扱うのはプラグイン自身の release だけで、リポジトリ外のプロジェクトやローカル worktree の流れは含みません。

---

## 1. リリース原則

- `dev` は安定統合 branch です。release 前の変更はすべて短命 branch PR で `dev` に入れます
- 通常の `feature/*`、`fix/*`、`docs/*`、`chore/*`、`hotfix/*` PR は、プラグインの公開 version metadata を `dev` と一致させます。該当 version を変えられるのは `dev` 向けの `release/*` PR だけです
- release は maintainer が手動で起動するか、`v*` tag を push したときに走らせます。Agent は `dev` を直接 merge したり push したりしません
- インストール方法は Godot Asset Library と `addons/godot_dotnet_mcp/` の直接コピーの 2 つだけを残します
- zip package、release bundle、ローカル build artifact、その導入手順は作りません、アップロードもしません、記録もしません
- `next` draft release は次版の release note 草稿です。正式 release ではありませんし、package asset もつきません

---

## 2. release 前チェック

1. `addons/godot_dotnet_mcp/plugin.cfg` の version、`docs/en/CHANGELOG.md`、`docs/ja/変更履歴.md`、公開文書が一致していることを確認する
   - changelog は、対象 version が前回の正式 release からどう変わったかを全部記録する。ユーザーに見える `Added` / `Changed` / `Fixed` だけでは足りない。重要な `Documentation` と `Internal` の変化も `docs/en/CHANGELOG.md` と `docs/ja/変更履歴.md` に載せる。たとえば release note source file、README / docs / Runbook の更新、CI / harness / workflow の動き、policy check、protocol facts、検証範囲の変化などがそれです
   - 単なる version metadata の切り替えは changelog に書きません。ユーザーが見る互換性、導入方法、release 検証の流れが変わるときだけ書きます。開発中に入れて同じ version line で直した内部問題も、独立した changelog 項目にはしません
2. その version の `docs/zh-CN/流程/发布说明/发布说明-v*.md` が存在し、ユーザー向けの手書き release narrative になっていることを確認する。workflow は changelog の version paragraph を検証し、commit summary を追記します
3. `next` draft release が正式 release 形式で更新されていて、そのまま GitHub Release 本文のプレビューとして使えることを確認する
4. PR に今の release 目標以外の修正や歴史的な未 merge commit が混ざっていないことを確認する
5. 公開文書がプラグイン自身の install、use、release、compatibility だけを説明していることを確認する
6. 次のコマンドを実行するか、CI が通っていることを確認する。

```powershell
.\scripts\test_plugin_side_roslyn.ps1 -GodotPath "<Godot Editor Path>"
```

7. `.github/workflows/**` を変えたなら、`lint-workflows` が通っていることを確認する
8. 正式 release tag を push するなら、tag が `v*` であること、tag が `dev` から到達できる commit を指すこと、tag version が `plugin.cfg`、英語、韓国語、日本語、簡体字の changelog と対応する `docs/zh-CN/流程/发布说明/发布说明-v*.md` と一致することを確認する

## 3. release note の形式

正式な GitHub Release 本文は `scripts/render_release_notes.ps1` で生成され、次の 2 層構造を保ちます。

1. 手書き summary layer。`docs/zh-CN/流程/发布说明/发布说明-v<version>.md` から来ます。version のテーマ、主要な亮点、互換性注意、upgrade 判断を説明します
2. 自動 summary layer。workflow は先に `docs/ja/変更履歴.md` の対象 version か `Unreleased` 段落を確認し、そのあと最近の commit summary を追加します

手書き summary を書くときは次を守ります。

- すでに公開した `v1.0.1` の emoji narrative 構造を学ぶこと。emoji、version、ユーザー向けテーマを含む 2 階層 title、わかりやすい 1 段のテーマ説明、ユーザーへの影響で分けた、各項目に emoji が付いた 3 階層の見出し、最後の emoji 付き compatibility / installation / upgrade 注意を入れること
- commit list、内部 task list、PR の復唱はしない。ユーザーが見える能力、editor 体験、診断品質、install / upgrade の影響、互換性の変化だけを書く
- 维护流程、开发流程、发布の機械的な変化は書かない。たとえば GitHub Actions の画面、dry-run cache、PR / branch policy、CI の内部分割、tag check 実装などです。ただし、それ自体が最終ユーザーの導入や使い方を変えるなら例外です
- 現在の `plugin.cfg` version に対応する `docs/zh-CN/流程/发布说明/发布说明-v<plugin.cfg version>.md` は必ず存在し、その version を指していなければなりません。新しい version に切り替えて対応 note を足したら、古い version source file を片付けます
- version を切り替えたばかりで、まだ実際の開発内容がないときは、後で埋めるための初期空テンプレートを作ります。テンプレートは、その version line が始まったことと、正式 release 前に前回 version からの実際のユーザー向け変化で埋めることだけを書き、機能、修正、運用フローを勝手に作らない
- 推奨テンプレート

```markdown
## <emoji> Godot .NET MCP vX.Y.Z: <user-visible theme>

Godot .NET MCP `vX.Y.Z` is a <release type> for <target users>. It improves <user-facing outcome> while keeping <compatibility / installation / tool-surface expectation>.

### <emoji> <user impact area>

Explain what changed, why it matters to plugin users, and what behavior they can expect.

### ✅ Compatibility and Upgrade Notes

Explain Godot/.NET compatibility, supported installation paths, upgrade judgment, and any user-visible caveats.
```

version を切り替えた直後の初期テンプレート。

```markdown
## 🧩 Godot .NET MCP vX.Y.Z: Release Theme Pending

Godot .NET MCP `vX.Y.Z` has been initialized as the next release line. Before the final release, replace this placeholder with the actual user-visible changes shipped since the previous release.

### ✨ Highlights To Be Filled

Add user-facing capabilities here once they exist.

### 🔧 Fixes To Be Filled

Add user-facing fixes here once they exist.

### ✅ Compatibility and Upgrade Notes

Confirm Godot/.NET compatibility, supported installation paths, upgrade judgment, and any user-visible caveats before release.
```

`draft-release-notes` は `dev` 更新後に同じ script で `next` draft release を更新します。正式な `v*` tag release では `publish-plugin` が同じ script で最終本文を生成します。

## 4. 遠隔 release の流れ

1. 最新の `origin/dev` から release 用の短命 branch を切る。例: `release/v1.0.1`
2. version、change log、`docs/zh-CN/流程/发布说明/发布说明-v*.md`、公開文書を仕上げる
3. 短命 branch を push し、`dev` 向け PR を作る
4. `validate-plugin-harness` と関連 workflow が通るのを待つ
5. maintainer が GitHub PR page で手動確認して merge する
6. `draft-release-notes` を手動実行するか待ち、`next` draft release の本文が正式 release 形式になっているか確認する
7. まず `publish-release` workflow を手動で起動する。GitHub Actions の `Use workflow from` で `dev` を選び、`dry_run=true` のまま version、release note、build check を確認する
8. dry run が通り、内容を確認できたら `publish-release` をもう一度実行し、`dry_run` を `false` にする。version と target commit が同じなら、workflow は成功した dry-run 記録を使い、重複 build と harness check を飛ばして、`dev` の現在 commit に新しい `v*` tag を作り、正式 GitHub Release を作成し、消費済みの `next` draft release を削除する
9. 以前の入口を使うなら、merge 後の `dev` に `v*` tag を作って push するか、`publish-plugin` workflow を手動起動してもよい。tag 入口は tag version、release note source file、`dev` 到達性を先に確認してから build と harness を実行する
10. `publish-release` と `publish-plugin` は、どちらも release 前に version 一致、release note source file、既存 release の有無を確認する。確認が通ったら GitHub Release を作るが、ローカルの package asset は作らない

`publish-release` は締めだけをします。version の変更を commit したり、PR を merge したり、`dev` を push したり、正式 tag を上書きまたは削除したり、zip / package asset を作ったりはしません。tag や GitHub Release がすでに存在する場合は失敗し、新しい version を選ぶか、人が処理する必要があります。

---

## 5. 失敗時の扱い

- CI が失敗したら、修正は短命 branch に戻してから再 push する。`dev` を直接直さない
- release note の内容が間違っていたら、まず GitHub Release 本文を直す。source document や changelog が間違っているなら、短命 branch を切って直す
- tag が間違っていたら、remote tag を消すかどうかは maintainer が決める。Agent は勝手に消したり書き換えたりしない
- `next` draft release の内容が間違っていたら、まず `docs/zh-CN/流程/发布说明/发布说明-v*.md` か changelog を直してから `draft-release-notes` をもう一度走らせる。render rule 自体が間違っているなら、workflow か script を短命 branch PR で直す
