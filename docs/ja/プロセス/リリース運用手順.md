# リリース Runbook

この文書は、Godot .NET MCP の release 前チェックと遠隔 release の流れを記録します。ここで扱うのはプラグイン自身の release だけで、リポジトリ外のプロジェクトやローカル worktree の流れは含みません。

---

## 1. リリース原則

- `dev` は安定統合 branch です。release 前の変更はすべて短命 branch PR で `dev` に入れます
- 通常の `feature/*`、`fix/*`、`docs/*`、`chore/*`、`hotfix/*` PR は、プラグインの公開 version metadata を `dev` と一致させます。該当 version を変えられるのは `dev` 向けの `release/*` PR だけです
- release は maintainer が手動で起動するか、`v*` tag を push したときに走らせます。Agent は `dev` を直接 merge したり push したりしません
- インストール方法は Godot Asset Library と `addons/godot_dotnet_mcp/` の直接コピーの 2 つだけを残します
- zip package、release bundle、ローカル build artifact、その導入手順は作りません、アップロードもしません、記録もしません
- `next` draft release は次版の release note 草稿です。正式 release ではありませんし、package asset もつきません

---

## 2. release 前チェック

1. `addons/godot_dotnet_mcp/plugin.cfg` の version、4 言語の changelog、4 言語の `v*` release-note source file、公開文書が一致していることを確認する
   - changelog は、対象 version が前回の正式 release からどう変わったかを全部記録する。ユーザーに見える `Added` / `Changed` / `Fixed` だけでは足りない。重要な `Documentation` と `Internal` の変化も `docs/en/CHANGELOG.md`、`docs/zh-CN/变更日志.md`、`docs/ja/変更履歴.md`、`docs/ko/변경-로그.md` に載せる。たとえば release note source file、README / docs / Runbook の更新、CI / harness / workflow の動き、policy check、protocol facts、検証範囲の変化などがそれです
   - 単なる version metadata の切り替えは changelog に書きません。ユーザーが見る互換性、導入方法、release 検証の流れが変わるときだけ書きます。開発中に入れて同じ version line で直した内部問題も、独立した changelog 項目にはしません
2. その version の英語、簡体字中国語、日本語、韓国語の `v*` release-note source file が存在し、永続文書として残り、ユーザー向けの手書き release narrative になっていることを確認する。workflow は英語 release note から GitHub Release body を render し、英語 changelog の version section を検証して commit summary を追記します
3. `next` draft release が正式 release 形式で更新されていて、そのまま GitHub Release 本文のプレビューとして使えることを確認する
4. PR に今の release 目標以外の修正や歴史的な未 merge commit が混ざっていないことを確認する
5. 公開文書がプラグイン自身の install、use、release、compatibility だけを説明していることを確認する
6. 次のコマンドを実行するか、CI が通っていることを確認する。

```powershell
.\scripts\test_plugin_side_roslyn.ps1 -GodotPath "<Godot Editor Path>"
```

7. `.github/workflows/**` を変えたなら、`lint-workflows` が通っていることを確認する
8. 正式 release tag を push するなら、tag が `v*` であること、tag が `dev` から到達できる commit を指すこと、tag version が `plugin.cfg`、4 言語の changelog、4 言語の `v*` release-note source file と一致することを確認する

## 3. release note の形式

正式な GitHub Release 本文は `scripts/render_release_notes.ps1` で生成され、次の 2 層構造を保ちます。

1. GitHub Release body に使う手書き summary layer は `docs/en/process/release-notes/release-notes-v<version>.md` から来ます。version のテーマ、主要な highlights、互換性注意、upgrade 判断を説明します。簡体字中国語、日本語、韓国語の release-note source file は localized documentation tree に残し、title と introduction の直後で言語間 link を持たせます
2. 自動 summary layer。workflow は先に `docs/en/CHANGELOG.md` の対象 version か `Unreleased` section を確認し、そのあと最近の commit summary を追加します。release workflow は他の localized changelog と release note も同じ version を指すか確認します

手書き summary を書くときは次を守ります。

- すでに公開した `v1.0.1` の emoji narrative 構造を学ぶこと。emoji、version、ユーザー向けテーマを含む 2 階層 title、わかりやすい 1 段のテーマ説明、ユーザーへの影響で分けた、各項目に emoji が付いた 3 階層の見出し、最後の emoji 付き compatibility / installation / upgrade 注意を入れること
- commit list、内部 task list、PR の復唱はしない。ユーザーが見える能力、editor 体験、診断品質、install / upgrade の影響、互換性の変化だけを書く
- 维护流程、开发流程、发布の機械的な変化は書かない。たとえば GitHub Actions の画面、dry-run cache、PR / branch policy、CI の内部分割、tag check 実装などです。ただし、それ自体が最終ユーザーの導入や使い方を変えるなら例外です
- 現在の `plugin.cfg` version に対応する英語、簡体字中国語、日本語、韓国語の release-note source file は必ず存在し、その version を指し、localized docs tree に残す必要があります。新しい version に切り替えて対応 note を足したら、古い version source file を片付けます
- version を切り替えたばかりで、まだ実際の開発内容がないときは、後で埋めるための初期空テンプレートを作ります。テンプレートは、その version line が始まったことと、正式 release 前に前回 version からの実際のユーザー向け変化で埋めることだけを書き、機能、修正、運用フローを勝手に作らない
- 推奨テンプレート

```markdown
## <emoji> Godot .NET MCP vX.Y.Z: <ユーザー向けテーマ>

Godot .NET MCP `vX.Y.Z` は <対象ユーザー> 向けの <リリース種別> です。<互換性 / インストール / ツール面の期待値> を保ちながら、<ユーザーが見える成果> を改善します。

### <emoji> <ユーザーへの影響領域>

何が変わったのか、plugin user にとってなぜ重要なのか、どのような挙動を期待できるのかを説明します。

### ✅ 互換性とアップグレードの注意

Godot / .NET 互換性、対応する導入経路、upgrade 判断、ユーザーが知るべき注意点を説明します。
```

version を切り替えた直後の初期テンプレート。

```markdown
## 🧩 Godot .NET MCP vX.Y.Z: リリーステーマ未確定

Godot .NET MCP `vX.Y.Z` は次の release line として初期化されています。正式 release 前に、前回 release 以降に実際に出荷したユーザー向け変更へ置き換えます。

### ✨ 補完予定のハイライト

ユーザー向け能力が実際に入ったらここに追加します。

### 🔧 補完予定の修正

ユーザー向け修正が実際に入ったらここに追加します。

### ✅ 互換性とアップグレードの注意

release 前に Godot / .NET 互換性、対応する導入経路、upgrade 判断、ユーザーが知るべき注意点を確認します。
```

`draft-release-notes` は `dev` 更新後に同じ script で `next` draft release を更新します。正式な release body は `publish-release` が生成し、`publish-plugin` は tag-triggered validation で release-note artifact を作るためだけに同じ script を使います。

## 4. 遠隔 release の流れ

1. 最新の `origin/dev` から release 用の短命 branch を切る。例: `release/v1.0.1`
2. version、4 言語の changelog、4 言語の `v*` release notes、公開文書を仕上げる
3. 短命 branch を push し、`dev` 向け PR を作る
4. `validate-plugin-harness` と関連 workflow が通るのを待つ
5. maintainer が GitHub PR page で手動確認して merge する
6. `draft-release-notes` を手動実行するか待ち、`next` draft release の本文が正式 release 形式になっているか確認する
7. まず `publish-release` workflow を手動で起動する。GitHub Actions の `Use workflow from` で `dev` を選び、`dry_run=true` のまま version、release note、build check を確認する
8. dry run が通り、内容を確認できたら `publish-release` をもう一度実行し、`dry_run` を `false` にする。version と target commit が同じなら、workflow は成功した dry-run 記録を使い、重複 build と harness check を飛ばして、`dev` の現在 commit に新しい `v*` tag を作り、正式 GitHub Release を作成し、消費済みの `next` draft release を削除する
9. 追加の tag validation が必要なら、merge 後の `dev` に `v*` tag を作って push するか、`publish-plugin` workflow を手動起動してもよい。この経路は tag version、release note source file、`dev` 到達性、build、harness、rendered release-note artifact を確認するが、validation-only で正式 GitHub Release は作成しない
10. `publish-release` は正式 GitHub Release を作成する前に version 一致、4 言語の changelog、4 言語の release-note source file、既存 release を確認し、英語 release note から正式本文を生成する。`publish-plugin` は pushed tag や manual verification に対して同じ source / tag validation を行うが、validation と artifact upload の後で終了する

`publish-release` は締めだけをします。version の変更を commit したり、PR を merge したり、`dev` を push したり、正式 tag を上書きまたは削除したり、zip / package asset を作ったりはしません。matching tag が target commit を指していて GitHub Release がない場合は、その tag を再利用して missing Release を作成できます。tag が別 commit を指す場合や GitHub Release がすでに存在する場合は失敗し、新しい version を選ぶか、人が処理する必要があります。

---

## 5. 失敗時の扱い

- CI が失敗したら、修正は短命 branch に戻してから再 push する。`dev` を直接直さない
- release note の内容が間違っていたら、まず GitHub Release 本文を直す。source document や changelog が間違っているなら、短命 branch を切って直す
- tag が間違っていたら、remote tag を消すかどうかは maintainer が決める。Agent は勝手に消したり書き換えたりしない
- `next` draft release の内容が間違っていたら、まず英語 release note か英語 changelog を直してから `draft-release-notes` をもう一度走らせる。localized source が同期していないなら、release 前に対応する言語の release note または changelog を直す。render rule 自体が間違っているなら、workflow か script を短命 branch PR で直す
