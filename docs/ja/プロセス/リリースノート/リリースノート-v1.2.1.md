## 🧩 Godot .NET MCP v1.2.1: Verified Editor UI Automation

この version line では editor UI automation を改善し、client が次の workflow に進む前に Godot editor 内の visible state を待てるようにします。Agent は既存の editor control で操作したあと、期待する UI condition が実際に現れたかを検証できます。

### ✨ 実際の UI 状態を待機

`system_editor_control` に `wait_for_ui` を追加しました。control の存在、可視性、text matching、enabled / disabled state を有界にポーリングできます。成功時は一致した control summary と timing detail を返し、timeout 時は最後に観測した payload を返すため、client は locator や次の action を調整できます。

### 🔧 より安全な automation loop

新しい wait action は menu、popup、click、hover、text entry control と組み合わせて使え、OS mouse automation は不要です。editor dialog を開く、setting を filter する、一時 panel を確認する、といった workflow を Godot 内で検証しやすくします。

Resource / prompt diagnostics は、resource output を報告する前に mixed-case URL credential、bearer / API-key variant、nested metadata secret を redact します。troubleshooting evidence は automation loop に有用なまま、summary に credential を露出しにくくなります。

### 🪟 Floating Window Evidence

`system_editor_control` は `get_popup` と `capture_popup` により、可視の floating popup / window surface を読み取り、crop した evidence を取得できるようになりました。client は button、menu item、text field、close action を選ぶ前に modal editor window や PopupMenu の状態を直接確認できます。

### 🧭 Configuration Navigation and Evidence

`system_settings_dialog` は Project Settings と Editor Settings 向けの high-level workflow を追加します。client は editor menu から settings surface を開き、dialog の可視化を待ち、候補 setting row を検索し、返された result に focus し、evidence を capture して、setting value を直接書き込まずに surface を閉じられます。

この workflow は `list_rows` で読み取り専用 row model も返せるようになり、可視 settings-like control を保守的な confidence と evidence 付きで要約してから、必要な value read、write、assertion を選べます。

`list_tabs` と `activate_tab` で settings tab を list / activate でき、`open(tab=...)` も使えるため、座標クリックなしで Project Settings / Editor Settings の tab 間を移動できます。

この settings workflow は visible category tree item を list し、row inspection の前に一意の category に focus できます。Project Settings / Editor Settings navigation が raw control enumeration に依存しにくくなります。

さらに `read_value` で一意に一致した可視 row の現在値を読み取り、row と value-control の evidence とともに text、bool、number、enum の型付き payload を返せます。setting value は引き続き直接書き込みません。

Project configuration evidence は input map も対象にします。Agent は `system_project_configure` から個別の project input action を読み取り、deadzone と具体的な key、mouse、controller binding を確認できます。これにより gameplay や editor shortcut を変更する前に、実際の project configuration に基づいて input map を確認できます。

Project configuration は `system_project_configure(action="list_export_presets")` で export preset も一覧できます。response は preset name、platform、runnable state、filter、script export mode、export path の形を要約し、sensitive option key と local absolute export path は redact します。

Client は `resolve_row` により、値の読み取りや後続 UI 操作の前に一意の可視設定行を解決できます。response には row path、confidence、selector evidence、ambiguity diagnostics が含まれ、読み取り専用のまま動作します。

Agent が一致した value editor へ keyboard focus だけを移したい場合は、`focus_value` が value control を focus し、設定を変更せずに focus evidence を返します。

対応している一意の可視 row は、`set_value` で text、number、bool control を編集できます。この workflow は editor UI control 経由で書き込み、操作後に row を再観測するため、client は click や text edit が成功したと仮定せずに変更後の値を確認できます。

Agent は読み取り専用の `verify_value` check も使い、期待する text、bool、number、enum 値を一意に一致した可視 row と比較できます。settings workflow に、UI action の前後で値を書き換えない assertion step を追加できます。

### 🔎 検索できる Tool Discovery

`system_tool_catalog` は、現在の tool catalog を読み取り専用で検索する入口です。client は query、category、domain で検索し、各 tool が一致した理由、公開する action と parameter、visible state、enabled state を確認できます。

これにより、profile、plugin domain tool、user tool state が変わったあとでも、configuration / editor workflow に入り直しやすくなります。Agent は古い tool name の記憶に頼らず、次の verified action の前に適切な system、project、editor、runtime、script、user-facing tool を再発見できます。

Native MCP discovery も resource と resource template の metadata をローカライズするようになりました。client が `resources/list` または `resources/templates/list` を呼ぶと、resource name と description は現在の plugin language に従い、URI と template は安定したまま維持されます。

### ✅ Compatibility and Upgrade Notes

これらの変更は public tool schema を拡張するだけです。既存の `system_editor_control`、`system_settings_dialog`、`system_project_configure` action は引き続き利用でき、新しい action を呼ばない client は request を変更する必要がありません。
