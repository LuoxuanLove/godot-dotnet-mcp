# ライフサイクルと装配

この文書は、plugin entry の `plugin.gd` が runtime object をどう組み立て、Dock を登録し、Autoload と debug bridge にどう接続し、完全 reload と終了時にどう片付けるかを説明します。

---

## 核心入口

現在の plugin entry は `addons/godot_dotnet_mcp/plugin.gd` で、型は `EditorPlugin` です。もはやすべての業務ロジックを抱え込まず、次の object を組み合わせる薄い装配層です。

- `LocalizationService`
- `PluginRuntimeState`
- `SettingsStore`
- `ServerRuntimeController`
- `ToolCatalogService`
- `ClientConfigService`
- `UserToolService`（`user_tool_catalog_service.gd` / `user_tool_maintenance_service.gd` に委譲）
- `PluginReloadCoordinator`
- `MCPRuntimeDebugStore`
- `plugin/features/server_feature.gd`
- `plugin/features/config_feature.gd`
- `plugin/features/ui_state_feature.gd`
- `plugin/features/user_tool_feature.gd`
- `plugin/features/reload_feature.gd`
- `plugin/features/tool_profile_feature.gd`
- `plugin/features/tool_access_feature.gd`
- `plugin/features/self_diagnostic_feature.gd`
- `PluginSelfDiagnosticStore`
- `plugin/presenters/dock_model_service.gd`
- `plugin/presenters/dock_presenter.gd`
- `plugin/presenters/client_config_presenter.gd`
- `ui/mcp_dock.tscn`

つまり入口は主に「装配」「同期」「橋渡し」を担当し、複雑な UI logic や tool 実装を直接持ちません。

---

## `_enter_tree()` の装配順

`plugin.gd._enter_tree()` の現在の順番。

1. 前回 plugin の自診断 cache を空にする
2. `PluginRuntimeState` を作り直し、hot reload 後に exit 中に空になった古い state container を再利用しないようにする
3. `_refresh_service_instances()` で今回の入口が持つ service bundle を更新する
4. `_load_state()` で settings file と custom profile を読む
5. localization service を reset して初期化し、現在 language を適用する
6. `MCPDebugBuffer` に log level を同期する
7. `PluginRuntimeCoordinator` を通して `ServerRuntimeController` を作成・接続し、server signal wiring を統一する
8. `PluginRuntimeCoordinator` を通して runtime bridge Autoload `MCPRuntimeBridge` を install する
9. `PluginRuntimeCoordinator` を通して editor debug bridge `MCPEditorDebuggerBridge` を install する
10. `ui/mcp_dock.tscn` を instantiate して attach する
11. 初回 load なら default profile から `disabled_tools` を導く
12. 最初の `_refresh_dock()` で UI model を投影する
13. `_process()` polling を有効にする
14. `auto_start=true` なら内蔵 MCP service を起動し、server start / reload chain の settings projection、server node、HTTP server、tool loader、stdio stage の所要時間を plugin self-diagnostic operation record に残す
15. reload 前に保存していた focus snapshot があれば、Dock page と focus を戻す

現在の entry は `PluginActionRouter`、`PluginDockCoordinator`、`PluginRuntimeCoordinator` を安定した member collaborator として保持し、実行中に lazy initialize 分岐を増やしません。`PluginDockCoordinator` は plugin 専用の dock create / remove / recreate、stale cleanup、signal wiring、dock instance count を引き受け、`PluginRuntimeCoordinator` は server controller、runtime bridge、debugger bridge の lifecycle を担当します。

`ServerRuntimeController` の create、attach、signal wiring、detach、recreate も `PluginRuntimeCoordinator` 側へ下がり、Dock lifecycle の包装も `PluginDockCoordinator` に下がりました。

## `_exit_tree()` の片付け順

退出時は Godot の「node が自然に解放される」のに任せず、明示的に順番を決めて片付けます。

1. `_process()` を止める
2. 現在 settings を保存する
3. Dock を外す
4. editor debug bridge を外す
5. `PluginRuntimeCoordinator` で server signal を切り、`detach()` を実行し、controller 参照を空にする
6. 入口が持つ feature / presenter / action router / service の参照と object graph を明示的に片付ける
7. localization service singleton を reset する
8. 次の hot reload に残らないよう、入口が持つ service reference を空にする

この順番の目的は、完全 reload と plugin disable のときの残留 state を減らすことです。

---

## Dock 装配の流れ

Dock の装配は `PluginDockCoordinator` の高レベル API が担当し、内部の流れは次の通りです。

1. 古い instance を片付ける
2. hot reload 後に残る stale Dock を掃除する
3. `ui/mcp_dock.tscn` を読む
4. root node を instantiate し、すべての page signal を接続する
5. `add_control_to_dock(DOCK_SLOT_RIGHT_UL, _dock)` で editor に登録する
6. 複数 instance が見つかれば、自診断 incident を記録する

entry と Dock の関係は一方向です。

- Dock は service object を持たない
- Dock は signal と `apply_model()` だけを出す
- signal は装配時に `plugin.gd` から feature または安定した bridge method へつながり、そこから具体的 service へ流れる

## runtime bridge と debug bridge

### runtime bridge Autoload

`PluginRuntimeCoordinator` は project に次のものがあることを保証します。

- Name: `MCPRuntimeBridge`
- Path: `res://addons/godot_dotnet_mcp/plugin/runtime/mcp_runtime_bridge.gd`

同名 Autoload が別の script に使われている場合、plugin は無理に上書きせず、次の動きにします。

- runtime bridge state を failure にする
- 自診断に conflict incident を記録する
- plugin の他の部分はそのまま動かす

### editor debug bridge

`PluginRuntimeCoordinator` は `MCPEditorDebuggerBridge` を instantiate して `EditorDebuggerPlugin` に登録し、動作中の主 project の debug session summary を plugin が読める data structure に同期します。

今は、以下もここが担当します。

- `ServerRuntimeController` の create、attach、signal wiring、detach、recreate
- `plugin.gd` が server controller の lifecycle 細部を直接持たないようにすること

---

## state polling と model refresh

plugin は各 service の state 変化を全部 deep notify にせず、軽い polling を使います。

- `plugin.gd._process()` が 0.5 秒ごとに `_refresh_dock()` を呼ぶ
- `_refresh_dock()` が統一 model を作り直し、Dock context の集約を `dock_model_service.gd` に任せ、それを presenter script で表示用に変換する
- `mcp_dock.gd.apply_model()` が model を 3 つの page に配る

このやり方の利点。

- 入口 logic が単純で、state 同期の流れがわかりやすい
- language、scale、service state、statistics を一緒に更新できる
- UI controller をほぼ表示専用に保てる

## 完全 reload の方針

plugin は 2 種類の reload を支援します。

### 1. runtime reload

`plugin_runtime_reload` の domain / soft reload action、または server page から触って、tool domain や server だけを更新し、plugin instance 全体は壊さない。

### 2. 完全 plugin reload

`system_plugin_reload(action="full_reload_plugin")`、互換入口 `plugin_runtime_reload(action="full_reload_plugin")`、または Home page の完全 reload button から触り、`PluginReloadCoordinator` が Godot plugin layer の次を動かす。

1. `set_plugin_enabled(false)`
2. 古い server node と TCP listen が外れるまで短く待つ
3. `set_plugin_enabled(true)`

この coordinator は editor の `base_control` にぶら下がり、plugin 自身の node にぶら下がりません。そのため plugin が disable されても、再有効化の手順を続けられます。今は再有効化の前に短い delay window を置き、完全 reload 時に古い `TCPServer` がまだ解放されていないまま新 instance の auto_start がぶつかる競合を減らしています。

完全 reload の前に記録するもの。

- 現在の host Dock tab
- `MCPDock` 内部の現在 Tab
- 現在 focus している control の相対 path

reload 後は host Dock をもう一度有効にし、その後で内部 tab と focus を戻します。

磁盤上の addon copy を更新することと、動いている instance を reload することは別段階です。`addons/godot_dotnet_mcp/` を copy、更新、install しても、それは target project の磁気的な file を変えるだけで、起動中の editor instance が自分自身をすぐに差し替えるわけではありません。Settings 更新同期は、archive の書き込みと `.mcp_sync.json` freshness marker の書き込みが両方成功したあと、自動で完全 plugin lifecycle reload を走らせ、今の editor で新しい file を反映します。それ以外の外部磁盤 copy 更新では、引き続き `system_plugin_reload(action="full_reload_plugin")` を呼んでください。reload 後は `/health`、`system_plugin_reload(action="get_freshness")`、`plugin_runtime_state(action="get_self_health")`、`system_project_state(include_runtime_health=true).runtime_health.freshness` を見て、`running_instance`、`disk_source`、`sync`、`comparison` を確認し、`needs_lifecycle_reload=false` であることを確かめます。

## 境界と責務

### `plugin.gd` が担当するもの

- lifecycle
- service object の装配
- Dock scene の装配入口
- UI signal -> feature / service call の橋渡し
- feature workflow の設定
- Dock model の collaborator 装配と presenter 呼び出し
- `tool_loader` に対する安定した tool access state 入口の公開
- settings の read / write の起点
- 自診断 incident の記録

### `plugin.gd` が担当しないもの

- 具体的な UI layout
- 個々の page の control state machine
- Server / Config / User Tool / Runtime Reload / Profile / Config Exchange / Tool Access / Self Diagnostic の interaction step の組み立て
- Dock page 状態の書き戻し、language 切り替え、Tree collapse の永続化、copy hint の組み立て
- Dock create / remove / recreate、stale cleanup、signal wiring、dock instance count の詳細
- Dock context の集約、tool tree projection、install detection の詳細
- `tool_loader` の tool access state query の実装
- tool protocol dispatch
- profile file の読み書き詳細
- client configuration merge logic
- tool domain の実行 logic
