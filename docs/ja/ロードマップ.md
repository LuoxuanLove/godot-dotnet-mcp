# ロードマップ

この文書は Godot .NET MCP の製品方向を示します。これは計画文書であって、release の約束ではありませんし、issue 単位の設計を置き換えるものでもありません。実装制約、テスト結果、ユーザーフィードバックが明確になるにつれて、バージョンの範囲は変わることがあります。

## 製品の位置づけ

Godot .NET MCP は、Godot 4.6 以降の .NET プロジェクト向けに作られた、エディター内蔵型の MCP プラグインです。1.x では次の立ち位置を保ちます。

- MCP サービスは Godot エディター内部で直接動く
- エディター、プロジェクト、シーン、runtime、診断、スクリーンショット、C# 構造、resource、tool extension の文脈をリアルタイムに提供する
- Agent には低レベルの原子的 tool を並べるのではなく、高レベルの `system_*` workflow を公開する
- 設定はそのまま使える形を保ち、主要な plugin 体験を別の常駐バックグラウンド service に依存させない
- Agent の作業を、ファイル編集だけでなく、診断、runtime の証拠、editor state で検証できるようにする

この project は、元の tool 数で勝つのではなく、意味のある quality、setup-aware な案内、C#/.NET project の理解、editor state の正確さ、runtime 検証、安定した MCP surface で勝つべきです。

## v1.x の開発方向

1.x では、editor native plugin structure を継続的に磨きながら、Godot .NET MCP を Agent 向けの evidence-first な workflow platform に育てます。最優先は、Agent が正しい capability を見つけ、狙いを絞った修正を行い、Godot で検証し、信頼できる証拠を報告できるようにすることです。

### v1.4.0 プロトコルリファクタ

v1.4.0 は [protocol refactor plan](プロセス/v1.4.0-プロトコルリファクタ計画.md) に従います。context、state、catalog は Resources に移し、workflow guidance は Prompts に残し、Tools は action と computational workflow entry に絞ります。target baseline は MCP 2025-11-25 で、`127.0.0.1:3000/mcp` を default Streamable HTTP endpoint、newline-delimited stdio を default stdio mode とし、schema / metadata / UI catalog adaptation を明示的な gate として扱います。作業は PR size の refactor axis に分け、removal guards と migration contracts を添えます。

現在の実行チェックリストは [v1.4.0 リファクタ進捗トラッカー](プロセス/v1.4.0-リファクタ進捗トラッカー.md) に記録しています。

### Capability discovery と tool governance

- `system_help` と tool catalog resource を強化し、Agent が大きなフラット一覧を当てずっぽうで探すのではなく、task に合った tool を選べるようにする
- core、runtime、DAP、editor UI、visual、plugin、user-extension の capability を含めて tool group と profile を分かりやすくする
- project 未実行、runtime control 不可、DAP endpoint 不可、editor foreground 必須、user tool 不足といった setup-gated 状態を表に出す
- 高レベルの `system_*` 入口を公開 workflow layer として維持し、低レベル executor は内部実装のままにする
- 公開 tool name、parameter、return field、protocol facts を 1.x workflow の安定 API surface とみなす

### 閉じた runtime 検証

- 既存の project run、runtime control、runtime step、screenshot、editor log、runtime diagnosis tool を、より明確な検証 workflow にまとめる
- 何を実行したか、どの marker に一致したか、どの screenshot や runtime state を取ったか、エラーが出たか、cleanup が終わったかを示す、証拠ベースのレポートを支える
- 起動できたことを、そのまま動作検証成功と見なさない
- marker validation、runtime event 処理、screenshot の利用可否、停止 / cleanup の挙動、error report の contract と harness coverage を広げる

### C# と Godot binding の深さ

- Roslyn が支える Godot .NET project 構造、export member、partial class、signal、NodePath の使い方、resource、PackedScene、生成済み project metadata の確認を深める
- C# diagnostics、Godot scene / resource reference、editor から見える binding、runtime error のつながりを改善する
- managed C# debugging の境界を明確にする。Godot DAP tool は Godot debugger workflow を支援できるが、managed C# breakpoint には専用の .NET debugger が必要な場合がある
- 広く浅い code analysis より、実際に使える binding、resource、build 診断 workflow を優先する

### project capability pack としての user extension

- `custom_tools/` の scaffold、compatibility check、hot load の安全性、audit 出力、復旧案内を改善する
- plugin source を変えずに、Agent が project 専用の `user_*` tool を作れるようにする
- user tool の想定 schema、return structure、dry-run mode、検証期待値、障害分離のルールを文書化する
- Tools ページと prompt guide で user extension を一級の capability として見せつつ、built-in tool と明確に分ける

### 見せられる workflow

1.x には、再現可能な例を含め、plugin が実際の Godot .NET 問題を end-to-end で解決する様子を示すべきです。たとえば次のようなものです。

- C# export や NodePath の binding 問題を見つけ、直し、再検証する
- 壊れた scene / resource reference を診断して修復する
- log、diagnostic、screenshot、focus repair を使って runtime failure を追う
- 1 つの user extension を安全に scaffold し、load し、audit し、使う

これらの例は、宣伝の幅ではなく、再現性と証拠を重視します。

### 安定性と公開 schema の規律

- すでに確立した `system_*` tool ID を維持し、むやみに壊さない
- 可能なら削除や rename よりも、field を追加する
- protocol facts、tool schema、Resources、Prompts、ローカライズ説明、文書、changelog、テストを同期させる
- 公開挙動を変えざるを得ないときは、明確な移行案内を残す

### editor UX と Agent UX

- Dock は service health、現在の context、tool discovery、設定、更新状態、実行可能な診断に集中させる
- editor UI 作業の screenshot 検証の道筋を改善する
- 対応 MCP client の設定摩擦を下げつつ、現在の install / config 状態を見えるようにする
- ユーザーに見える plugin UI と tool 説明のローカライズを保つ

### 診断と証拠の質

- 大きな project でも、完全な file enumeration を強いずに project state summary を改善する
- scene dependency、resource reference、binding audit、runtime log、performance snapshot を読みやすい証拠サマリーへ広げる
- 失敗報告は具体的にする。何が失敗したのか、なぜ今の session ではできないのか、どの設定手順で解除できるのかを示す

### テストと release の信頼性

- headless harness、editor probe、contract、localization、release validation coverage を広げ続ける
- Asset Library install の検証と export された plugin content の整合を保つ
- release notes と changelog は、ユーザーが見える capability と重要な内部検証の変化を説明し、実装ログにはしない

## v3.0 の開発方向

v3.0 は、1.x の editor native plugin の境界を超える structure 拡張を探る段階です。中心的な探索先は、任意の外部または headless companion mode です。

### 任意の外部 / Headless Companion

companion を考えるのは、それが editor native plugin では届きにくい実際の workflow を解決できる場合だけです。候補は次の通りです。

- editor UI を開かずに `.tscn`、`.tres`、`.csproj`、solution file、C# source を調べる
- local automation や CI 風の環境で build、restore、静的 audit、resource reference、binding check を走らせる
- editor の realtime context が要らないときに、制御された headless もしくは runtime validation mode で Godot を起動する
- remote または automated な Agent session への入口を軽くする
- editor plugin session が使えるときは、live editor context に昇格する

この companion は core plugin の体験を弱めてはいけません。editor plugin は、live editor state、selected node、Dock state、editor screenshot、editor log、editor UI control の正規の source のままであるべきです。

### v3.0 の設計原則

- 1.x の editor native plugin は安定モードとして扱い、廃止予定の移行案としない
- companion は任意、明示的、capability-gated であるべきで、隠れた必須バックグラウンド process であってはならない
- editor-live capability と headless/static capability の間に厳密な protocol boundary を置く
- 結果の structure と制約がはっきり記録されない限り、異なる mode で tool の意味を重複させない
- 書き込み操作は、可能な範囲で preview、audit、復元可能性を保って信頼を維持する

### .NET Runtime と debugging の叙述を深める

Godot と .NET の debugging / toolchain の境界が許すなら、v3.0 ではさらに深い .NET workflow も探れます。

- managed exception を C# source、scene、resource へもっと強く結びつける
- MSBuild と SDK の互換性診断を豊かにする
- Godot DAP debugging と managed .NET debugging の責務をより明確に分ける
- runtime failure を project file、scene binding、export member により正確に割り当てる

## 非目標

- 原始的な tool 数を増やすことを成功指標にしない
- 任意の local code execution を既定の user-visible capability として公開しない
- 曖昧な debugging の主張で専用の .NET IDE debugger を代替しない
- 外部 companion を 1.x の editor native workflow の必須依存にしない
- project 専用の業務 tool を plugin repository に組み込まない。project 専用 capability は user extension の担当にする
- この文書を、そのまま確約された release schedule と見なさない
