# エンコーディングとアーキテクチャ規約

この規約は `godot-dotnet-mcp` の強制ルールです。本文中の「必須」「禁止」は hard rule で、`scripts/validate_refactor_guardrails.ps1` が直接止めます。

---

## 1. 適用範囲と実行レベル

- 適用範囲は `godot-dotnet-mcp` リポジトリのみ
- 実行レベルは即時 hard stop。移行期間はなし
- 互換戦略は破壊的 refactor を許可し、置き換え後は旧実装を削除する。compatibility layer は残さない

---

## 2. 層境界の行列

許可される依存方向。

```text
plugin composition -> plugin runtime -> tools domain
plugin composition -> plugin presenters/ui
```

禁止される依存方向。

- `tools/*` が `plugin/*` に逆依存すること
- `plugin runtime` が `ui/*` に逆依存すること
- 層を越えた string method name や global singleton で collaborator injection を迂回すること

---

## 3. 注入と装配の規則

必須。

- typed context か明示 parameter で collaborator を注入する
- composition root は object assembly と lifecycle connection だけを担当し、業務分岐を持たない
- collaborator の `configure()` はべき等かつ再入可能であること。`dispose/reset` で参照解除もできること

禁止。

- `configure(callbacks: Dictionary)`
- 主経路で「任意 key name」の callback dictionary を使うこと
- context/factory から cross-domain の大きな dictionary を返し、それを事実源として渡すこと

---

## 4. サイズ上限

責務ごとに分けて扱います。

- `plugin.gd`、`plugin/runtime/mcp_http_server.gd` は `<= 360` 行
- `plugin/runtime/*service*.gd` は `<= 320` 行
- `plugin/*coordinator*.gd` は `<= 260` 行
- `ui/*tab*.gd` は `<= 420` 行
- `tools/*/catalog.gd` は `get_tools` が `<= 120` 行。超えるなら static data source と安定した読み口へ切り替える
- どの GDScript でも 1 関数は `<= 90` 行。data table 関数は例外だが、catalog rule は守る
- どの GDScript でも公開関数数は `<= 28`
- 新しい `*context*.gd` は `<= 28` 行で、field 定義と少数の無分岐 helper だけにし、業務ロジックは持たない

---

## 5. 小さな空壳ファイルの規則

許される小さな空壳ファイルは `<= 8` 行で、次に限る。

- `tools/*/executor.gd` の bridge entry
- 白名单に入った安定した re-export entry

禁止。

- 上限逃れのために意味のない薄い shell file を大量に作ること
- 空壳に実際の振り分けを隠すこと

---

## 6. 反パターン禁止

禁止項目。

- dual track 実装。新旧 path が両方生きること
- compatibility wrapper、compatibility alias、transition helper の長期残存
- layer を越えた内部可変 state field への直接アクセス
- string method callback (`call("method_name")` など) を主経路にすること
- 「あとで消す」前提の old code を残すこと

必須項目。

- 置き換え後は旧入口、旧 helper、旧 test path をすぐ消す
- 構造変更と同じ batch で contract test を補う。長い test debt を残さない

---

## 7. 外部 protocol と tool interface の方針

- 外部 MCP tool 名や protocol payload の形は、よりよい設計があるなら変更してよい
- 外部の形を変えたら、同じ batch で次を済ませる
  - protocol facts source の更新（文書と code を一致させる)
  - contract test の更新
  - change note の更新（`docs/`）

---

## 8. ガードと debt 基準

guard script は次を hard stop しなければならない。

- 新しい `callbacks: Dictionary` 注入 signature
- 新しい大きな dictionary の assembly entry
- file / function の上限超過
- 小さな空壳ファイルの乱立
- 既知 anti-pattern の再流入

残っている debt の基準。

- 基準は下がる一方で、上げてはいけない
- debt を 1 つ消したら、その場で baseline も下げる
- 上限を緩めて新しい結合を隠してはいけない

---

## 9. 実行順序

各 batch は次の順で進めます。

1. 現在の要求、範囲、リスク、検証基準を確認する
2. code refactor と old code deletion を行う
3. 文書と protocol 説明を更新する
4. guard と contract test を走らせる
5. 検証結果と残りリスクを記録する

---

## 10. 逸脱時の扱い

- この規約に反する変更は merge できない
- 緊急修正で一時的に緩める場合でも、同じ batch で必ず戻して hard rule を復活させる。次の batch に持ち越さない

---

## 11. 残っている debt 基準

現在の残存 debt 基準。

- `callbacks: Dictionary` 注入の残り。runtime の主経路ではゼロ。新しい残りは guard で止める
- 大きな dictionary assembly の残り。plugin composition の主経路ではゼロ。新しい残りは guard で止める
- 大きい file の残り（収束中)
  - `plugin/runtime/mcp_runtime_command_service.gd`（331 行、上限 320）
  - `plugin/runtime/user_tool_maintenance_service.gd`（418 行、上限 320）
  - 複数の `tools/*/catalog.gd:get_tools`

これらの debt は減らすだけで、増やしたり、同種の新しい構造へ置き換えたりしてはいけません。

---

## 12. 進める順番

次の順で進めます。飛ばしたり、外へ広げたりしてはいけません。

1. runtime の callback dictionary をゼロにする
2. composition layer を dictionary 依存から外す
3. HTTP composition layer を軽くする
4. UI の巨大 file を分割する
5. catalog を static data に分ける
6. 旧実装と compatibility path をすべて消す
