# ランタイムサービス

この文書は、`plugin/runtime/`、`plugin/config/`、tool loader がどう協調するか、そして HTTP 入口から入った request がどの executor に流れるかを説明します。

## 状態と設定の層

### `plugin_runtime_state.gd`

この object は軽量な runtime state container として機能し、主に次を持ちます。

- 現在の settings dictionary
- 現在の custom profiles cache
- 現在の CLI scope / Config platform / tab などの UI state field
- mutable runtime field だけを持ち、schema、profile directory、persistence details は担当しない

profile catalog や settings schema の静的な規約は、もうこの object の役目ではありません。

### `plugin_runtime_state_service.gd`

担当するもの。

- `PluginRuntimeState.build_default_settings()` に基づく settings 初期化
- runtime state の load/save の組み立て
- custom profile の load
- `current_cli_scope` / `current_config_platform` / `needs_initial_tool_profile_apply` などの state field の正規化
- state bootstrap / persistence の詳細を `plugin.gd` から分離すること

### `plugin_runtime_coordinator.gd`

担当するもの。

- `user_tool_watch_service.gd` の stop / configure / start の組み立て
- user tool watcher の外部 refresh callback を、`plugin.gd` の文字列 method 名に頼らず、`plugin_action_router.gd` の明示的 callback へつなぐ
- runtime bridge Autoload の install、state projection、stale instance 診断
- `MCPEditorDebuggerBridge` の install / uninstall lifecycle

### `plugin_dock_coordinator.gd`

担当するもの。

- Dock scene の作成、attach、destroy
- stale Dock の掃除と duplicate instance 検出
- `FileDialog` node の作成 / cleanup と callback 接続
- Dock signal wiring の統一的な組み立て

これで `plugin.gd` は Dock lifecycle の細部を直接持たなくてよくなります。

### `plugin_action_router.gd`

担当するもの。

- Dock / Config / Server / User Tool などの UI event を、対応する feature へ一括で map する
- `plugin.gd` の action forwarding layer として、show message / confirmation、dock refresh、各種 action handler をまとめて受ける
- `user_tool_watch_service.gd` に明示的 callback 入口を与え、watcher が `plugin.gd` の文字列 method 名に依存しないようにする
- user tool catalog refresh と runtime reload に関する補助入口を 1 か所に集める

### `mcp_http_connection_state.gd`

担当するもの。

- connection array、pending data、processing state、request statistics
- `mcp_http_server.gd` に残っていた transport bookkeeping を独立 helper に下ろす
- 今後さらに `mcp_http_server.gd` を薄くするための安定した state boundary を用意する

### `mcp_http_request_decoder.gd`

担当するもの。

- `Content-Length` request body の decode
- chunked body の decode
- trailing data の保持
- incomplete headers / body / chunked body の待機状態を返すこと

これで `mcp_http_server.gd` は HTTP body parse の細部を持たなくてよくなります。

### `tool_profile_catalog.gd`

担当するもの。

- builtin tool profiles
- custom profile storage dir

### `plugin_runtime_state.gd`

担当するもの。

- settings path
- default settings
- collapsed domain / system tool の default
- settings 初期化に必要な category / domain の default input
- 現在の settings / custom profiles / UI state field

### `settings_store.gd`

担当するもの。

- plugin settings の読み書き
- custom profile の読み書き
- profile 名の変更と削除
- tool configuration JSON の import / export

現在の persistence boundary。

- `user://godot_dotnet_mcp/settings.json`
- `user://godot_dotnet_mcp/profiles/*.json`
- ユーザーが指定した import / export JSON path

### `client_config_service.gd`

担当するもの。

- Config page の configuration chain の façade
- serializer / inspection / transaction / launcher adapter への一括委任
- UI feature と、実際の file write / CLI behavior を切り離すこと

### `client_install_detection_service.gd`

担当するもの。

- client の install path 探索
- client の実行状態探索
- 手動 executable path と自動検出結果の正規化
- 短期的な detection cache と失効制御

今は `config_feature.gd`、`ui_state_feature.gd`、`dock_model_service.gd` が直接使い、`plugin.gd` の wrapper を通しません。

### `dock_model_service.gd`

担当するもの。

- Dock に必要な runtime context を集約する
- tool tree で高レベル tool とその下の atomic tool / action を見せるため、完全な tool category を集める
- self-diagnostic、user tool watch、Config tab の install detection 状態をまとめる
- context を `dock_presenter.gd` に渡す

### `dock_presenter.gd`

担当するもの。

- Dock context を最終 UI model に変える
- profile description、central service からの feedback text、Config page の補助表示を解釈する
- `client_config_presenter.gd` を Config page の client view sub-collaborator として公開する

## service と診断の層

### `server_runtime_controller.gd`

これは `plugin.gd` と `MCPHttpServer` の間にある proxy 層です。担当は次の通り。

- server node の作成と attach
- `soft_reload_plugin` のときに controller と server node を再構成すること
- start / stop / restart
- settings と disabled tool list を server に同期すること
- `server_started`、`server_stopped`、`request_received` を入口へ流すこと
- start / reload operation の中で settings projection、server node ensure、HTTP server reinitialize/start、stdio ensure の各 stage の時間を記録し、自診断の slow-operation 解析に使うこと

これで `plugin.gd` は TCP server の細部を直接触らなくてよくなります。

### `mcp_http_server.gd`

これは実際の内蔵 HTTP + MCP service node です。担当は次の通り。

- TCP port を listen する
- HTTP request を受ける
- JSON-RPC / MCP request body を parse する
- HTTP path の分配を `mcp_http_request_router.gd` に任せる
- JSON-RPC method の分配を `mcp_json_rpc_router.gd` に任せる
- `mcp_protocol_facts.gd` から `protocolVersion / toolSchemaVersion / serverInfo` を統一して読む
- `/health`、JSON-RPC response、HTTP response の書き出しと JSON clean-up を `mcp_http_response_service.gd` に任せる
- editor lifecycle の close / restart confirmation、accepted payload、deferred execution を `mcp_editor_lifecycle_action_service.gd` に任せる
- editor lifecycle state snapshot の構築を `mcp_editor_lifecycle_state_builder.gd` に任せる
- `mcp_tool_rpc_router.gd` に `tools/list`、`tools/call`、tool name の解決、result normalisation を任せる
- `mcp_resources_service.gd` に `resources/list`、`resources/templates/list`、`resources/read` を任せ、project info、diagnostics summary、scene / script / resource file read resource を公開する
- `mcp_prompts_service.gd` に `prompts/list`、`prompts/get` を任せ、project orientation、content authoring、diagnostic triage、reference integrity、runtime validation、editor UI control の prompt を公開する
- connection 数、request 数、最近の method と時刻を保持する
- `mcp_tool_loader_supervisor.gd` に tool loader の lifecycle、自動回復、state summary を任せる
- `mcp_editor_lifecycle_endpoint.gd` に editor lifecycle request の parse と action dispatch を任せる
- `mcp_tools_api_service.gd` に `/api/tools` snapshot の構築を任せる
- reinitialize / start path で service bundle、tool loader registration / performance、TCP listen stage の時間を記録する
- `get_tool_access_provider()` で tool access state を `tool_loader.gd` に直接 bridge し、plugin は permission level system を持たない
- `runtime_control_service.gd` を持ち、`system_runtime_*` の editor 側 runtime command 協調入口にする

### `mcp_resources_service.gd` と `mcp_prompts_service.gd`

この 2 つは MCP の native Resources / Prompts surface を tool execution path を通さずに提供します。

- `mcp_resources_service.gd` は project info、diagnostics summary、tool catalog の 3 つの JSON resource を固定で公開し、`scene/{path}`、`script/{path}`、`resource/{path}` template で project file を読む
- `mcp_prompts_service.gd` は `godot.project_orientation`、`godot.content_authoring`、`godot.debug_triage`、`godot.reference_integrity`、`godot.runtime_validation`、`godot.editor_ui_control` の 6 つの prompt を固定で公開し、project orientation、content authoring、diagnostic triage、reference integrity 修復、runtime validation、editor UI 操作の前に、同じ入り口説明を client に渡す。各 prompt は MCP `messages` だけを返し、内容には適用場面、推奨 tool 順、検証要件、避けることが含まれ、tool を直接実行しない
- `system_help` は help payload に `prompt_guides` summary を入れ、client が `prompts/list` で prompt を見つけ、`prompts/get` で parameterized workflow text を取れるようにする
- HTTP JSON-RPC path は `mcp_json_rpc_method_service.gd` からこの 2 つを呼び、stdio path も同じ service を使って、両 transport の返し方をそろえる

### `mcp_tool_loader_supervisor.gd`

担当するもの。

- 現在の `MCPToolLoader` を持つ
