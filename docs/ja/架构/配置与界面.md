# 設定と UI

## Dock の構成

現在の Dock は 3 つの仕事に集中しています。

- `Home`：service state、port、language、debug switch、自診断 summary
- `Tools`：tool category の有効無効切り替えと統計
- `Config`：外部 MCP client 向けの接続設定の表示と書き込み

もう担当しないもの。

- 作者紹介
- 宣伝情報
- tool capability と関係のない説明ブロック

## 入口と page の責務

Dock 入口は今も `plugin.gd` から Godot editor の右側 panel に登録されますが、node 構造は scene 化されています。

- `ui/mcp_dock.tscn`：Dock root scene、title bar、status light、TabContainer を担当
- `ui/server_panel.tscn`：service state と基本設定
- `ui/tools_tab.tscn`：tool tree、search、preview、category/tool の on/off、折りたたみ状態
- `ui/config_panel.tscn`：client 設定と command 生成

対応する controller script は `apply_model(model)` だけを受け取り、service object を直接持ちません。

## `Home` page の操作

### 見える情報

- 状態：service が今動いているか
- service address：現在の host/port から組み立てた MCP address
- active connection：接続中 client 数
- total request：累積 request 数と累積 connection 数
- recent request：最後に受けた HTTP method と時刻

### 実行できる操作

1. port を変える
2. auto start を切り替える
3. debug log を切り替える
4. plugin language を切り替える
5. service を起動する
6. service を再起動する
7. service を停止する
8. plugin を完全 reload する

### 動作説明

- `启动` は `plugin.gd -> ServerRuntimeController.start()` を呼ぶ
- `重启` は先に `reinitialize()`、その後 `start()` を呼び、port、debug mode、disabled tool list を更新する
- `停止` は `MCPServer` の listen だけを止め、Dock は壊さない
- `完全重载插件` は単なる runtime `detach()` / `attach()` ではなく、独立 coordinator node が Godot plugin layer の `set_plugin_enabled(false/true)` を呼び、Project Settings で plugin を off/on するのに近い挙動を目指す
- 完全 reload の前には `MCPDock` の外側 tab、内部 tab、内部 focus の snapshot を記録し、新しい instance が立ち上がったあとに host Dock の `MCPDock` tab に戻してから、元 focus を復元する
- language 切り替えは `settings.language` を更新して軽量な `apply_model()` refresh をするだけで、Dock 全体は作り直さない
- language 切り替えと完全 reload 後の focus 復元は、元の control だけを戻し、無理に focus を奪わない。元 control がない、または focus 不能なら静かに続ける
- language menu は「自称（現在言語での呼び方）」形式で出し、たとえば `English（英文）`、`日本語（日语）` のようにする

## `Tools` page の操作

### 実行できる操作

1. 現在見えている tool を search する
2. 単一 tool、category 全体、domain 全体を on/off する
3. root / category / tool / atomic の折りたたみ状態を記録する
4. 右クリック menu から localized name、English ID、schema を copy する
5. `user` category から user tool 削除 request を出す
6. 選択中 item の preview text、parameter summary、system atomic tool chain を見る

### 動作説明

- tool tree の enabled 数は、実行中 service が返す実際の tool list から計算し、静的な固定値にはしない
- 現在の主 tree は runtime 生成の Tool Presentation Model を優先する。`toolTree` は domain / category / 高レベル tool / atomic / action の階層で tool structure を表し、この model がないときだけ古い local group tree ロジックへ戻る
- `/api/tools`、MCP `tools/list`、stdio `tools/list` は flat な `tools[]` を保ちつつ、`toolTree`、`toolGroups`、`groupPath`、`treeChildren` も返し、client と Dock が同じ presentation semantics を共有できるようにする
- search result は独立 search collaborator が先に計算し、その後で main controller が tree を組み直す
- preview text は独立 preview collaborator が作り、今は domain、category、tool、atomic、action の 5 種類の node をカバーする
- `collapsed_system_tools` 設定は tree 上で既定で折りたたむ system tool を決め、既定では公開 built-in `system_*` tool を対象にする

## `Config` page の操作

configuration 生成ロジックは UI script から切り離され、helper module にまとめています。目的は 2 つです。

- Dock code と string template の結合を弱める
- client ごとの configuration 変更が UI layer を直接汚さないようにする

### platform filter

Config page の上部で Agent platform を選び、その platform に対応する内容だけを見せる。もう全 platform 情報を 1 つの長い list に詰め込まない。

現在の platform は 2 系統です。

- desktop / config file 系：Claude Desktop、Cursor、Trae、Codex Desktop、OpenCode Desktop、Windsurf、Cline、Roo Code、Cherry Studio
- CLI command 系：Claude Code、Codex、Gemini、OpenCode、Qwen Code

### 推奨の流れ

1. まず上部の platform dropdown で target client を選ぶ
2. 今見えているのが「config file area」か「CLI config area」かを確認する
3. desktop client なら、config file path と JSON を確認してから `write` か `copy` を選ぶ
4. CLI client なら、command text を確認し、scope 対応 client なら `user / project` scope も確認する
5. copy または write が終わったら、client 側で接続確認をする

### config file area

現在 one-click write を支援する client は次です。

- Claude Desktop
- Cursor
- Trae
- Windsurf
- Cline
- Roo Code
- OpenCode

各項目には次が含まれます。

- config file path
- 書き込む JSON text
- one-click write button
- copy button

config text area は `PanelContainer + Label` で持ち、`TextEdit.read_only` の theme style を再利用する。copy button は text area の右上に浮くボタンとして表示し、文字でも icon でも出せる。Config page の外側の group card と client card は `Tree.panel` background と `Editor.separator_color` border を使い、`Tools` page と同じ深さ感を保ちつつ、カードの境界ははっきりさせる。

one-click write の動き。

1. 現在の JSON text を parse する
2. target file がすでにあり、合法な JSON なら最小限の merge をする
3. `mcpServers["godot-mcp"]` node だけを更新し、他の server 設定は壊さない
4. directory がなければ再帰的に作ってから書き込む

補足。

- `write` は `mcpServers["godot-mcp"]` だけを更新し、target file の他の MCP service は消さない
- `copy` は text box にある complete configuration を copy するので、version control 管理下や制約のある環境に手で貼るのに向く

### CLI config area

現在の CLI platform は次です。

- Claude Code
- Codex
- Gemini
- OpenCode
- Qwen Code

そのうち。

- Claude Code、Gemini、Qwen Code は scope dropdown（`user` / `project`）を追加表示する
- Codex、OpenCode は current command text、config file、または現在 project を直接開く操作を見せる

CLI area の制約。

- `scope` は、user-level / project-level configuration を支える CLI command parameter や config path に影響する
- CLI area は client 自身の command 実行で one-click add / remove を優先する。直接 command write を支えない client には copy または open config file の流れを出す
- platform を desktop client に切り替えると CLI area は隠し、無関係な command が同時に見えないようにする

## settings persistence

editor 内 settings は次を満たすべきです。

- default value がある
- reset できる
- restart 後に復元できる
- current project と current editor の境界が明確

現在の persistence path。

| Path | 役割 |
|---|---|
| `user://godot_dotnet_mcp/settings.json` | port、language、auto start、debug mode、disabled tool、collapsed state、完全 reload 時の一時 focus snapshot を保存する |
| `user://godot_dotnet_mcp/profiles/*.json` | custom tool profile を保存する |

load logic は `plugin/config/settings_store.gd` にある。

- 初回で settings file がなければ、すべての category と domain を既定で折りたたむ
- 既存 settings file があれば、足りない field は互換補完する
- `tool_profile_id` が空なら、強制的に `system` に戻す

## UI 変更に関する文書上の約束

UI や settings item が変わったら、文書には次を一緒に書く。

- 入口 page の位置
- setting key または config field 名
- protocol layer に影響するか
- 既存 client 設定の移行が必要か

## 実装方法

### UI 装配

現在の流れは次の通りです。

1. `_dock_model_service.build_model()` が state、tool list、config text、`editor_scale` をまとめる
2. `ui/mcp_dock.gd` が model を 3 つの page に配る
3. `ui/server_tab.gd` が現在の `Home / 主页` page を担当し、まず `server_tab_model_projection.gd` で純表示 data に投影してから、text、button 状態、dropdown を埋める。`ui/tools_tab.gd`、`ui/config_tab.gd` はそれぞれの collaborator を読み続ける
4. user action は明示的 signal で `plugin.gd` に戻り、service object または settings store を呼ぶ

### UI 文言のローカライズ

現在の Dock root container、Home / Tools / Config 3 page、config client title、install state、log level、tool tree name、高レベル tool 説明はすべて localization key から埋める。scene file の hard-coded text には頼らない。

Godot editor がよくある英単語をさらに自動翻訳しないように、Dock root container と 3 つの page root control は明示的に `auto_translate_mode` を切っている。したがって plugin 内 language 切り替えは完全に `LocalizationService` で制御し、editor の全体翻訳状態には依存しない。

tool 実行時 error は引き続き構造化された `error/message` で返し、呼び出し側が tool の意味に沿って処理する。Dock 内で見える text はローカライズ層で統一して管理する。

### UI scaling

現在の scale policy は `EditorInterface.get_editor_scale()` を唯一の倍率源にする。scale が効く場所。

- Dock root container の minimum size
- page 内 margin
- 各種 `HBoxContainer` / `VBoxContainer` / `GridContainer` の spacing
- `SpinBox`、`OptionButton`、`Button` の minimum height
- Config の text area の read-only panel height
- Tools tree の動的説明文字の font size

理由。

- 元の定数は、高 DPI や editor scale が `1.0` を超えると詰まり気味に見える
- 現在の scale logic はすでに各 controller 内に下ろしてあり、単一入口 script に頼らない

### service page と config page に追加の layout 制約が要る理由

この 2 つの page には次がある。

- `GridContainer`
- 長文 `Label`
- 読み取り専用 `TextEdit`
- 横に広がる必要がある `OptionButton`

明示的に `size_flags_horizontal = SIZE_EXPAND_FILL` と倍率に応じた minimum height を補わないと、次のような問題が出る。

- text area が細すぎる
- button の高さが editor 全体の見た目と合わない
- checkbox の文言が端に寄る、または見えていないと誤解される
