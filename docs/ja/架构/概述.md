# アーキテクチャ概要

## 参照入口

- 厳格なエンコーディングとアーキテクチャ規則は、まず `docs/架构/编码与架构规范.md` を読んでください。

## 位置づけ

`godot_dotnet_mcp` は、Godot 4 プロジェクト向けに安定して組み立て可能で、検証しやすい自動化入口を提供する、エディタ内 MCP サービス層です。

現在の設計は、次の点を重視しています。

- オフラインスクリプト生成ではなく、エディタ内部のツール呼び出しを中心にする
- Roslyn を Godot .NET ランタイム内で動かし、syntax-first で扱う
- Godot .NET の 4.6+ Mono/.NET ビルドを前提にする
- 外部ホストも子プロセスも使わない
- 似た入口を増やすのではなく、カテゴリ構造の安定を優先する
- Godot.NET プロジェクトの静的解析とバインド検査を中核機能にする
- 必要な GDScript 対応は残しつつ、GDScript を中心には置かない

## レイヤー構造

```text
EditorPlugin
  ├─ plugin.gd
  ├─ Dock scene assembly
  ├─ plugin state and settings assembly
  ├─ service start and stop coordination
  └─ explicit signal connections with the UI controllers

MCPServer
  ├─ plugin/runtime/mcp_http_server.gd
  ├─ tools/core/tool_loader.gd
  ├─ HTTP/TCP listener
  ├─ JSON-RPC / MCP request dispatch
  ├─ tools/list
  └─ tools/call

Tool Executors
  ├─ tools/<category>/executor.gd
  ├─ tools/*.gd (compatibility implementation layer)
  ├─ system (high-level tools: project, scene, script, index, including Atomic Bridge)
  ├─ scene / node / script
  ├─ filesystem / resource / project
  ├─ animation / physics / navigation / audio / ui
  ├─ editor / debug / plugin domains
  └─ custom_tools/*.gd (User tools, loaded by system/executor.gd)

Plugin-internal Roslyn
  ├─ addons/godot_dotnet_mcp/dotnet_bridge/ (plugin-local Roslyn syntax library)
  ├─ plugin/runtime/roslyn/ (plugin-local Roslyn facade)
  └─ syntax-first analysis, no SemanticModel

Shared Helpers
  ├─ base_tools.gd
  ├─ plugin/config/config_paths.gd
  └─ tools/core/*
```

## ランタイムオブジェクトの関係

エントリポイントは、単一の巨大スクリプトから薄い装配層へ整理されました。現在のオブジェクト構成は次の通りです。

```text
plugin.gd
  ├─ PluginRuntimeState
  ├─ SettingsStore
  ├─ ServerRuntimeController
  ├─ ToolCatalogService
  ├─ ClientConfigService
  ├─ DockModelService
  ├─ DockPresenter
  ├─ PluginReloadCoordinator
  ├─ MCPRuntimeBridge (Autoload, injects the main project runtime event channel)
  ├─ MCPEditorDebuggerBridge (receives editor debugger session events)
  └─ ui/mcp_dock.tscn
       ├─ ui/server_panel.tscn
       ├─ ui/tools_tab.tscn
       └─ ui/config_panel.tscn
```

つまり、`plugin.gd` は装配、状態同期、信号ブリッジだけを担い、Dock のモデル集約と表示マッピングは別の協力者に分離されています。

## 主要責務

### `plugin.gd`

担当すること。

- プラグインのライフサイクル管理
- Dock シーンとコントローラの装配
- 状態、サービス、ツールカタログ、設定サービスの接続
- 最小限の公開 API の提供 (`get_server` / `start_server` / `stop_server`)
- `tool_loader` 向けの安定した `get_tool_access_provider()` ブリッジ
- `editor_scale`、現在言語、サービス参照を Dock モデル層へ渡すこと
- 完全再読込の前後で Dock タブ、フォーカス、スナップショットを保存・復元すること

担当しないこと。

- Dock ノードツリーの具体的な構築
- profile の照合とツール数の計算
- 設定ファイルの詳細な読み書き
- プロトコル層のリクエスト分配
- ボタン押下後の個別コントロール更新

### `plugin/runtime/mcp_http_server.gd`

- リクエスト受信
- プロトコル解析
- ツール一覧の構築
- `MCPToolLoader` へのツール呼び出し転送
- 一貫したレスポンス整形
- 接続数、リクエスト数、直近の method と時刻の追跡

### `tools/core/tool_loader.gd`

- `category -> script path -> runtime instance` の装載関係を維持
- builtin ツールと `custom_tools/*.gd` を走査
- 有効化された category を先に読み込み、他 category の定義キャッシュは保持
- 単一 domain と全体 hot reload の入口を提供
- load state、reload status、性能要約を集約

### `tools/*.gd`

- それぞれの能力 domain に対する権威ある入口を提供
- `action` でサブ挙動を分配
- 入力、出力、エラー構造を揃える
- `base_tools.gd` のパス解析、ノード直列化、JSON/Variant 正規化 helper を再利用

### `ui/*.tscn` + `ui/*.gd`

- Dock ルート UI と各タブのノード構造を持つ
- 明示的な信号で `plugin.gd` にユーザー操作を伝える
- 表示と操作だけを担当し、サービスのライフサイクルは持たない
- `editor_scale` に応じて余白、最小サイズ、テキスト領域の高さを調整する
- プラグイン内部テキストの Godot 自動翻訳を切り、表示言語はローカルの本地化サービスで決める

### `plugin_*` サービスオブジェクト

- `plugin/runtime/plugin_runtime_state.gd` は runtime fields と current settings / custom profile state を持つ
- `plugin/runtime/tool_profile_catalog.gd` は builtin profile の目録と profile 保存先を持つ
- `tools/tool_registry.gd` は builtin executor 登録の事実源
- `tools/tool_manifest.gd` は tool domain と category metadata の安定入口
- `plugin/config/settings_store.gd` は設定と custom profile の永続化を担当
- `plugin/runtime/server_runtime_controller.gd` は `MCPHttpServer` のライフサイクルと状態プロキシを担当
- `plugin/runtime/tool_catalog_service.gd` は domain / category / profile の計算を担当
- `plugin/config/client_config_service.gd` は Config ページの facade で、具体処理は serializer / inspection / transaction / launcher adapter 協力者へ下ろす

### `plugin/runtime/roslyn/*`

- `plugin_roslyn_service.gd` は C# syntax analysis 要求を扱う plugin-local Roslyn service facade
- `PluginRoslynRuntimeFacade.cs` は Roslyn syntax tree を DTO に変換する C# facade
- `PluginRoslynSyntaxCore.cs` は共有 Roslyn syntax core

## 起動フロー

1. `plugin.gd._enter_tree()` が `_load_state()` を呼び、`user://godot_dotnet_mcp/settings.json` と `user://godot_dotnet_mcp/profiles` から読み込む。
2. プラグインが言語を適用し、`ServerRuntimeController` を組み立てる。
3. `MCPRuntimeBridge` を `project.godot` へ注入して Autoload として登録する。
4. `MCPEditorDebuggerBridge` を `EditorDebuggerPlugin` に登録し、主プロジェクトの debugger session events を受け始める。
5. 入口が `ui/mcp_dock.tscn` を生成し、すべての明示 signal を接続する。
6. 初回読み込みなら builtin profile から `disabled_tools` を計算する。
7. `auto_start` が有効なら server を起動する。
8. 直前の完全再読込で保存された focus snapshot があれば、最初の更新後に Dock tab、内部 tab、フォーカス中コントロールを復元する。
9. `_process()` が 0.5 秒ごとに Dock model を再構築し、service state と統計を同期する。

## UI データフロー

Dock は一方向データフローを使います。

1. `_dock_model_service.build_model()` が `dock_model_service.gd` に state、statistics、tools、config text、`editor_scale` の集約を委譲する。
2. `dock_model_service.gd` が context を `dock_presenter.gd` に渡して最終 model を作る。
3. `mcp_dock.gd.apply_model()` が model を 3 つの tab に配る。
4. tab controller は `start_requested`、`tool_toggled`、`config_write_requested` のような signal としてユーザー操作を返す。
5. `plugin.gd` が signal を受け、状態を更新し、service object を呼び、再度 `_refresh_dock()` を行う。

この構造の利点は次の通りです。

- UI スクリプトが service 参照を保持しなくてよい
- 言語切替とスケーリング更新をまとめて再描画できる
- どの tab も model から再生でき、後のテストや分割がしやすい

## 現在のアーキテクチャ制約

- ツール名はカテゴリの安定を優先し、重複した prefix を安易に増やさない
- 戻り値は MCP クライアントがそのまま消費できる形で返す
- 書き込み操作は可能な限り write-then-read の検証を持つ
- シーン、スクリプト、リソース系ツールはエディタ内ワークフローを優先する
- 外向きの category 名は安定させ、内部ディレクトリ構成は今後も進化してよい
- プラグイン UI はシーンベースで組み、入口スクリプトは薄い装配層に保つ
- tab スクリプトは表示と操作だけを担当し、`plugin/runtime/mcp_http_server.gd` へ直接触れない
- スケーリングの唯一の倍率源は `EditorInterface.get_editor_scale()` である
