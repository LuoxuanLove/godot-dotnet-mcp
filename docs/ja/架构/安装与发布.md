# インストールとリリース

この文書は、Godot .NET MCP プラグインのインストール方法、有効化手順、リリース前確認をまとめます。

このプラグインは self-contained です。Roslyn の syntax analysis は Godot .NET runtime 内で動き、外部 host process は必要ありません。

---

## インストール方法

### 方法 1: Godot プラグインマーケット

Godot で対象プロジェクトを開き、`AssetLib` タブで `Godot .NET MCP` を検索して `Install` を押します。Godot の asset library ページを直接開いても構いません。

```text
https://godotengine.org/asset-library/asset/4923
```

導入後はディレクトリ構成を次のように保ちます。

```text
addons/godot_dotnet_mcp
```

そのあと、

1. Godot で対象プロジェクトを開く
2. `Project Settings > Plugins` を開く
3. `Godot .NET MCP` を有効化する
4. `MCPDock` を開く
5. `ホーム` tab で service を起動する

### 方法 2: ソースを直接コピーする

リポジトリ開発や、ローカルプロジェクトへそのまま入れるときに使います。

1. `addons/godot_dotnet_mcp/` をソースから対象 Godot プロジェクトへコピーする
2. Godot でプロジェクトを開く
3. `Project Settings > Plugins` を開く
4. `Godot .NET MCP` を有効化する
5. `MCPDock > ホーム` で service を起動する

---

## 実行時要件

- Godot `4.6+`。`.NET` 対応の Mono/.NET build が必要です
- プロジェクトで `.NET` スクリプト対応を有効にすること

### C# 解析の説明

- C# の syntax analysis はプラグイン内 Roslyn が担当し、Godot .NET runtime 内で動きます
- 取得するのは syntax tree の情報だけで、SemanticModel は使いません。プロジェクト全体の compile load もしません
- 外部 Roslyn のインストールや設定は不要です

## ブランチとマージの流れ

- 長期の `develop` や `main` は持たず、`dev` を唯一の長期統合ブランチとして維持します。`dev` は常に最新の検証可能状態にします
- 機能開発は `dev` から `feature/*` の短命 branch を切り、修正は `fix/*`、文書は `docs/*` から進めます
- PR、`dev` への push、手動実行は plugin validation workflow を起動します。通常の短命 branch PR は `pull_request` 側で検証し、同じ commit で `push` と `pull_request` を二重に回さないようにします。PR は必ず `dev` 向けにし、merge 前に validation を通し、必要な README、CHANGELOG、docs、CI required subset をそろえます。CHANGELOG はユーザー向け機能だけでなく、重要な Documentation と Internal の変化も記録します
- 正式 release の締めは `release/v1.0.1` のような短命 branch を使います。version、change log、doc、validation 結果を確認してから `dev` に戻します

---

## リリース入口

詳細な手順は `docs/流程/发布Runbook.md` を参照してください。release flow では Godot Asset Library と `addons/godot_dotnet_mcp/` の直接コピーだけを配布経路として残し、zip package、release bundle、ローカル build artifact、その導入手順は扱いません。`dev` 更新後は `next` draft release を次版の説明草稿として保てます。draft と正式 release はどちらも `docs/流程/release-notes/release-notes-v*.md` の手書き要約、`docs/ja/CHANGELOG.md` の明細、commit summary を同じ構造へ描画します。正式な `v*` release では version 一致と release note source の preflight を行い、同じ version と同じ commit で成功した dry-run があれば、重複する build と harness チェックを飛ばせます。

Agent や bot が参加する場合は `docs/流程/Agent与Bot流程.md` に従います。短命 branch の commit と push は自動化できます。追加アカウントを使わない場合は、`actions-bot-relay` で `github-actions[bot]` に patch から PR を作らせることもできます。遠隔の `dev` merge は maintainer が GitHub PR page で手動確認します。

## 検証のすすめ

### install 閉ループ

次の順で検証するのがおすすめです。

1. Godot でプラグインを有効化でき、`MCPDock` を開ける
2. `MCPDock > ホーム` で service state が正しく表示される
3. `GET http://127.0.0.1:3000/health` が正常に返る
4. `GET http://127.0.0.1:3000/api/tools` が tool list を返す
5. MCP client が `http://127.0.0.1:3000/mcp` に接続できる
6. C# script tool (`script_inspect`、`script_exports` など) が `engine=roslyn`、`mode=syntax` を返す

### release 前チェック

少なくとも次を確認します。

1. `plugin.cfg`、protocol facts、change log の version が一致する
2. README、CHANGELOG、`docs/流程/release-notes/release-notes-v*.md`、関連文書、validation 結果がそろっている。CHANGELOG には重要な Documentation / Internal 変化が入っており、release notes はユーザーが見える release 叙事だけにする
3. source tree にプラグイン外コードやローカル build artifact が混ざっていない
4. `.github/workflows/**` の変更は workflow lint を通している
5. PR の target branch は `dev` で、正式 release の `v*` tag、`plugin.cfg`、英語 changelog、簡体字 changelog、release note source file の version が一致している
6. release note はプラグイン自身の要約、互換性注意、検証情報、commit summary だけを含む
