# プラグイン Headless テスト

この文書は `Godot Headless Harness` の今の構造、coverage、既知の境界を説明します。

---

## 目的

plugin 側テストの目的は次の通りです。

- `gdUnit` や `GUT` のような third-party framework を持ち込まない
- repository 内の fixture project を使い、直接 `headless Godot` を動かす
- plugin runtime、tool loading、routing、system impl の要となる動きを確かめる
- plugin runtime refactor に対して素早い regression 面を持つ

## 今の重要な実装点

### 1. `Program.cs` は一時的な本物の環境を組み立てる

今の harness は元の repository 直下でそのまま動かすのではなく、次の手順で進めます。

1. `tests/godot_plugin_harness_fixture/` をコピーする
2. `addons/godot_dotnet_mcp/` をコピーする
3. 新しい一時 `stageRoot` で Godot を起動する
4. `res://tests/headless_suite_runner.gd` を走らせる
5. harness 自身が起動した `dotnet build` と headless Godot PID を `.tmp/godot_plugin_harness/processes/<runId>.json` に記録する

このやり方の利点。

- テスト環境が実際の装配経路に近い
- 作業ディレクトリを直接汚さない
- 失敗時は `--keep-stage-root` で現場を残して調べられる
- process cleanup は registry に登録した harness-owned の一時 process だけに限定される。`godot` や `dotnet` の process name を一括で殺したり、今この MCP を載せている editor session を cleanup 対象にしたりはしない

### 2. suite は単独 case と batch 選択の両方を支える

`headless_suite_runner.gd` は今、次を扱います。

- case ごとの start / end log
- `GODOT_PLUGIN_HARNESS_ONLY_CASE` で単独 case を選ぶ
- `--cases` / `GODOT_PLUGIN_HARNESS_SELECTED_CASES` で複数 case を一度に選ぶ
- suite と case ごとの `duration_ms`
- 各 case の `cleanup_case()` hook
- suite 末尾の `_suite_final_cleanup()`

これは hang、performance、resource cleanup を調べるのに役立ちます。CI required subset の普通の headless case は 1 回の stage / Godot run にまとめ、共有 headless state に敏感な少数の case は独立 run のまま残します。editor probe が必要な case も分けて走らせます。

### 3. headless path には既定の tool access provider がある

bare `MCPHttpServer.new()` は、plugin の parent がない headless path で default tool access provider を作ります。これで loader が access state source を持たず、`tool_loader_status=no_visible_tools` になるのを防ぎます。

今の headless path は本当に tool directory を装着し、tool state を公開できます。plugin は権限 level の設定をもう持ちません。

### 4. 第一段の安定 test seam を足した

今の plugin 側 seam は次の通りです。

- `mcp_editor_lifecycle_endpoint.gd`
- `mcp_editor_lifecycle_action_service.gd`
- `mcp_editor_lifecycle_state_builder.gd`
- `mcp_http_request_router.gd`
- `mcp_http_response_service.gd`
- `mcp_json_rpc_router.gd`
- `mcp_protocol_facts.gd`
- `mcp_tools_api_service.gd`
- `mcp_runtime_fallback_store.gd`
- `mcp_runtime_reply_service.gd`
- `mcp_runtime_control_request_coordinator.gd`
- `mcp_runtime_control_reply_resolver.gd`
- `plugin_dock_coordinator.gd`
- `plugin_runtime_coordinator.gd`
- `client_config_serializer.gd`
- `client_config_inspection_service.gd`
- `client_config_file_transaction.gd`
- `client_config_file_support.gd`
- `client_config_launcher_adapter.gd`
- `tools_tab.gd`。context menu、model、selection、search、preview を内聚済み
- `mcp_http_server.gd` の public test entry
- `mcp_runtime_bridge.gd` の public command capture / fallback entry
- `initialize / /health` path に対する `protocolVersion / toolSchemaVersion / serverInfo` の統一 protocol field 断言
- `tool_loader.gd` の facade と `tool_lsp_diagnostics_adapter.gd` の loader-owned GDScript diagnostics 分離
- `tool_lsp_diagnostics_adapter.gd` が GDScript LSP diagnostics service の唯一の主 chain owner であり、正式 source では `GDScriptLspDiagnosticsService.get_singleton()` fallback を許さない
- `script/csharp_edit_service.gd` と `script/gdscript_edit_service.gd` の facade、semantic provider、edit action service の分離

これは、headless contract test がもう production code の underscore method に直接依存していないことを意味します。

## 現在の境界

### 1. private method name 依存は抜けたが、seam はまだ独立させられる

`http_server_contract_test.gd` と `runtime_bridge_contract_test.gd` は、今は public test entry を通ります。内部 method 名の変更や分割で test が先に壊れる危険はかなり減りました。

ただし seam の一部はまだ `mcp_http_server.gd` と `mcp_runtime_bridge.gd` に残っています。今の batch で runtime fallback / reply 行動は独立 helper に分け、`client_config_service.gd` も facade に寄せました。

### 2. 現在は structure contract と局所 fake の混合モード

今はこの形が実際の test の姿です。

## 現在の実行コマンド

推奨コマンド。

```powershell
dotnet run --project .\tests\godot_plugin_harness\GodotPluginHarness.csproj -c Release -- --godot-path "<Godot Editor Path>"
```

よく使う追加 option。

- `--keep-stage-root`
- `--cases case_a,case_b`
- `--cleanup-stale-processes`

現在の出力には次が含まれます。

- suite success と success-marker detection
- stage root
- 各 case の result と `duration_ms`
- total suite duration と phase timings
- Godot exit code
- exit cleanup diagnostics
- stderr summary

通常 headless suite で `ObjectDB instances leaked at exit` または `resources still in use at exit` が見つかると、harness は失敗し、`reason=godot_exit_leaks_detected` を残します。editor probe mode は editor exit noise を引き続き無視し、`exitCleanupWarningPolicy=ignored_editor_probe` で示します。

## 結論

plugin headless harness は準備できており、実際の runtime issue を見つけて修正する助けになっています。現在の focus は、testing seam と cleanup boundary を安定して保つことです。
