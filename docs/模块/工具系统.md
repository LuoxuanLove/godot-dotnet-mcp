# 工具系统

## 概览

`Godot .NET MCP` 的工具系统按能力域拆分，每个工具族负责一类明确工作流，例如场景管理、节点修改、脚本分析、资源处理或插件运维。

当前版本的工具目录更强调三点：

- 分类稳定：优先按能力域找工具，而不是在单个大工具里堆叠过多动作
- 写后可验证：大多数写操作都应配套读回或查询工具
- 面向真实使用：优先覆盖 Godot 编辑器内的常见操作，而不是追求理论上的 API 全覆盖


## MCP Resources 与 Prompts

JSON-RPC 层除 `tools/list` / `tools/call` 外，还提供一等 MCP Resources 与 Prompts：

- `resources/list` 暴露项目信息与诊断摘要 JSON resources，保留 capability 与 tool catalog JSON resources 供客户端快速建立上下文。
- `resources/templates/list` 暴露 `godot-dotnet-mcp://scene/{path}`、`godot-dotnet-mcp://script/{path}` 与 `godot-dotnet-mcp://resource/{path}` 三个只读模板。模板读取会把项目相对路径归一化为 `res://`，拒绝 `..`、绝对路径和非匹配扩展。
- `prompts/list` / `prompts/get` 暴露 `godot.scene_bootstrap`、`godot.debug_triage`、`godot.binding_fix` 三个参数化 prompt，返回 MCP `messages` 形状，帮助客户端按场景创建、调试排查和 C# 绑定修复流程起步。

这些能力不替代高层工具；它们用于连接建立后的轻量上下文读取与工作流提示。需要执行编辑器操作或修改文件时，仍应通过相应 `system_*`、`scene_*`、`script_*`、`resource_*` 或 `filesystem_*` 工具完成。

Prompt Guides 是 MCP 原生 prompt surface，不通过 `tools/call` 执行动作。客户端应先用 `prompts/list` 枚举可用 prompt，再用 `prompts/get` 传入可选参数读取工作流正文：`godot.scene_bootstrap` 用于场景修改前的项目状态、场景验证、结构分析与安全编辑顺序；`godot.debug_triage` 用于按项目状态、编辑器日志、运行时诊断和 DAP 证据排查错误；`godot.binding_fix` 用于在修复 C# / GDScript / signal / export / NodePath 绑定前先运行绑定审计、脚本分析和场景验证。连接后调用 `system_help` 也会返回 `prompt_guides` 摘要，便于 Agent 从帮助入口发现这些 prompt。

## 当前分组

Tools 页签当前按以下根分组展示：

| 根分组 | 主要分类 | 典型用途 |
|---|---|---|
| `Core` | `system`、`scene`、`node`、`script`、`resource`、`filesystem`、`project`、`editor`、`debug`、`dap`、`group`、`signal` | 系统高层工具、场景、节点、脚本、资源、项目、编辑器日常操作与 Godot DAP 调试能力 |
| `Plugin` | `plugin_runtime`、`plugin_evolution`、`plugin_developer` | 插件运行状态、User 工具管理、开发者控制项 |
| `Visual` | `animation`、`material`、`shader`、`lighting`、`particle`、`tilemap`、`geometry` | 动画、渲染、视觉资源和关卡可视内容 |
| `Gameplay` | `physics`、`navigation`、`audio` | 物理、寻路、音频和运行时行为 |
| `Interface` | `ui` | UI 结构、主题与布局 |
| `User` | `user` | 通过用户扩展机制加载的自定义工具 |

## 主要工具分类

### `system`

系统层是 Agent 使用本插件的推荐起点，提供项目状态、插件 freshness / 生命周期重载、编辑器界面控制、运行时诊断、场景分析、脚本结构检查和符号索引等高层能力。

当前公开的系统高层工具分为八组：

**项目级**：`system_project_state`、`system_editor_state`、`system_runtime_diagnose`、`system_project_configure`、`system_project_run`、`system_project_stop`。其中 `system_project_state` 支持 `summary=true` 返回紧凑状态，也支持 `sections=[...]` 按 `summary`、`project`、`files`、`runtime`、`capabilities`、`health` 分段读取；未指定时仍返回完整平铺响应。`system_project_run` 可选通过异步 MCP tool path 等待 runtime bridge 结构化事件中的 `success_markers` / `failure_markers`；未提供 marker 时保持兼容的立即返回和 `timeout_ms` 自动停止语义，提供 marker 时 `timeout_ms` 改为带上限的等待超时，失败 marker 优先，`auto_stop` 默认只通过 `scene_run stop` 收尾。该能力读取的是 runtime bridge 结构化日志，不是通用 stdout 捕获。

**插件生命周期级**：`system_plugin_reload`、`system_plugin_update`。`system_plugin_reload` 用于读取运行中插件实例与磁盘 / 同步状态的 freshness，或调度一次完整插件 disable/enable 生命周期重载；调用成功表示已调度，重载后客户端应重新连接并重新拉取工具清单。`system_plugin_update` 用于读取当前版本 / fingerprint / source ref，选择更新来源，启动 ref discovery / sync，并轮询同步与重载进度。

**编辑器界面级**：`system_editor_control`、`system_editor_log`。其中 `system_editor_control` 会在控件枚举 / 截图 / 点击结果中返回坐标映射信息，并支持 `click_control` / `right_click_control` 以 Control 本地坐标派发 Godot `Viewport` 内部鼠标事件；它不移动物理光标，也不执行系统级窗口控制。

**运行时自动化级**：`system_runtime_control`、`system_runtime_step(action=step|capture|input)`

**DAP 调试级**：`system_dap_debugger(action=status|get_settings|set_settings|initialize|launch|attach|configuration_done|disconnect|terminate|threads|set_breakpoint|remove_breakpoint|list_breakpoints|pause|continue|step_over|stack_trace|output)`，默认连接 `127.0.0.1:6006` 且仅允许 loopback 主机，使用 DAP `Content-Length` JSON 帧请求 Godot 调试端点；端点不可达时统一返回 `dap_unavailable` 结构化数据，便于客户端降级处理。协议响应默认不回显 raw request / messages；需要排查协议帧时可显式传入 `include_raw=true` 获取已脱敏的原始上下文。

运行时自动化与项目只读能力分开报告：`system_project_state(include_runtime_health=true)` 和 `system_editor_state` 会返回 `runtime_capabilities`，其中 `can_start_project`、`can_control_runtime`、`can_capture_runtime`、`headless_logic_ok`、`visible_capture_required`、`can_run_without_focus`、`no_focus_launch_supported`、`foreground_window_policy`、`foreground_window_fallbacks` 与 `blocking_reasons` 用于判断当前 MCP 是否能启动、接管、截图运行时或保证不抢焦点。项目、场景、脚本等只读工具可用时，这些运行能力仍可能因为编辑器接口缺失、编译错误、没有 commandable debugger session、外部 Godot 进程未接入或当前平台无法保证 no-focus 启动而为 false。

**场景级**：`system_scene_validate`、`system_scene_analyze`、`system_scene_patch`

**脚本级**：`system_bindings_audit`、`system_script_analyze`、`system_script_patch`

**索引级**：`system_project_symbol_search`、`system_scene_dependency_graph`

与原子工具的关系：系统工具通过 Atomic Bridge 组合调用下层原子 executor，适合"理解上下文 → 分析问题 → 批量修改"的完整工作流；原子工具适合已知目标的精细操作。

运行时自动化组的额外约束是：

- `system_project_run` 的 marker 校验只匹配 runtime bridge 结构化事件，不提供截图回退、后台 / no-focus / minimized 启动或项目专属 PASS / FAIL 约定；marker 数量、长度、等待时间、轮询间隔和日志尾部数量均被限幅。
- 只对编辑器内运行态开放，不覆盖独立导出程序或桌面级自动化。
- 需要先显式启用 `system_runtime_control(action=enable)`。
- `step` 是长期推荐主闭环，复杂循环由外层 Agent 自己编排。

索引组的额外约束是：

- 不再公开单独的 `index_build` 工具。
- `system_project_symbol_search` 与 `system_scene_dependency_graph` 会在首次调用时自动构建内部索引。
- 当项目文件在长会话中发生变化时，这组工具会自动检测 stale cache 并重建；`refresh_index=true` 仍可用作显式强制刷新。

详细说明见 [System工具层.md](System工具层.md)。

当前常用工具包括：

- `scene_management`
- `scene_run`
- `scene_hierarchy`
- `scene_bindings`
- `scene_audit`

适合场景：

- 打开或切换当前编辑场景
- 读取当前选中节点和层级结构
- 对 C# / GDScript 导出字段做场景绑定检查

### `node`

当前常用工具包括：

- `node_query`
- `node_property`
- `node_transform`
- `node_visibility`
- `node_process`
- `node_call`
- `node_hierarchy`
- `node_lifecycle`

适合场景：

- 查询节点路径和节点信息

### `plugin_runtime`

`plugin_runtime` 负责插件自身的运行控制和工具装载状态。

当前工具包括：

- `plugin_runtime_state`
- `plugin_runtime_reload`
- `plugin_runtime_server`
- `plugin_runtime_toggle`
- `plugin_runtime_usage_guide`

适合场景：

- 查看已加载的 domain 和最近一次重载结果

### `plugin_evolution`

`plugin_evolution` 负责 User 工具的完整生命周期管理。

全部 7 个工具：

- `plugin_evolution_list_user_tools` — 列出所有已注册 User 工具

- `plugin_evolution_delete_user_tool` — 预览或删除 User 工具脚本（两步授权）

- `plugin_evolution_check_compatibility` — 对比现有 User 工具与当前脚手架版本
- `plugin_evolution_usage_guide` — 返回推荐的授权工作流说明

详细说明见 [用户扩展.md](用户扩展.md)。

## 插件工具域

插件相关工具按职责拆分为独立 category：

- `plugin_runtime`
- `plugin_evolution`
- `plugin_developer`

新接入、文档和脚本示例应使用对应的细粒度工具名，并由 `tools/tool_registry.gd` 统一注册与展示。

## 典型使用方式

### 先查再改再验证

推荐顺序：

1. 先用查询工具确认目标路径、状态或文件存在性。
2. 再执行写操作。
3. 最后立即用对应读取工具验证结果。

示例：

1. 用 `node_query` 或 `scene_hierarchy` 找到目标节点。
2. 用 `node_property`、`filesystem_json` 或 `animation_track` 执行修改。
3. 用 `node_property`、`filesystem_json` 或 `animation_track` 读回确认。

### 插件和 User 工具操作

如果涉及插件自身状态或 User 工具：

1. 先用 `plugin_runtime_state` 查看当前状态。
2. 再用 `plugin_runtime_toggle` 或 `plugin_runtime_reload` 做调整。
3. 如需处理 User 工具，再使用 `plugin_evolution_*`。
4. 变更完成后可再次读取状态或审计记录确认结果。

### 运行时问题回读

如果问题发生在主项目运行阶段：

1. 正常从编辑器运行主项目。
2. 停止后使用 `system_runtime_diagnose`。
3. 读取运行时错误、编译问题与性能快照。

## 输入与返回约定

### 工具名格式

当前工具系统统一使用：

- 工具名：`{category}_{tool}`
- 工具参数：按各工具自己的字段定义传入

例如：

- `scene_management`
- `plugin_runtime_reload`
- `plugin_evolution_scaffold_user_tool`

`/api/tools`、MCP `tools/list` 和 Dock Tools 页会基于同一份“当前可见工具集合”生成展示结果；插件运行态调试细节统一收敛在 `plugin_runtime_state` 的 action 中，不再为自检扩增新的顶层工具名。

### 常见路径写法

- 资源路径使用 `res://`
- 节点路径优先使用当前场景根节点下的相对路径
- `/root/...` 风格路径在当前版本也可用

### 常见返回结构

工具返回结果默认包含以下字段：

- `success`
- `message`
- `data`

失败时会返回：

- `success: false`
- `error`

## 使用建议

- 新增工作流优先寻找现有分类，不要先假设需要新工具。
- 修改项目内容时，优先选择可以“写后读回”的工具组合。
- 需要插件说明时，可直接使用三个 `usage_guide` 工具。
- 处理 User 工具前，先阅读 [用户扩展.md](用户扩展.md)。
